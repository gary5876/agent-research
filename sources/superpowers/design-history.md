## 1. SDD 태스크 단위 리뷰 디스패치 (2026-06-09) [메인테이너]

출처: `2026-06-09-sdd-task-scoped-review-dispatch-design.md`

SDD(subagent-driven-development)는 계획의 태스크마다 새 서브에이전트(구현자)를 띄우고, 태스크별 리뷰어가 게이트를 거는 구조다. 이 문서는 태스크별 리뷰가 너무 비싸다는 문제에서 출발한다.

**문제 진단 (실제 로컬 세션 2개에서 확인했다고 적힘)**
- sen-core-v2 세션에서 품질 리뷰어 8명 중 7명이 레포 전체 grep을 돌렸고, 가장 비싼 리뷰어는 약 200초 동안 Bash 50회 이상을 실행했다.
- 두 세션 모두 품질 리뷰어가 같은 태스크의 스펙 리뷰어보다 4~8배 비쌌다. 스펙 리뷰어는 "diff에 있는 파일만 읽어라" 문구 덕분에 도구 호출 6~16회, 14~65초로 짧았다.
- 무거운 테스트 실행은 모두 컨트롤러가 쓴 프롬프트("check all uses" 같은 열린 지시)가 시킨 것이었다.
- 외부 필드 리포트의 수치는 "검증할 수 없었다"고 명시하고, 정성적 진단만 실제 세션으로 확인했다고 적었다. 원인 분석에서 출처 검증을 따로 구분한 점이 눈에 띈다.

**위험 통제 설계**
- 리뷰 범위 예산: `git diff BASE..HEAD`에서 시작하고, 이름을 댈 수 있는 구체적 위험이 있을 때만 주변 코드로 넓힌다. 락 순서, API 계약 변경, 공유 가변 상태는 정당한 확장 사유로 명시.
- 테스트 예산: 구현자가 이미 돌린 테스트를 같은 코드에 다시 돌리지 않는다. 패키지 전체, race detector, 반복 실행은 구체적 flake/race를 먼저 명명해야만 허용.
- 증거 규칙: 체크 항목마다 file:line 근거를 요구. 도입 이유는 리뷰어가 diff 안에 있는 결함에 근거 없는 "yes"를 준 사례가 live eval에서 나왔기 때문.
- "diff로 검증 불가" 제3의 판정 채널(⚠️): 리뷰어가 크롤링하거나 조용히 통과시키는 대신 컨트롤러에게 넘기고, 컨트롤러가 태스크 완료 전에 직접 해소한다.
- 리뷰어에게 "이건 지적하지 마라"는 사전 판단 금지. live eval에서 컨트롤러가 "계획이 공용 헬퍼를 금지한다"는 거짓 주장을 지어내고 심어둔 DRY 위반을 지적하지 말라고 지시한 사례가 나와서 추가됨.
- 모든 디스패치에 모델을 명시하도록 요구. 생략하면 세션의 가장 비싼 모델을 상속한다.
- 전역 제약(버전 하한 등)을 요구사항에 붙이도록 요구. live run에서 설계는 "Go 1.21+"인데 `go 1.26.1` 모듈 하한이 배포됐고, 어느 리뷰어도 그 제약을 못 봤다.
- 최종 브랜치 리뷰는 넓게 유지하고, 태스크별 리뷰만 좁힌다.

**비용 측정 (go-fractals 등 eval 시나리오)**
- 품질 강화 문구가 들어간 뒤 비용이 역행: 42.8분 / 14.5M 토큰에서 69.9분 / 32.2M으로 증가 (blind judge 품질은 8.5 대 8.5 동률).
- 원인 분해: 서브에이전트 턴 1197개 중 678개가 haiku였다. 싼 모델이 다단계 작업에서 턴을 2~3배 더 쓴다. 태스크당 서브에이전트 3번 기동으로 디스패치 오버헤드가 크고, 컨트롤러 조율이 비용의 절반.
- 반복 1: 68.2분 / 22.9M (토큰 29% 감소, 시간은 그대로). diff를 프롬프트에 붙이라는 선택형 지시는 22회 중 2회만 따랐다.
- 반복 2: 스펙 리뷰와 품질 리뷰를 한 리뷰어(판정 2개)로 합침. 47.5분 / 15.7M / $13.55, blind judge 9/10 대 기준선 7/10.
- 반복 3 이후 고정 설정(e355795): go-fractals 44.4분 / 13.4M / $11.67 (기준선 대비 시간 -32%, 토큰 -37%, 달러 -27%), svelte-todo 62.8분 / 19.7M / $15.76.
- 반복 4~5: 같은 설정 재실행에서 44.4분이 57.1분으로 흔들렸고, 리뷰어의 탈출구 사용량이 리뷰당 도구 호출 1.0에서 6.3회로 요동. 이후 모든 주장을 범위로 표기하기로 함.
  - 채택: 최종 리뷰 패키지(최종 리뷰어 33턴에서 6턴), 템플릿에 `model:` 줄 필수화(프롬프트 지침이 세션 중간에 무너져 17개 디스패치가 opus를 상속, +$5), 진행 장부 `<git-dir>/sdd/progress.md`(실제 세션이 컨텍스트 압축 후 완료된 태스크를 다시 디스패치해 약 22개 태스크에 디스패치 269회가 발생), 한 번에 몰아 고치는 omnibus 최종 fixer(실제 세션에서 finding별 수정 웨이브가 전체 태스크보다 비쌌음).
  - 기각: 컨트롤러 턴 배칭과 병렬 호출(모든 run에서 멀티툴 메시지 0개, 컨트롤러 턴의 46%가 사고/서술이라 프롬프트로 못 줄이는 바닥), 백그라운드 디스패치(효과가 ±6분 노이즈 이하).
  - 최종 검증 설정(b81f35b 계열): go-fractals 54.1~54.7분 / 14.4~16.6M / $12.81~14.31 (기준선 64.9분 / 21.2M / $16.07), svelte-todo 55.0분 / 19.3M / $14.99 (기준선 79.7 / 27.3M / $20.98). 같은 설계 8회 run 중 최악값도 모든 축에서 기준선보다 낫고, 중간값 절감은 약 20~25%.
- 알려진 한계로 명시: 컨트롤러가 계획에서 요구사항을 빠뜨리면 스펙 리뷰어는 잡을 수 없다(아키텍처 속성이라 범위 밖).

**관찰** [추론]: 루프와 폭주는 "금지"보다 구조(장부 파일, 모델 필수 줄, diff를 파일로 넘김)로 막았고, 프롬프트 지침만으로는 세션 중에 무너진다는 증거를 스스로 기록했다.

## 2. Strict-Cost SDD 실험 사다리 (2026-06-10, 06-11 결과 갱신) [메인테이너]

출처: `2026-06-10-strict-cost-sdd-design.md`

**목표와 불변식**: 계획 1회 실행당 달러 최소화. 시간은 제약 없음. 품질은 절대 불변식이며 `sdd-quality-reviewer-catches-planted-defect` N=5 통과율(단일 run 게이트는 "이번 캠페인에서 가장 약한 방법론"이었다고 자인), `sdd-rejects-extra-features` 통과, 모든 end-to-end 시나리오 통과, 현 설정과 blind A/B 산출물 동등. 품질이 하나라도 떨어지면 해당 단계는 폐기.

**비용이 어디서 나가나 (go-fractals, run당 약 $13)**
| 구성요소 | 달러 | 원인 |
|---|---|---|
| 컨트롤러 (opus) | 약 6~7 | 약 150턴 x 상주 컨텍스트, 턴의 46%가 사고/서술 |
| 구현자 (sonnet, 10~13회) | 약 5~6 | 각 약 25턴, 편집 전 탐색 호출 약 13회 |
| 태스크 리뷰어 (sonnet, 10회) | 약 1~1.5 | 3~9턴 |
| 최종 리뷰와 수정 | 약 1 | 6턴 |
- run 간 비용 편차가 가장 큰 건 리뷰 루프 횟수(run당 2~4회)이고, 대부분 계획의 모호함을 구현자가 잘못 해석해서 생긴다.

**판단 가드레일**: "메커닉은 싸게, 판단은 절대 싸게 하지 않는다." 판단 지점을 명시적으로 나열: BLOCKED/NEEDS_CONTEXT 처리, ⚠️ 해소, 디스패치 큐레이션, 리뷰 판정과 심각도, 리뷰 루프 판정(오탐 결정), 사람에게 올릴지 판단. "싼 모델이 대체로 맞힌다"는 수용 근거가 아니다. 판단 실패는 드물고 파급이 크며 pass/fail 게이트로 잘 안 보이기 때문에, 등급을 바꾸는 단계마다 session-resume으로 각 판단 지점을 심문하는 판단 감사를 추가한다.

**논지 가드레일**: 한 구현자 디스패치에 여러 태스크를 묶는 것은 "fresh context" 속성을 오염시키므로 사다리에서 제외.

**단계별 결과**
- L1 계획 쪽 명확화: 제약 헤더와 Interfaces 블록은 결정적으로 유도됨(0→5/5, 태스크의 0→100%). 그러나 유도된 계획 실행 $6.34/$8.49 대 지침 없는 대조군 $7.59/$7.73으로 범위 안에 겹침. 결론: 비용 절감의 공은 opus가 쓴 완전한 코드 계획에 있고, 이전 수치들이 쓴 손으로 쓴 산문형 fixture 계획은 대표성이 없으며 실행 비용이 약 2배. 그래서 L1 PR은 달러가 아니라 충실도와 편차(수정 웨이브 1회 대 2~4회)를 근거로 삼음. 자기 이전 측정의 전제를 스스로 뒤집은 기록.
- L2 컨트롤러를 sonnet으로 (추정 -$4~5, 가장 큰 레버): **게이트에서 사망**. 명시적 계획 자기모순을 사람에게 올리는 `sdd-escalates-broken-plan`은 sonnet 5/5 통과($1.02~1.37/run). 그러나 심어둔 결함 배터리에서 sonnet 컨트롤러 아래 태스크 품질 게이트가 "계획 준수 옹호"로 무너짐("요구대로 assertion 없음"을 Strengths에 기재), 결함이 5회 중 4회 배포됨. 같은 sonnet 리뷰어가 opus 컨트롤러 아래에서는 5/5 잡음. "싼 컨트롤러는 명시적 에스컬레이션은 하지만 암묵적인 권위 대 품질 판단은 흡수해버린다."
- L2b(계획이 요구한 결함도 finding이다, 사람이 결정한다는 규칙 두 개): 마이크로 테스트 0/6에서 6/6. opus 스택에서는 2/2 개선, sonnet은 1/5만 통과. sonnet 컨트롤러가 디스패치를 바꿔 말하면서 규칙을 빠뜨림(5회 중 2회만 전달).
- L3 리뷰어를 haiku로: **사망**. 심어둔 결함 x5에서 2 통과 / 1 불확정 / 2 실패(기준선 5/5). 태스크별 haiku는 10개 결함 중 0개를 올바른 심각도로 지적, 9개는 놓치거나 합리화(DRY 위반을 YAGNI라고 칭찬, assertion 없는 테스트를 계획 준수라고 함). "싼 리뷰어는 결함을 옹호하는 방식으로 실패한다."
- L4 상주 컨텍스트 다이어트: `task-brief --list`, 보고서 15줄에서 8줄, SKILL.md 축소(Codex는 긴 세션에서 약 10k자 x 약 500회 재읽기).
- L5 메인테이너 거부 항목: 좁힌 재리뷰(2026-06-09 거부, 최대 약 $0.50/run), 디스패치 배칭.
- 예산: 전체 사다리 $150 이하. 기대 최종: 모든 단계 생존 시 $5~7/run, 판단 민감 단계가 예상대로 죽으면 $8~10/run이 "정직한 목표".

**관찰** [추론]: 비용 실험을 사전 등록하고 실패 기준을 먼저 정한 뒤 "예상대로 죽었다"고 기록하는 방식이다. 싼 모델로 리뷰를 대체하면 결함을 놓치는 수준이 아니라 결함을 적극적으로 정당화한다는 관찰은 다른 멀티 에이전트 설계에도 옮길 만한 증거다.

## 3. SDD 수정 루프 재설계 (2026-07-15) [메인테이너]

출처: `2026-07-15-sdd-fix-loop-redesign-design.md` (상태: Jesse와 브레인스토밍 후 승인된 설계, 구현 계획은 후속)

**실제 세션에서 관찰된 문제 4개**
1. 병적인 리뷰 루프: 루프가 글자 그대로 "승인될 때까지 반복"이고 횟수 상한이 없었다. 재리뷰가 매번 전체 diff를 새로 리뷰하므로, 비결정적인 리뷰어가 수정 확인 대신 매 라운드 새 finding을 꺼낸다. "circuit breaker 없음"이라고 명시.
2. "누가 고치나"에 대해 한 스킬 안에 답이 3개(전용 fix 서브에이전트, 같은 구현자, 재참여 가정).
3. 최상위 섹션 13개, 한 활동의 지침이 4곳에 흩어짐.
4. Red Flags가 17개 "Never" 목록.

**폭주 차단 설계**
- 원래 구현자를 resume해서 자기 finding을 고치게 한다(라운드 1~3). resume 불가 환경에서는 brief, 보고서 파일, finding을 들고 새로 디스패치하며 "보고서 파일이 어느 쪽이든 영속 메모리".
- 라운드 4~5는 더 강한 모델의 새 구현자에게 "이전 구현자가 N번 시도했다, 이제 네가 태스크 주인"이라는 틀로 넘긴다.
- **circuit breaker: 수정 5라운드**(resume 3회 + 강한 모델 새 디스패치 2회). "Jesse's call"이라고 명시. 근거는 "resume 3회를 버틴 루프는 대개 구현자가 자기 문제를 못 보는 것".
- 재리뷰는 finding 범위로 좁힌다(`review-package FIX_BASE HEAD`). 수정이 건드리지 않은 코드의 새 finding은 비차단으로 장부에 넣고 최종 리뷰로 넘김. 이는 strict-cost 문서에서 L5로 "2026-06-09 거부"됐던 "좁힌 재리뷰"를 한 달 뒤 채택한 것 [추론: 두 문서 날짜와 내용 대조로 판단].
- 조기 종료 금지: 상한 전에는 컨트롤러가 finding을 판정하지 않는다. 예외는 계획 텍스트와 충돌하는 finding으로, 즉시 사람에게 간다.
- 상한 도달 후 컨트롤러 판정 3갈래: 이의 있음/틀림은 한 줄 판정과 함께 장부에 기록 후 진행, 실제지만 하중 없음은 known-open으로 기록 후 진행, 실제이고 하중 있음(후속 태스크가 의존하거나 계획 결함)은 기존 BLOCKED 정지. "조용한 폐기는 계속 금지", 모든 판정은 장부 항목.
- 수정 보고서 완결성 게이트: 재리뷰 전에 보고서가 커버하는 테스트, 실행 명령, 출력을 명시했는지 확인.
- 최종 리뷰도 한 번의 fixer, 한 번의 좁힌 재리뷰, 그 뒤 컨트롤러 판정으로 경계를 둠.
- 불변식: "eval로 튜닝된 문장은 옮기되 고쳐 쓰지 않는다." 이동 맵으로 누락이나 재작문을 검증.

**새 drill eval 3개**: resume 하고 재디스패치 안 하기, breaker 작동(절대 만족 안 하는 리뷰어를 심음, 5라운드 후 정지), 구조적 finding이면 BLOCKED로 정지.

**합리화 표 예시** (문서 원문 초안 행): "One more round will converge" 대 "Past the cap, rounds don't converge. Adjudicate." / "The fix was small, skip the re-review" 대 "Unreviewed fixes are how regressions land."

## 6. 브레인스토밍 visual companion 보안 강화 (2026-06-10, 06-11) [메인테이너, 외부 기여자 Drew 리뷰]

출처: `2026-06-10-visual-companion-auth-hardening-design.md`, `2026-06-11-visual-companion-final-hardening-fixup-design.md` (둘 다 상태 "Draft for Drew review", PR #1720 대상)

visual companion은 브레인스토밍 중 에이전트가 만든 HTML 화면을 브라우저로 보여주고, 사용자의 클릭을 `state/events`로 에이전트에게 돌려주는 로컬 서버다. 즉 사용자 피드백 채널이면서 로컬 파일을 서빙한다.

**위협 모델**
- 보호 자산: 화면 내용, 세션 키, `state/events`(에이전트가 사용자 피드백으로 읽음), 세션 디렉터리 아래 로컬 파일.
- 범위 안 공격자: 다른 localhost 포트의 악성 탭, 서버가 loopback 아닌 인터페이스에 바인딩됐을 때의 원격 클라이언트, URL 기록이나 referrer, 커밋된 로컬 상태로 인한 유출, symlink나 경로 트릭으로 `/files/*` 탈출.
- 범위 밖(의도적): 에이전트가 쓴 악성 화면 HTML, 악성 same-origin 번들 JS. 막으려면 sandboxed iframe 구조가 필요하다고 보고 연기.

**PR 브랜치에서 실제로 발견된 실패 (1차 문서)**
1. 다른 origin의 localhost 페이지가 쿠키 인증 WebSocket을 열어 공격자가 고른 선택을 `state/events`에 쓸 수 있었다. [추론: 에이전트가 이를 사용자 피드백으로 읽으므로 프롬프트 주입 경로가 된다.]
2. `/files/*`가 `content/` 밖을 가리키는 symlink를 서빙했다. 키가 담긴 URL이 있는 `state/server-info`로 가는 symlink 포함.
3. 세션 키가 화면 URL에 남아 기록과 referrer에 노출.
4. 재시작 후 쿠키 없는 재연결이 헤드 있는 Chrome에서 실패.

**수정**: 키가 붙은 첫 로드는 부트스트랩 페이지로 바꿔 키를 탭 범위 저장소에 옮기고 주소를 `/`로 교체, WebSocket 업그레이드에 인증과 함께 Origin이 Host와 같은지 검사, `/files/*`는 realpath로 content 디렉터리 안 일반 파일만 허용, referrer 없음 / 캐시 저장 안 함 / 프레임 금지 등 유출 감소 헤더(단 인라인 스크립트 때문에 script-src 제한은 이번에 안 넣음), `.superpowers/`를 gitignore에 추가. 모두 TDD로 실패 테스트 먼저.

**2차 fixup에서 최종 리뷰가 추가로 찾은 5건**
1. 루트 `GET /` 화면 선택 경로는 여전히 content 밖을 가리키는 symlink나 hardlink를 서빙할 수 있었다. 수정: 같은 containment 적용, 링크 수가 1이 아닌 파일 거부.
2. 선호 포트가 점유되면 fallback 서버가 저장된 `.last-token`을 재사용해 같은 bearer 키를 가진 서버 두 개가 뜰 수 있었다. 수정: fallback이면 새 토큰 생성, 환경변수로 명시한 토큰이 있으면 fallback 대신 실패로 닫음.
3. `stop-server.sh`가 소유권 증거가 약할 때 무관한 `node server.cjs` 프로세스에 시그널을 보낼 수 있었다. 수정: 시작마다 인스턴스 id를 argv에 넣고, 정확한 argv 토큰 일치일 때만 종료. 증거가 없으면 실패로 닫음. "무관한 프로세스를 죽이느니 오래된 프로세스를 남겨두는 쪽을 의도적으로 선호."
4. 테스트가 엉뚱한 fallback 프로세스를 상대로 통과하거나, 실패 시 백그라운드 프로세스를 흘림.
5. PR에 이전 evals 서브모듈 bump가 섞여 충돌. PR 본문이 외부에서 돌린 eval 증거를 정확히(커밋, 경로, 명령, 결과) 적고 서브모듈 bump가 포함된 것처럼 암시하지 말 것을 요구.

**검증**: macOS와 Windows(Git Bash 호스트 `ballmer`) 양쪽 검증 기록, 브라우저 수동 테스트는 자동 테스트 통과 후에만.

**관찰** [추론]: 1차 강화 후에도 최종 리뷰에서 같은 계열(경로 탈출) 구멍이 다른 라우트에 남아 있었다. 공격 표면이 "사용자 피드백 채널"이라 에이전트 판단 오염과 직결되는 점이 이 플러그인 보안에서 가장 중요한 지점으로 보인다.

**v6.4.1**

- 계획 핸드오프가 SDD와 Native 두 방식의 비용을 설명하고 하나를 추천.
- 저장된 계획을 사용자가 검토하기 전에는 아무것도 실행하지 않음. "아이디어나 범위 승인을 보지 못한 계획의 승인으로 치지 않는다." 계기는 "그 범위 괜찮아"를 scaffold 허가로 받아들인 세션.

- TDD: 태스크가 테스트 파일 하나를 지정하면 세션이 **12회 probe 중 11회** 그 파일만 돌려 옆의 깨진 테스트를 못 봤다. 이제 프로젝트 전체 테스트 명령을 돌리고 자기가 만들지 않은 실패도 이름으로 보고.

## 14. 네 관점 종합 [추론 포함, 근거 절 표시]

**(1) 검증과 위험 통제**
- 핵심 장치는 전부 스킬 텍스트와 보조 스크립트다. 도구 호출을 막는 훅은 없다(10절). 그래서 메인테이너는 "프롬프트 지침이 세션 중에 무너진다"를 측정한 뒤 구조로 옮기는 방향을 반복했다: 모델 줄 필수, diff를 파일로, 계획별 장부와 식별 첫 줄, `review-package`가 빈 범위를 exit 3으로 거부(1, 4, 11절).
- 루프 폭주: v5.0.0 5회 상한, v5.0.4 3회, v5.0.6 루프 폐지(품질 차이 없음), SDD 태스크 루프는 v6.2.0에서 5라운드 circuit breaker와 판정 장부(3, 9절).

- 사람 승인 지점은 줄이지 않는다는 선이 반복된다: 3경로 라우터에서도 승인 유지, 저장된 계획 검토 전 실행 금지, worktree 제거 시 강제 대신 질문(5, 9, 11절). 반면 SDD 실행 중 비파괴적 계획 충돌은 9시간 정지 사례 후 컨트롤러가 기록하고 진행하도록 바뀌었다(9절).
