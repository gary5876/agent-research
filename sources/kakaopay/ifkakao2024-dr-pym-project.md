# [if(kakaoAI)2024] 카카오페이증권의 Kubernetes 지능형 리소스 최적화 (feat. Dr.Pym Project 공유)

## 핵심 한 문장
Prometheus 메트릭을 매주 분석해 서비스별 CPU/메모리 스펙, Replicas, 시간대별 스케일 스케줄을 "추천"하고, 서비스 담당자가 배포 신청 화면에서 한 번의 클릭으로 적용 요청하면 RE 담당자가 승인 후 배포하는 구조로, 운영 CPU 54%, 메모리 32%, EKS 비용 약 21%를 줄인 사례.

## 배경과 문제
- 인프라: Wallga라는 CI/CD 플랫폼(Jenkins + ArgoCD) 위에 AWS EKS, 카카오클라우드 같은 매니지드 k8s와 IDC 온프레미스(Multi IDC) k8s 클러스터를 운영. 개발자는 Code push와 CD Job 실행 두 번으로 배포.
- CD Job(Jenkins) 파라미터 spec_type에서 리소스 스펙을 선택하면 ArgoCD가 그 스펙으로 배포.
- 세 가지 이슈:
  1. 지속적인 리소스 부족: IDC 노드 리소스 부족 반복, EKS는 오토스케일링그룹으로 비용 증가.
  2. 서비스 안정성 부족: 한 번 고른 스펙을 계속 쓰므로 트래픽 변화 대응이 수동적. OOM, 스로틀링은 지속 모니터링해야 비로소 확인.
  3. Rightsizing 고민: 현재 리소스가 적절한지, 이벤트 때 Pod를 얼마나 늘리고 줄일지 판단이 어려움.
- 목표: 비용 절감과 안정성 향상을 동시에, "스스로 학습하고 의사결정을 가이드해 주는 지능형 시스템", "사람의 개입을 최소화".

## 구조와 구성요소
- Dr.Pym(앤트맨의 핌 박사에서 따온 이름): Prometheus에서 수집 → 분석과 추천 → 사람이 적용 → Wallga(Jenkins, ArgoCD)가 리소스 최적화 반영.
- Prometheus recording rule: 2주 이상 쿼리가 느리고 부하가 커서 미리 계산.
- KEDA(Phase 2): 이벤트 기반 오토스케일러. 내부적으로 HPA 사용. CPU, Memory, Cron Scaler 사용 중.
- 로켓단: 카카오페이증권 릴리즈 플랫폼. 배포 요청 → 승인 → 배포 실행 흐름. Dr.Pym이 배포 요청 단계에 연동되어 현재값과 추천값 표시.
- Grafana 대시보드: 서비스별 시간별 CPU/Memory/요청건수/평균응답시간/replicas. 플랫폼 담당자용 "Dr.Pym - Rightsize정보" 대시보드(클러스터/네임스페이스/애플리케이션별 적용 현황, 추천값, KEDA 적용 여부).
- 추천 알림 메시지(Phase 1 그림): "[Dr.Pym 리소스 추천] Dr.Pym은 서비스 자원 사용량을 분석하여 최적의 리소스 할당값을 추천합니다." 서비스명, 현재 설정값, 추천 설정값, Grafana 링크. "@@sec.reops에게 요청시에 해당 spec으로 반영됩니다", "Dr.Pym 추천값으로 리소스 설정을 변경하기를 권장드립니다. 검토부탁드립니다."

## 절차와 규칙
Phase 1 (CPU/메모리 추천):
- CPU: quantile_over_time(0.99, ...[2w]). 대부분 서비스가 배포/기동 시 순간적으로 CPU를 많이 쓰고 평시엔 낮음. 상위 1% 이상치는 CPU Limit 제거로 해결한다고 보고 99% 분위수 선택.
- Memory: 2주 최댓값 + 마진(개발 15%, 운영 20%).
- 적용: CPU 추천값은 Request에만, Memory는 Request와 Limit을 동일하게. CPU Limit은 제거.
- 너무 잦은 추천을 막기 위해 0.25 단위 올림.

Phase 2 (KEDA):
- 목적: Phase 1로 슬림해진 서비스가 급증 트래픽을 못 견딜 위험을 막는 안전장치, Phase 3를 위한 확장성.
- CD Job의 replicas 파라미터: 기존엔 CD 입력값을 다음 default로 저장했는데, KEDA로 replicas가 가변이 되자 배포 시 옛 값으로 의도치 않은 scale-in 위험. default를 latest로 바꿔 배포 시점의 현재 replicas로 배포하도록 파이프라인 개선.
- ScaledObject 기본값(플랫폼 기준값, 서비스별 변경 가능): CPU Utilization 평균 100% 이상에서 스케일(발표 때는 150%였으나 안정성 측면에서 더 보수적인 100%로 변경), Memory 80% 이상.

Phase 3 (Replicas 추천, 핵심):
- 요구사항: 현재 Replicas가 적절한가, 한가한 시간대는 미리 줄이고 바쁜 시간대는 미리 늘리고 싶다, 트래픽 추이를 지속 확인하고 싶다.
- 추가 수집 메트릭: 시간별 요청건수, 시간별 평균응답시간, 시간별 Replicas.
- Function 1 Check Enough Pod: 최고 요청건수 시간대의 평균응답시간과 그 외 시간대를 비교, 차이가 크면 Replicas 증가 추천(예: 평시 50ms, 피크 100ms면 부족).
- Function 2 Scheduled Scaling: 정상 응답시간을 보인 최고 요청건수 시간대 기준으로 Pod당 허용가능 요청건수 계산(예: 20만 건 / 20 Pod = 1만 건). 10 Pod로 버틸 수 있는 10만 건 이하 시간대(예: 0-8시, 12-16시)를 찾아 평일/주말 스케일 스케줄 추천.
- Function 3 Check RPS Volatility: 주별 총합과 주별 순간 최대 요청건수를 비교해 변동 알림(예: 총합 1억 → 1.5억 50% 상승, 최대 20만 → 24만 20% 상승).
- 분석 주기: "수집된 Metric을 토대로 매주 분석하여 분석결과를 알려주기".

사람의 역할(승인 경계):
- 서비스 담당자: 로켓단 배포 신청 화면에서 현재값/추천값을 보고 "Dr.Pym 적용하기" 또는 "무시하기"를 선택해 적용 요청.
- RE(Release Engineer) 담당자: 로켓단의 승인 이후 배포 실행. 추천된 Rightsizing 값으로 배포.
- 추천 메시지의 "적용하기" 버튼은 "한 번의 클릭만으로 추천값을 적용". 단 추천은 자동 적용이 아니라 담당자 선택이 필요.
- 플랫폼 담당자: Grafana로 전체 Rightsizing 현황을 확인하고 follow-up.

## 수치와 결과
- 리소스 절감: 개발 환경 CPU 46%, Memory 17% 감소 / 운영 환경 CPU 54%, Memory 32% 감소.
- 비용: EKS 약 21% 절감. IDC는 실비용 감소는 아니지만 노드 기준 약 18% 여유 확보(100대 가정 시 18대).
- CPU Limit 제거 사례: As-Is limits cpu 4 / requests cpu 2, memory 8Gi → To-Be limits cpu 제거. 이후 순간 6 이상까지 사용하지만 변동성은 오히려 안정, 메모리 그래프 변동성도 감소.
- 추천 메시지 예(그림 14): 현재 2core/8.0Gi → 추천 0.5core/6.0Gi, Replicas 30 → 35 추천, 시간당 58870 요청 이하 기준 평일 1시~8시 및 주말 0시~24시 Replicas 15 추천, 지난주 대비 요청 총합 33% 이상 감소, 순간 최대 26% 이상 증가.
- 대시보드 예(그림 18): 전체 Dr.Pym 적용 72%, 미적용 28%.
- 배포 신청 화면 예(그림 17): 현재 2core/16Gi, 추천 0.25core/0.75Gi.

## 실패, 한계, 주의점
- CPU Limit 제거 부작용: WebFlux 서비스 중 CPU Request를 1로 둔 서비스에서 JVM 스레드가 평소보다 많아지고 부하 시 OOM으로 Pod가 죽음. 원인은 CPU Request가 1일 때(cgroup cpu shares 1024를 "설정 없음"으로 해석) availableProcessors가 노드 CPU 개수를 반환. 대응: Wallga 파이프라인에서 Request 1이면 1.01로 바꿔 배포, JVM 옵션 ActiveProcessorCount 지정 가능하게 개선. 결과 스레드 정상화.
- 최초 계획과 다름: CPU 사용률이 시간대별로 오르내릴 것이라 보고 CPU 기반 Replicas 추천을 계획했지만, 실제로는 배포 시점 외 CPU 편차가 크지 않고 메모리는 항상 일정. 그래서 요청건수와 평균응답시간으로 방향 전환.
- API 통신을 하지 않는 Consumer 같은 서비스는 향후 과제로 남김.
- 발표 후 CPU 스케일 임계치를 150%에서 100%로 보수적으로 변경.
- 리소스를 줄인 것 자체가 급증 트래픽 위험을 키울 수 있어 KEDA를 안전장치로 추가해야 했음.
- 앞으로의 계획: 메트릭 추가로 모든 서비스 적용, Prometheus 메트릭 기반 Scaler, AI 예측 기반 PredictKube Scaler 제공 준비.

## 우리 설계에 쓸 만한 점
- [추론] "추천은 자동, 적용은 사람 선택, 실행은 승인 후 운영 담당" 3단 구조가 운영 부서 에이전트의 자율성 경계 모델로 그대로 쓸 만하다. 에이전트는 분석하고 제안서를 만들되, 반영은 요청자 클릭과 운영 승인 게이트를 통과해야 한다.
- [추론] 추천을 기존 업무 동선(배포 신청 폼)에 끼워 넣고 "적용하기/무시하기"를 둔 것이 채택률을 만든다. 에이전트 제안도 별도 채널이 아니라 사람이 이미 거치는 승인 화면에 붙이는 것이 좋다.
- [추론] 추천 떨림 방지(0.25 단위 올림), 보수적 임계치(150%에서 100%), 환경별 마진(개발 15%, 운영 20%)처럼 운영 환경에 더 보수적인 파라미터를 기본값으로 두는 원칙.
- [추론] 최적화(자원 축소) 에이전트를 도입하면 안전장치(오토스케일, 롤백)를 함께 도입해야 한다는 점: 한 에이전트의 개선이 다른 위험을 키우는 상호작용을 점검 역할이 검토해야 한다.
- [추론] 자동화끼리 충돌(KEDA가 늘린 replicas를 CD 파라미터가 되돌림)이 있었으므로, 여러 에이전트가 같은 설정값을 건드릴 때 "현재 실측값(latest)을 기준으로 한다" 같은 소유권/우선순위 규칙이 필요하다.
- [추론] 매주 분석 리포트와 주간 변동성 알림(총합, 순간 최대 비교)은 운영 부서 모니터링 에이전트의 정기 산출물 템플릿으로 쓸 수 있다. 마케팅 이벤트 전후 트래픽 변화를 운영에 알리는 부서 간 연결고리로도 쓸 만하다.
- [추론] 적용률 대시보드(적용 72%/미적용 28%, updated_at)는 에이전트 제안의 채택률을 추적하는 피드백 지표의 예시다.
- [추론] 가설(CPU가 시간대별로 변동)이 데이터로 뒤집혀 지표를 바꾼 과정은, 운영 에이전트가 1단계 데이터 수집 결과로 2단계 설계를 수정하는 단계적 롤아웃의 근거가 된다.
