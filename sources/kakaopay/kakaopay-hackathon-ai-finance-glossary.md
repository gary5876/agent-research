# 어려운 용어가 있으신가요? '금.용.사.'가 알려드립니다!

- URL: https://tech.kakaopay.com/post/kakaopay-hackathon-ai-finance-glossary/
- 게시일: 2025-06-24 (페이지에 2026. 9. 1 날짜도 함께 표시됨, 수정일로 보임)
- 저자: bambi.kwon(보험 서비스 PM), dong.gri(보험 프론트), katfun.joy(서버 개발), noah.you(보험 백엔드)
- 태그: 카페톤, AWS, Bedrock, AI
- 소속: 카카오페이 인슈어런스클랜(보험). 팀명 "아 팀이름 안정했따"(슬라이드에 #13)
- 리뷰어: ellie.sys

## 핵심 한 문장
화면 문단 텍스트를 통째로 보내면 AI가 어려운 용어를 골라 설명하는 서비스로, 기능을 simple(20자 툴팁), detail(상세 설명), products(연관 보험 상품) 3개의 Lambda와 3개의 Bedrock Agent로 기능별로 나누고, 에이전트 명령을 단순화(용어 1개씩 병렬 호출)하고 DynamoDB 캐시로 30초 지연을 0.5초 미만으로 줄임.

## 배경과 문제
- 팀원 모두 보험 도메인 크루. 처음 보험을 접했을 때 느낀 용어의 어려움이 사용자에게도 해석이 필요할 것이라고 봄.
- 아이디어 선정 기준 3가지: 잘 아는 보험 도메인, 사용자의 서비스 이용에 도움, 실현 가능성.
- 카페톤은 사전 자료 및 기술 조사는 허용, 구현은 당일. 네 명 모두 AWS AI 서비스를 처음 접함.
- 용어 설명에서 끝내지 않고 관련 금융 상품 추천으로 사업 모델까지 연결. 보험 중심 구현이지만 대출, 카드, 투자로 확장 가능하게 설계.
- 사용자 진입 경로는 카카오톡 알림톡 등을 가정.

## 구조와 구성요소
- 아키텍처(그림 09): AWS Amplify(User) <- Amazon API Gateway <- AWS Lambda <- Amazon Bedrock Agents -> Amazon Bedrock Knowledge Base(보험 상품 목록, 보험 용어 및 약관, 질병 용어). Knowledge Base 원천은 AWS S3(외부 데이터: 금융 용어, 약관 PDF)와 웹 금융 용어 사전 crawling. Amazon DynamoDB가 Lambda에 붙어 "응답 일부 캐싱 역할".
- 배포: 서비스 앞단은 CodeDeploy(본문).
- Lambda 3개: simple, detail, products(서비스 기획 단위로 분리). 각 Lambda가 필요에 따라 Bedrock Agent 호출.
- Agent 3개: 간단 소개(simple), 자세한 소개(detail), 연관 상품 추천(products). 에이전트 간 협업이나 Supervisor는 원문에 없음. 기능별 독립 에이전트.
- 모델: Claude 3.5 Sonnet v2(그림 12 에이전트 빌더 화면 기준. 본문에는 모델명 없음).
- 에이전트별 출력 형태: simple은 {용어: 설명} key-value JSON, detail은 2~3문장 설명 후 요점 불릿, products는 표(HTML).
- Knowledge Base 4개(목적별 분리): 보험 용어(정적 자료만), 보험 용어(정적+동적 자료), 질병 용어(정적+동적 자료), 가상 보험 상품 자료(정적 자료). 분리 이유는 RAG 정보 수가 많을수록 검색이 오래 걸리는 경향.
- 캐시: DynamoDB에 '용어(Key)-설명(Value)' 저장, TTL로 만료 후 재생성.
- FE: 설명 영역을 컴포넌트로 감싸 자식 텍스트를 모두 추출해 API로 전달(CMS "페이어텐션" 텍스트도 고려). 응답을 전역 상태 저장소(Zustand, Jotai 등)에 저장하고 텍스트 인덱싱으로 해당 단어를 span으로 치환, 하이라이팅과 클릭 핸들러.

## 절차와 규칙
- 사용자 흐름: "용어설명" 토글 ON -> AI가 어려운 용어를 인식해 하이라이팅 -> 클릭 시 20자 이내 툴팁 -> 툴팁 클릭 시 상세 설명 페이지(상세 설명 + 연관 상품 추천 동시 호출).
- 어려운 용어 판단 기준: 보험 용어는 외래어, 영어보다 한자 기반 단어와 질병명 같은 의료 전문 용어가 대부분이라는 조사 결과에 따라, (1) 한자어 기반 전문 용어 (2) 질병명 등 의료 관련 용어만 해설 대상으로 선별하는 Agent를 구성.
- simple agent 지침(그림 12): 최대 20자(띄어쓰기 포함) 이내, 어려운 한자어나 영어 최소화, 20대도 이해할 표현. "입력된 단어는 어떤 경우에도 변형하지 말고 원본 그대로 JSON의 키로 사용"을 두 번 반복 강조. 순수 한글 단어(고유어)는 선택하지 말고 한자어나 영어 단어만 선택. 단어는 | 기호로 구분.
- 에이전트 기능 최소화: 처음엔 용어 목록을 한 번에 넘겼으나 용어 수가 많아질수록 응답 내용과 형태가 기대에서 벗어남 -> 용어 1개만 처리하도록 바꾸고 클라이언트에서 병렬 요청.
- 프롬프트 구조화: '역할', '응답 조건', '출력 형식'을 `<Base>`, `<Condition>`, `<Result>` 태그로 분리. products 예시 조건: [보험사명]: [보험상품명] - [보장명] [보장금액] 형식, 보장금액 큰 순 정렬, 같은 보험사 상품 2개 이상 금지, 다른 보험사 상품 더 있는지 꼭 확인, 타이틀은 "소액암을 보장하는 상품"처럼 용어 포함, HTML 응답, 타이틀 h2, 4열 표.
- 비용 최적화: 같은 화면에서 이미 번역된 용어는 API 요청에 함께 보내 무시하게 함.
- 캐시 운영: 첫 요청만 AI 호출, 이후 DynamoDB 조회. TTL 만료 후 AI가 새 설명 생성(최신 정보, 다양한 관점).
- 구상만 한 것: AWS Batch나 CloudWatch + Lambda로 비동기 선제 캐시 구축(첫 방문 지연 제거), 운영자가 원할 때(업그레이드된 Agent 적용) 또는 새벽 시간 갱신으로 용어 설명 검토 및 갱신 자동화.

## 수치와 결과
- API 응답 시간 30초 이상(시연 중 발견) -> 캐시 적중 시 0.5초 미만.
- 툴팁 설명 최대 20자.
- detail 설명 2~3문장.
- Agent 3개, Lambda 3개, Knowledge Base 4개, 팀원 4명.
- 정확도 등 품질 평가 수치는 원문에 없음.

## 실패, 한계, 주의점
- 테스트 결과 "한 번에 마법처럼 잘 되지는 않았습니다": 정의한 글자 수 초과, 지정한 말투와 다른 문구로 응답.
- 에이전트는 명령이 복잡할수록 기대대로 응답하지 못하는 경향. 여러 용어를 한 번에 처리시키면 내용과 형태가 벗어남.
- 첫 방문 시 지연은 남은 이슈(비동기 선제 캐시는 미구현).
- 캐시는 TTL 만료 시에만 갱신되는 구조.
- 교훈: 기술적 제약과 현실적인 사용자 경험 사이의 균형점을 찾는 게 중요.

## 그림 설명
- 01: 발표 슬라이드 "금융 서비스는 쉬운데, 용어는 왜 이렇게 어려울까요?"(장식성).
- 02, 03: 아이디어 소개와 시연 영상 화면으로 보임(장식성, 상세 확인 생략).
- 04, 05: 용어설명 OFF/ON 비교. 05는 "암, 뇌, 심장 3대 질환 위험" 화면에서 소액암진단, 뇌혈관질환 등이 노란 하이라이트, "소액암진단"에 "작은 암으로 진단받았을 때 받는 보험금 >" 툴팁, 우하단 "용어설명" 토글.
- 06, 07: 상세 설명 및 연관 상품 추천 화면, AI가 생성한 용어 설명.
- 08: "소액암을 보장하는 상품" 표(보험사, 보험상품, 보장명, 보장금액), 가상 보험사 데이터와 소액암 범위, 면책기간 주석.
- 09 전체 아키텍처: 위 "구조와 구성요소"에 기술.
- 10, 11: 기존 카카오페이 화면(내 보험 상세 보험용어 설명 영역, 신용관리 용어 설명 영역). 어려운 용어가 별도 설명 문단에 모인다는 근거.
- 12: Amazon Bedrock 에이전트 빌더 화면. 에이전트 이름 agent-simple, 설명 "보험 용어를 간단하게 설명하기 위한 에이전트", 모델 Claude 3.5 Sonnet v2, 에이전트 지침 전문, 우측 테스트 창에서 "전이암" 입력에 "암이 다른 장기로 퍼져서 새로 생긴 암" 응답.
- 13: 마무리 슬라이드 "금.용.사와 함께라면 금융이 쉬워집니다"(장식성).

## 원문 인용
1. "Lambda는 앞서 소개한 서비스 기획에 맞춰 simple, detail, products로 나뉘어 있습니다."
2. "저희는 금융 용어에 대한 간단 소개, 자세한 소개, 연관 상품 추천을 담당하는 3개의 agent를 구성하였습니다."
3. "Agent는 주어진 키워드에 대해 저마다 정해진 방식으로 응답을 생성했는데, 정해진 방식은 프롬프트 작성을 통해 정의하였습니다."
4. "RAG를 구성하는 정보의 수가 많을수록 응답에 사용할 정보를 찾는 데 시간이 오래 걸리는 경향이 있어, 용도에 따라 구분해서 사용하도록 하였습니다."
5. "보험 용어는 외래어나 영어 표현보다는 한자 기반의 단어나 질병명과 같은 의료 전문 용어가 대부분을 차지한다는 특징을 발견했습니다."
6. "이후의 반복적인 접근에서는 성능(기존 30초 -> 0.5초 미만)이 훨씬 나아졌습니다."
7. "운영자가 원할 때(업그레이드된 Agent 적용) 혹은 서비스 사용이 적은 새벽 시간에 업데이트를 진행하여 최신 정보를 유지하고 용어 설명 품질을 지속적으로 향상하고자 했습니다."
8. "정의한 글자 수를 초과해서 응답을 하거나, 지정했던 말투와 다른 문구로 응답하기도 했습니다."
9. "Agent는 명령한 대로 응답을 잘 만들어 주기는 하지만, 명령이 원하는 바가 복잡할수록 기대한 대로 응답하지 못하는 경향이 있습니다."
10. "명령을 조금 단순화하고자, 용어를 한 개만 처리하는 방식으로 agent를 변경했습니다."
11. "AI가 기대한 대로 답을 못 할수록 아쉬운 건 사람이니, 요청을 최대한 구체적으로 해야 합니다."
12. "저희는 '역할', '응답 조건', '출력 형식' 세 가지를 정의하고, 이를 잘 구조화하여 응답에 사용했습니다."
13. "내용이 뒤섞이지 않도록 구분한 내용을 tag 형식으로 감싸고, 각 tag에서 기대하는 역할을 작성했습니다."

## 우리 설계에 쓸 만한 점
- [추론] "에이전트 하나에 일 하나"를 넘어 "호출 하나에 항목 하나"까지 쪼개고 병렬로 돌린 사례는, 부서 에이전트에 대량 항목을 넘길 때 배치보다 단건 병렬이 안정적일 수 있다는 근거가 된다.
- [추론] 프롬프트를 역할(Base), 조건(Condition), 출력(Result) 태그로 나누는 형식은 모든 부서 에이전트 지침의 공통 템플릿으로 삼을 만하다.
- [추론] "입력 키를 절대 변형하지 말라"를 반복 명시한 것은, 에이전트 출력이 다음 단계 코드의 키로 쓰일 때 필요한 규칙이다.
- [추론] Knowledge Base를 목적별로 쪼갠 이유(검색 속도)는 부서별 지식베이스 분리의 근거로 쓸 수 있다.
- [추론] 결과가 입력에 대해 결정적인 작업(용어 설명 같은)은 key-value 캐시와 TTL, 운영자 수동 갱신 트리거를 두면 지연과 비용을 크게 줄일 수 있다. 운영 부서 에이전트의 반복 질의에 적용 가능하다.
- [추론] "어려운 용어" 판단 기준을 먼저 도메인 조사로 정하고 그 기준을 에이전트 지침에 넣은 방식은, 라우팅이나 필터링 기준을 사람이 먼저 정의해야 한다는 교훈으로 읽을 수 있다.
- [추론] 이 글의 3개 에이전트는 서로 호출하지 않는 기능별 에이전트이므로, 오케스트레이션 사례가 아니라 에이전트 분할 단위 사례로 참고해야 한다.
