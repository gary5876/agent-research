# 카카오페이 배포 효율화 1년 회고: 자동화 도입과 팀 생산성 향상

- URL: https://tech.kakaopay.com/post/slack-bot-improving-operational-efficiency-2/
- 게시일: 2024-07-17 (페이지 표기상 수정일 2025-09-17)
- 저자: ari.a (아리)
- 태그: SRE, 슬랙봇, 배포, 자동화, 회고
- 소속: 카카오페이 SRE팀 RE파트 (대고객서비스 배포 담당 조직)

## 핵심 한 문장
배포 준비와 커뮤니케이션을 슬랙봇으로 자동화한 지 1년 뒤, 상시 배포 인원은 10명에서 3명으로 줄고 배포 전담 어시스턴트를 둘 수 있게 되었지만, 그라운드 룰 혼란, 직접 배포하지 않게 된 팀원의 개선 의지 약화, 개선 전 데이터 미수집이라는 문제가 남았다.

## 배경과 문제
- 이전 글(2023-06) 요약(원문 코드 블록): 수동 작업이 많아 실수 가능, 상태 변경 알림이 없어 계속 확인해야 함(긴장 상태 유지) → 배포 작업 할당 자동화, 슬랙봇으로 할당/진행/완료 상태 변경 알림.
- 이번 글의 목적: 개선 이후 1년 동안의 긍정적 변화와 아쉬운 점, 새로 마주한 문제를 공유.

## 구조와 구성요소
- 슬랙봇: 배포 담당자 할당, 상태 변경 알림(이전 글 기능 그대로).
- 어시스턴트 크루: 카카오페이에서 주로 단순/반복 운영업무 담당. RE파트 어시스턴트는 정규 업무 시간(10:00 ~ 19:00) 동안 배포를 담당. 근무 기간 1개월에서 6개월.
- 배포 데이터 수집과 대시보드: Jenkins, Spinnaker 등 배포 시스템에서 이벤트(스테이지 또는 상태 변경 등)가 발생할 때마다 데이터를 수집하고 대시보드 구성. 추적 지표 예시로 배포 소요 시간, 실패율, 롤백 빈도.
- 여유 시간으로 진행한 프로젝트: 배포 모니터링 시스템 개선, 파이프라인 구성, Integration test 지원을 위한 Mocking Platform 구축, QA팀과 협업한 테스트 자동화.

## 절차와 규칙
- 슬랙봇이 담당자를 할당하므로 새 배포 요청에 계속 주의를 기울일 필요가 없어짐.
- 리소스 문제로 일부 서비스 배포를 각 서비스 조직 내부에 RE파트를 발령 내어 진행하던 것을, 여유가 생긴 뒤 SRE팀 RE파트로 가져와 진행. 배포 환경이 동일하게 구성되어 일관된 배포가 가능해짐.
- 어시스턴트 도입 시 그라운드 룰 수립(구체 규칙 내용은 원문에 없음). 운영 중 예상치 못한 상황으로 계속 수정.
- 개선 의지 약화 대응:
  - 정기적인 배포 프로세스 리뷰: 어시스턴트 크루와 팀원이 함께 참여하는 회고, 스프린트 단위 2주 간격.
  - 데이터 기반 개선 필요성 공유: 배포 소요 시간, 실패율, 롤백 빈도 추적 및 대시보드 공유.
- 슬랙봇 도입 이후 개발자 경험은 설문조사로 수집(정성 데이터).

## 수치와 결과
- 상시 배포 인원: 10명(2022년) → 3명(2023년).
- 월평균 배포 지원 건: 약 1,000건(2022) → 약 1,500건(2023), 50% 증가.
- 월 최대 배포 지원 건: 1,436건(2022) → 1,830건(2023), 27.5% 증가.
- 어시스턴트 근무 시간 10:00 ~ 19:00, 근무 기간 1~6개월, 회고 주기 2주.
- 배포 소요 시간, 실패율의 개선 전후 수치는 없음(개선 전 데이터 미수집).

## 실패, 한계, 주의점
- 흔들리는 그라운드 룰: 어시스턴트 제도 운영 중 예상치 못한 상황이 생겨 규칙을 계속 수정, 어시스턴트와 팀원이 혼란.
- 개선 의지 약화: 직접 배포하지 않게 되면서 불편함에 둔감해짐. 회고와 데이터 대시보드로 보완.
- 개선 전 데이터 미수집: 효과를 정량 분석하기 어려웠고 설문으로 정성 데이터만 확보. 교훈으로 사전에 데이터 수집 계획과 정량 평가 지표를 먼저 설정하겠다고 함.
- 긍정 측면: 어시스턴트의 입퇴사로 "새롭고 신선한 시선"이 들어와, 처음 온 사람들의 잦은 질문을 통해 프로세스 중 직관적이지 않고 경험에 의존하는 부분을 발견하고 개선.

## 그림 설명
- 그림 1: 카카오 캐릭터가 서류 더미 앞에서 땀 흘리는 삽화. 장식용.
- 그림 2: 막대그래프 "상시 배포 인원" 2022년 10, 2023년 3.
- 그림 3: 막대그래프 "월 평균 배포 지원 건" 2022년 1,000, 2023년 1,500.
- 그림 4: 막대그래프 "월 최대 배포 지원 건" 2022년 1,436, 2023년 1,830.

## 원문 인용
1. "기존의 수동 작업과 알림 부재 문제를 자동화하여 상시 배포 인원을 10명에서 3명으로 줄이고, 다양한 프로젝트를 성공적으로 수행했습니다."
2. "슬랙봇이 배포 담당자를 할당하기 때문에, 새로운 배포 요청에 지속적으로 주의를 기울일 필요가 없게 되었습니다."
3. "그에 따라 1인 당 처리할 수 있는 배포 모듈의 개수가 늘어났고, 상시 배포 인원을 10명에서 3명으로 줄일 수 있었습니다."
4. "RE파트의 어시스턴트 크루는 정규 업무 시간(10:00 ~ 19:00) 동안 배포를 담당합니다."
5. "이 덕분에 운영 배포 프로세스에 직관적이지 않고 경험에 의존하는 부분이 있다는 점을 인지하고 개선할 수 있었습니다."
6. "이는 서비스들의 배포 환경이 동일하게 구성됨으로써, 배포 환경에 따른 차이를 최소화하고 일관적으로 배포를 진행하게 되었다는 점에서 의의가 있습니다."
7. "어시스턴트 제도를 도입하면서 그라운드 룰을 세우긴 했지만, 실제 운영 과정에서 예상치 못한 상황들이 발생하면서 규칙을 계속 수정해야 했습니다."
8. "직접 배포를 진행하지 않게 되면서, 배포 프로세스 개선에 대한 의지가 약해지고 불편함에 둔감해지는 경향이 나타났습니다."
9. "저희는 Jenkins, Spinnaker 등 카카오페이에서 배포에 사용하는 시스템에서 이벤트( 스테이지 또는 상태 변경 등 )가 발생할 때마다 데이터를 수집하고, 대시보드를 구성했는데요."
10. "하지만 저희는 개선 전 데이터를 충분히 수집하지 못했고, 개선의 효과를 정량적으로 분석하는 데 어려움을 겪었습니다."
11. "개선작업을 진행할 때는 사전에 충분한 데이터 수집 계획을 세우고, 정량적인 평가 지표를 설정하여 개선의 효과를 객관적으로 측정하려고 합니다."

## 우리 설계에 쓸 만한 점
- [추론] 자동화를 도입하기 전에 베이스라인 지표(소요 시간, 실패율, 롤백 빈도)를 먼저 기록하는 "측정 먼저" 단계를 운영 부서 첫 작업으로 둘 것. 이 글의 가장 큰 후회가 그것이다.
- [추론] 파이프라인 도구의 모든 이벤트(스테이지, 상태 변경)를 수집해 대시보드로 만드는 방식은 운영 부서 모니터링 에이전트의 기본 입력으로 쓸 수 있다.
- [추론] 반복 실행(배포 수행)은 전담 실행자(어시스턴트, 우리 경우 실행 에이전트)에게 넘기고, 설계자(팀원)는 개선 프로젝트에 집중하는 역할 분리가 효과를 냈다. 다만 실행에서 멀어진 설계자가 불편함에 둔감해지므로, 실행 로그와 마찰 신호를 설계자 쪽으로 되돌려주는 피드백 루프가 필요하다.
- [추론] 2주 주기 정기 회고를 운영 부서의 점검(inspection) 루틴으로 고정하고, 회고 입력은 사람 감상이 아니라 대시보드 지표로 삼을 것.
- [추론] 새로 들어온 실행자의 "헷갈리는 질문"이 암묵지 발견 신호였다. 에이전트가 판단 불가로 멈추거나 질문한 지점을 로그로 모으면 규칙(그라운드 룰) 보강 후보가 된다.
- [추론] 그라운드 룰이 계속 바뀌어 혼란이 생겼으므로, 에이전트용 운영 규칙은 버전 관리하고 변경 이력을 공지하는 절차가 필요하다.
- [추론] 흩어져 있던 배포를 한 부서로 모아 환경을 통일한 효과가 언급되므로, 운영 부서가 배포 경로를 단일화해 소유하는 편이 일관성에 유리하다.
