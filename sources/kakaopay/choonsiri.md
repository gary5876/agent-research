# 페이증권의 업무도우미 AI봇을 소개합니다! 근데 이제 춘식이를 곁들인

- URL: https://tech.kakaopay.com/post/choonsiri/
- 게시일: 2025-01-24
- 저자: terra.bite (카카오페이증권 DevOps팀 "테라")
- 태그: 카카오페이증권, AI, 슬랙봇, DevOps, AWS
- 소속: 카카오페이증권

## 핵심 한 문장
AI 개발 경험이 없던 DevOps팀이 Amazon Bedrock(Claude 3 Haiku, Titan 임베딩)과 PGVector로 Confluence 기반 RAG 봇 "춘시리"를 만들어 슬랙(위키질문/학습/일반질문/요약), 아지트(1차 문의 응대), 깃헙(PR 리뷰), 주간보고 자동화에 붙이고, 보안팀과 가드레일, exclude 레이블, 민감정보 감지 알림으로 통제했다.

## 배경과 문제
- 카카오페이증권의 산재된 내부 정보를 RAG로 LLM을 통해 쉽게 조회하려는 목적. 이름 'siri'에서 춘식이를 곁들여 '춘시리'.
- 보안상 ChatGPT 등 외부 AI 도구를 사내에서 쓸 수 없어서 그 대체도 원함.
- 위키 검색만으로는 필요한 문서 찾기가 어려움. 예: "VDI" 검색 시 623개 결과, 사용자용/어드민용 문서가 섞여 있음. 신규 입사자일수록 오래 걸림.
- 팀은 "그전까지 AI를 활용한 개발 경험이 없"었고 LLM, RAG, Embedding을 처음 공부하며 시작. 데이터 사이언티스트가 아니므로 외부 상용 LLM을 써야 함.

초기 목표:
- AI 봇에게 내부 문서(Confluence)를 학습시킨다.
- 학습된 내부 정보를 바탕으로 질문에 답한다.
- 필요하면 내부 정보가 아닌 일반 LLM 답변도 제공한다(ChatGPT 대체).
추가 목표: 수동으로 추가 정보 학습, 깃헙 PR 코드 리뷰, 지라 티켓 분석/요약으로 주간 리포트와 장애 리포트 자동 작성.

## 구조와 구성요소
모델과 인프라:
- LLM: Amazon Bedrock의 Anthropic Claude (코드상 `anthropic.claude-3-haiku-20240307-v1:0`). 작성 시점(2025.01.24) 서울 리전 베드락에서 유일하게 쓸 수 있던 모델 시리즈.
- 임베딩: Amazon Titan (`amazon.titan-embed-text-v2:0`). 서울 리전 베드락에서 유일하게 지원되던 임베딩 모델.
- 벡터 DB: PGVector (PostgreSQL 확장). "가장 접근성이 좋은" 선택, 쉽고 빠른 구축에 적합.
- 베드락 선택 이유: 이미 AWS 사용, 모델 직접 호스팅 불필요, AWS 비용으로 같이 청구되어 별도 빌링 프로세스 불필요, 입력 프롬프트와 답변을 저장/기록하지 않아 보안상 문제 없음.
- 모든 컴포넌트는 연구개발망에 위치.
- 언어: Python, AWS SDK boto3.

아키텍처 두 파트:
- 전처리 파트 (cronJob, 1시간마다):
  1. Confluence(위키)에서 데이터 쿼리, 텍스트 추출, 청크 생성
  2. S3에 백업된 데이터와 비교해 업데이트된 부분만 추출
  3. 베드락으로 임베딩 후 벡터 DB 업데이트
  4. 업데이트된 부분을 S3에 백업(최신화)
- 서비스 파트 (서비스 Pod):
  1. 슬랙, 아지트, 깃헙(Github Enterprise)에서 요청 수신
  2. (optional) RAG이 필요하면 요청을 임베딩 후 벡터 DB 유사도 검색
  3. 검색 결과(optional)와 질문을 합쳐 베드락 LLM에 질의
  4. LLM 답변을 요청자에게 전달

채널별 기능:
- 슬랙춘시리(업무 도우미): 위키질문(`위키/`), 학습하기(`학습/`), 일반질문(커맨드 없음, 기본값), 요약하기(`요약/`, 원격 요약은 스레드 링크 첨부).
- 아지트춘시리(세미 데브옵스 엔지니어): DevOps팀 문의에 위키 기반 1차 답변.
- 깃헙춘시리(PR 리뷰봇): PR diff 전체를 프롬프트에 넣어 파일별, 라인별 변경 요약과 의견 작성.
- 주간보고 자동화: 지라 티켓을 크루별로 슬랙에서 정리하면 요약 자동 생성, 팀 전체 요약 후 리더가 버튼으로 아지트에 포스팅.

호출 API 선택:
- `invoke_model`: 모델 공급사별 요청 형식이 다름(Claude는 anthropic_version/messages, Titan은 inputText/textGenerationConfig).
- `converse`(2024년 5월 출시): invoke_model을 한 단계 추상화, model_id만 바꾸면 동일 코드. 인터페이스가 일관되어 모델 변경에 용이해 채택.
- RAG 경로는 LangChain `ChatBedrockConverse` + `BedrockEmbeddings` + `PGVector`(collection_name "vector_store", use_jsonb True) + PromptTemplate(`<context>`, `<question>` 태그) + `RunnablePassthrough` + `StrOutputParser`. 실제로는 history 태그로 스레드 내 질의응답 내역도 포함.
- 분기: RAG이 필요한 내부 문서 질문(슬랙 위키질문, 아지트)은 ChatBedrockConverse, 그 외 LLM 기능은 converse.
- 예제 파라미터: temperature 0.5, max_tokens 512(converse 예시), 2048(RAG 예시), topP 0.9.

보안 구성:
- Bedrock Guardrails: 보안팀이 직접 가드레일 버전을 관리하고, 춘시리는 반드시 가드레일을 통해 베드락을 호출.
- exclude 레이블: 예외 처리할 문서에 'exclude' 레이블을 걸면 전처리에서 제외.
- 보안춘시리 모듈: 검색된 문서에 민감정보/개인정보가 있으면 보안팀 슬랙 채널로 알림. `vectordb.as_retriever() | format_docs` 단계에서 호출되도록 format_docs 함수 안에서 호출.
- 원격 스레드 요약 시 요청 유저가 해당 채널에 속해 있는지 검사.

## 절차와 규칙
- 커맨드 접두어로 기능 분기: `위키/`, `학습/`, `요약/`(또는 요약해줘/, 뭔소리야/, 뭔소리야?), 접두어 없으면 일반질문.
- 일반질문이 기본값이 된 경위: 알파 오픈 때는 위키질문 중심이었으나 사용 후기에서 일반질문(당시 "llm질문")을 훨씬 많이 쓰고 기본값을 원한다는 의견이 많아 변경.
- 학습하기: 문서화 안 된 정보나 틀린(옛) 정보를 사용자가 `학습/`으로 입력하면 위키에 등록되고 춘시리도 학습. 이후 같은 질문에 새 정보로 답함.
- 알파 공지 규칙: 위키 데이터를 매시간 정각마다 학습, 위키에 없는 내용은 답변을 잘 못하지만 위키를 업데이트하면 1시간 후 더 정확한 답변, 민감정보나 비밀정보는 비공개 처리하거나 "exclude" 라벨을 넣어 학습 제외.
- 원격 요약: `@춘시리 <요약커맨드> <스레드링크>`. 요청 유저와 춘시리가 모두 속한 채널의 스레드만 읽음(DM방 불가).
- PR 리뷰 트리거: 1) PR이 새로 열림 2) 열린 PR에 새 커밋 3) 닫힌 PR 재오픈. 이전 춘시리 리뷰는 Minimize 처리해 PR이 지저분해지는 것을 방지.
- 주간보고: 크루가 슬랙에서 자기 티켓 정리(완료 티켓, 차주 IN PROGRESS 티켓, 이슈 및 협의 필요사항 입력, "다시 생성" 또는 "이대로 확정" 버튼), 모두 확정되면 팀 전체 요약, 리더가 "티켓 정리 완료. 아지트로 발사!" 버튼으로 포스팅.
- 보안팀이 체크한 2가지: 베드락 입력/출력값 제어(민감정보, 개인정보 필터링), 위키 내 민감정보 문서는 읽지 않아야 함(예외 처리).
- 보안춘시리 알림은 검색한 사람을 잡으려는 것이 아니라 민감정보 문서를 보안팀이 빠르게 예외 처리하거나 삭제하도록 하기 위한 장치.

## 수치와 결과
- 전처리 주기: 1시간
- 위키 "VDI" 검색 결과 623개
- 답변 시간 표시(그림): 위키질문 9.0초, 7.0초, 학습하기 17.0초, 일반질문 5.0초, 요약하기 49.0초, PR 리뷰 16.0초, 12.0초
- 요약 사례 스레드: 댓글 100개 이상
- 알파 오픈 공지 반응 이모지 수 다수(45, 49 등, 그림)
- 가드레일 스로틀링 에러: "reached max retries: 4"
- 주간보고 자동화로 "많은 크루들의 시간과 노력을 절감"했다고 서술하나 정량 수치는 원문에 없음
- 요약하기 기능이 "의외로 반응이 가장 핫했"다는 서술(정량 없음)

## 실패, 한계, 주의점
- 위키에 옛 정보가 남아 있으면 틀린 답을 함(Vault 권한 신청 옛 링크 사례). 학습하기로 정정.
- "사내의 모든 정보가 문서화 되어있진 않습니다." 문서 없는 내용은 답을 잘 못함.
- PR diff가 너무 크면 가드레일에서 ThrottlingException 발생: "On-demand ApplyGuardrail content filter policy text units per second limit exceeded". AWS Quota를 조정하거나 Stream API로 해결 가능.
- 서울 리전 베드락 모델이 한정적(Claude만, 임베딩은 Titan만). Titan 텍스트 모델은 서울 리전 불가.
- exclude 레이블을 모든 대상 문서에 다는 것은 쉽지 않음. 그래서 감지 알림을 추가.
- 한 PR에 리뷰가 많이 달릴 수 있음(이벤트마다 호출). Minimize로 완화.
- ChatBedrockConverse만으로 다 구현할 수 있었겠지만 당시 차이를 잘 몰라 converse와 분기 처리해 둠.
- 개발 기간 대부분은 LLM 모듈이 아니라 슬랙 메시지 포맷팅, 아지트 API 분석, 리팩토링에 들었음.
- 향후 계획: Ollama로 오픈소스 LLM 제공, 베드락 Knowledge Bases, 개인/팀별 커스텀 조건(트리거 명령어, LLM과 벡터 DB 종류, 코드리뷰 트리거), 다양한 페르소나와 Multi Agent 아키텍처, 일부 전문 분야 파인튜닝. "다 할 수 있을진 모르겠지만"이라고 명시.

## 그림 설명

- "전처리 파트: 1시간마다 사내 문서를 스캔하고, 업데이트분을 벡터 DB에 저장합니다."

- "예외 처리할 문서에 ‘exclude’ 레이블을 걸면 전처리 파트에서 제외하도록 개발하였습니다."

- "실제로 전체 개발 기간 동안 LLM 모듈 쪽 작업은 그리 길지 않았습니다. 오히려 슬랙 메시지 포맷팅과 아지트 API 분석, 그리고 리팩토링에 시간이 더 걸렸던 것 같습니다."

## 우리 설계에 쓸 만한 점
- [추론] 문서관리 역할은 "주기적 스캔, 이전 백업과 비교해 변경분만 임베딩, 반영 후 백업 갱신" 파이프라인을 그대로 따라 지식 저장소를 증분 갱신하도록 설계할 수 있다.
- [추론] 지식 저장소에 "exclude" 같은 제외 표시를 두고 전처리 단계에서 걸러내는 규칙은 폐기된 문서, 개인 메모, 민감 문서를 에이전트 검색 대상에서 빼는 기본 장치로 쓸 수 있다.
- [추론] 옛 정보로 틀린 답을 한 사례처럼, 답변에 관련 문서 목록과 각 문서의 업데이트 날짜를 항상 붙이면 사람 검토자가 근거의 최신성을 바로 판단할 수 있다. 검수 역할의 출력 형식으로 채택할 만하다.
- [추론] "학습/" 커맨드처럼 사람이 정정한 내용을 위키에 먼저 등록하고 그 문서를 검색 대상으로 삼는 방식은, 지식 저장소의 원본을 사람이 볼 수 있는 문서로 유지하는 원칙(에이전트 기억이 아니라 문서가 원천)으로 옮길 수 있다.
- [추론] 커맨드 접두어로 기능을 명시적으로 분기하는 방식은 오케스트레이터 라우팅의 단순한 첫 버전으로 쓸 수 있다. 다만 사용자가 기본값으로 원한 것은 일반질문이었으므로, 기본 라우팅은 실제 사용량을 보고 정해야 한다.
- [추론] 아지트 1차 응대 후 사람이 최종 조치(stop 후 1주 관찰 뒤 삭제)를 한 흐름은 운영 에이전트는 진단과 근거 제시까지, 변경 조치는 사람 승인으로 나누는 설계의 근거가 된다.
- [추론] PR 리뷰의 트리거 이벤트 3종과 이전 결과 Minimize 규칙은 검수 에이전트가 반복 실행될 때 이전 산출물을 접고 최신만 노출하는 규칙으로 옮길 수 있다.
- [추론] 주간보고 흐름(개인이 정리하고 재생성 또는 확정, 전원 확정 후 팀 요약, 리더 버튼으로 게시)은 제작 에이전트 산출물에 사람 확정 단계를 두고 최종 게시도 사람이 누르는 human review 패턴의 구체 예시다.
- [추론] 모든 LLM 호출을 보안팀이 관리하는 가드레일 경유로 강제하고, 검색 단계(format_docs)에서 민감정보 감지 시 별도 채널로 알리는 구조는 모니터링 역할의 입출력 필터와 알림 설계로 옮길 수 있다. 알림 목적을 사용자 감시가 아니라 문서 조치로 명시한 점도 운영 원칙에 넣을 만하다.
- [추론] converse처럼 모델 공급사와 무관한 단일 호출 인터페이스를 두면 부서별 에이전트의 모델 교체 비용을 줄일 수 있다.
- [추론] 큰 입력(PR diff 전체)이 가드레일 쿼터에 걸린 사례는 검수 에이전트 입력 크기 상한과 분할, 재시도 정책을 미리 정해야 한다는 근거다.
- [추론] 저자들도 Multi Agent 아키텍처와 페르소나 정의를 "향후 계획"으로만 제시했으므로, 멀티에이전트 설계 자체에 대한 카카오페이증권의 검증된 결과는 이 글에 없다.
