## 핵심 한 문장
Bedrock Agent + Lambda 서버리스 구상을 버리고 EC2 서버가 Bedrock API를 직접 호출하는 구조로 바꾼 뒤, "LLM이 이미지 프롬프트를 만들고 Nova Canvas가 그리는" 2단 생성과 "의도 분류 -> Entity 추출 -> SQL 생성 -> SQL 검증 -> 도구 선택(tool calling) -> 서버가 도구 실행" 체인으로 자연어 거래내역 검색을 구현함.

## 배경과 문제
- 카카오페이 통합내역 서비스의 거래 내역에는 기본 정보만 있어 어디서, 누구와, 무엇을 하며 발생한 거래인지 맥락 파악이 어려움.
- 기존 메모 기능은 문자열 입력만 가능해 입력 허들이 높음.
- 기획: 메모 입력을 쉽게(칩 선택), 메모 기반 이미지로 캘린더 요약, 메모까지 활용한 자연어 검색.

## 구조와 구성요소
- 전체(그림 04): 유저 -> AWS Amplify(FE) -> Amazon EC2(애플리케이션 서버) -> Amazon Bedrock. EC2 -> Amazon S3(이미지), EC2 -> Amazon RDS(거래 내역). Amplify -> S3.
- 설계 변경: 초기에는 Lambda + Bedrock Agent로 서버가 호출만 하는 서버리스 구조를 생각했으나, 길이를 알 수 없는 거래 내역 목록을 Lambda 인자나 Bedrock Agent 프롬프트로 넘기는 것이 비효율적이라고 결론 -> 서버가 Bedrock API를 호출할 때 Tool 목록과 파라미터를 제시하고, 응답으로 받은 Tool을 서버가 직접 핸들러로 실행.
- 모델: Claude 3.5(Bedrock `invoke_model`, anthropic_version "bedrock-2023-05-31"). 이미지 모델 Nova Canvas.
- 이미지 생성(그림 05): EC2 -> (1) 거래내역 전달 -> "프롬프트 생성" LLM -> "이미지 생성" 모델 -> 생성된 이미지 반환 -> (2) S3 업로드.
- 자연어 검색(그림 10): EC2 -> (1) 유저 프롬프트 전달 -> 의도 분류 -> Entity 추출 -> TEXT2SQL (의도, Entity, SQL 반환) -> (2) RDS에서 관련 거래내역 조회 -> (3) 유저 프롬프트, 의도, Entity, 관련 거래내역 전달 -> Tools 판단 -> Tools 반환.
- Text2SQL은 LangChain 체인 + Bedrock Claude 3.5. 체인: 의도 분류 전용 체인, Entity 추출 체인, sql_generation_chain, sql_validation_chain.
- 도구(tools_config에 name, description, input_schema): display_transactions, calculate_sum, analyze_trend 등(본문에 등장한 이름 기준, 전체 목록은 "중략").
- FE: 도구별 응답을 독립 UI 컴포넌트로 렌더링(analyze_trend UI component, display_transactions UI component).

## 절차와 규칙
- 메모 입력: 목적, 인물, 감정 카테고리 칩 선택. 입력 텍스트 기반으로 근접 카테고리 추천.
- 이미지 모델 선택: 사용 가능했던 Amazon Titan Image Generator G1(최대 512자), Stability AI SDXL(최대 77자), Nova Canvas(최대 1024자) 중 프롬프트가 가장 긴 Nova Canvas 선택. 같은 프롬프트로 3개 모델을 반복 생성해 팀원 모두 Nova Canvas가 가장 자연스럽다고 평가.
- 이미지 프롬프트 생성기: 개발자가 조건문으로 프롬프트를 짜면 다양성 부족, 번거로움, 1024자 관리 어려움 -> LLM이 데이터와 조건으로 이미지 프롬프트를 자동 생성.
- 이미지 입력 요소: 거래 데이터(결제처, 타임스탬프, 금액, 카테고리), 사용자 추가 정보(메모, 함께한 사람, 감정), 사용자 개인데이터(성별, 나이, 선호 스타일).
- 이미지 규칙: 메모를 핵심 요소로(셔츠 구매 -> 셔츠 고르는 모습), 거래 시간으로 시간대와 계절감 반영("거래 시간을 통해 시간대와 계절감을 반영합니다." 한 줄 지시), 감정과 인원에 따라 구도(혼자 슬픔 -> 클로즈업, 2명 이상 -> 중거리 샷), 성별과 나이 반영, 국적 한국인 고정, 스타일 옵션(애니메이션, 수채화, 픽셀), negative prompt에 'text', 'captions', 'speech bubble' 등.
- 자연어 검색 3단계: Text2SQL -> Tool Selection -> Tool Execution.
  - 의도 분류 7가지 + 그 외: 내역, 비교, 추이, 최대, 최소, 합계, 평균. '그 외'는 거래 데이터로 답할 수 없는 질문으로 판단.
  - Entity 추출: type, category, time_period, keywords를 JSON으로. SQL WHERE 조건 재료.
  - SQL 생성: 현재 날짜, DB 스키마, 의도, Entity, 유사 질문 예시 제공. SQL 검증: 생성된 SQL을 다시 LLM에 넣어 문법 오류와 구조 문제를 최소 수정. 최종적으로 'SELECT *' 구조 유지.
  - Tool Selection: 조회 후 Claude가 다시 질문을 해석해 어떤 도구를 어떤 인자로 호출할지 결정. Few-Shot 예시(User query, Thought process, Intent, Tools)를 제공.
  - 추이 분석 시 기간 미지정이면 기본 최근 3개월.
  - Tool Execution: LLM은 계획만 세우고 실행하지 않음. 도구별 함수를 미리 매핑하고 서버가 실행. 결과 JSON(tool, success, result, parameters), 여러 도구면 배열.

## 수치와 결과
- 수상: 제 2회 카카오페이 해커톤 2등.
- 이미지 프롬프트 최대 길이: Titan G1 512자, SDXL 77자, Nova Canvas 1024자.
- 의도 분류 7가지 + 그 외.
- 추이 기본 기간 최근 3개월.
- 저자 서술: Few-Shot 제공으로 "도구 선택 오류가 줄어들고" 복잡한 요청(비교 + 시각화 + 상세 보기)에서도 도구를 올바르게 조합. 오류 감소 폭의 수치는 원문에 없음.
- 정량 평가(정확도, SQL 성공률 등)는 원문에 없음.

## 실패, 한계, 주의점
- 제한된 정보로 이미지를 만들면 "AI가 마음대로 사용자의 하루를 예측"해 실제 경험과 괴리 -> 메모, 감정, 인물 입력으로 보완.
- 개발자 정의 프롬프트만으로는 이미지 다양성 부족, 조건문 번거로움.
- Lambda/Bedrock Agent로 가변 길이 거래 목록 전달은 비효율이라는 판단으로 설계 변경.
- "수많은 오류와 씨름" 했다는 서술 외 구체적 실패 사례는 원문에 없음.

5. "제공받은 데이터와 주어진 조건에 따라 LLM이 자동으로 프롬프트를 만들어주는 '이미지 프롬프트 생성기'를 개발했습니다."
6. "제한된 정보로 이미지를 생성할 경우, AI가 마음대로 사용자의 하루를 예측하게 되어, 실제 경험과 괴리감이 큰 결과물이 나오기 마련이었습니다."

9. "sql_validation_chain : 생성된 SQL 쿼리를 다시 LLM에 전달하여 문법 오류를 검토하고 구조적 문제를 최소한의 수정으로 보완하는 체인"

11. "실제로 Few-Shot 예시들을 사전에 제공함으로써 LLM의 분석 도구 선택 오류가 줄어들고, 복잡한 요청 (ex. 비교 + 시각화 + 상세 보기)의 경우에도 분석 도구들을 올바르게 조합하여 목적에 맞는 분석 흐름을 생성할 수 있었습니다."

13. "프론트엔드에서는 각 분석 도구의 응답 결과를 하나의 독립적인 UI 컴포넌트로 구성해, 사용자가 분석 결과를 직관적으로 이해할 수 있도록 했습니다."

## 우리 설계에 쓸 만한 점
- [추론] 대량, 가변 길이 데이터는 에이전트 프롬프트로 넘기지 말고 서버가 들고 있으면서 LLM에게는 "도구 선택과 인자"만 받게 한 판단은, 운영 부서 에이전트가 로그나 지표 같은 큰 데이터를 다룰 때 그대로 적용할 수 있다.
- [추론] "의도 분류 -> 엔티티 추출 -> 생성 -> 검증"을 별도 체인으로 쪼개고 앞 단계 결과를 뒤 단계에 넘기는 구조는, Supervisor 라우팅 앞단에 의도 분류기를 두는 설계의 구체 예시다.
- [추론] 의도 범주에 "그 외(처리 불가)"를 명시적으로 두는 것은 라우터가 억지로 어떤 부서에 배정하지 않게 하는 가드레일이다.
- [추론] 생성 결과(SQL)를 별도 LLM 호출로 검증하는 단계는, 개발 부서 에이전트의 코드 생성 뒤 검증 에이전트를 두는 패턴과 대응된다.
- [추론] LLM은 계획만, 실행은 사전 매핑된 서버 함수가 하는 분리는 권한 통제(에이전트가 직접 실행하지 못함)에도 유리하다.
- [추론] 마케팅 콘텐츠 생성에 "LLM이 생성 모델용 프롬프트를 쓰고, 생성 모델이 만든다"는 2단 구조와 negative prompt, 모델별 프롬프트 길이 제한 비교를 참고할 수 있다.
- [추론] 결과 화면에 최소/최대가 뒤바뀐 값이 그대로 노출된 것으로 보아, 도구 실행 결과에 대한 자동 검증이 없었던 것으로 보인다. 우리 설계에는 도구 출력 검증 단계를 넣을 필요가 있다.
- [추론] 이 글은 멀티 에이전트가 아니라 단일 LLM의 다단계 체인과 tool calling 사례다.
