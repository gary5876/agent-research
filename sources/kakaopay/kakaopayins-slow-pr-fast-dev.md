# PR을 더 느리게 만들기 위한 고민

- URL: https://tech.kakaopay.com/post/kakaopayins-slow-pr-fast-dev/
- 게시일: 2026. 6. 12
- 저자: long.black (롱). 자기소개 "카카오페이손해보험 재무서버개발팀 백엔드 개발자 롱 입니다. 크루들과 AI 눈높이를 올리고 있어요."
- 태그: AI, 카카오페이손해보험
- 소속: 카카오페이손해보험 (재무서버개발팀)
- 요약(블로그 메타): "AI 도입 이후 코드 생산 방식은 바뀌었으나 PR을 다루는 방식은 과거에 머물러있습니다. 이천 줄짜리 PR 앞에서 approve를 누르는 손이 망설여진 적 있다면 이 글이 도움이 될 수 있습니다."
- 읽은 방법: curl 원본 HTML에서 본문 전문 추출, 본문 이미지 4장 직접 확인.

## 핵심 한 문장

AI로 코드 생산은 빨라졌지만 병목이 "코드를 이해하는 곳"(사람 리뷰)으로 옮겨갔으므로, 리뷰를 빠르게 하는 대신 PR 이전 단계(설계 문서, Task 분해, 의사결정형 PR 템플릿)를 의도적으로 느리게 하고, AI 리뷰어(조르깃)가 기계적 지적을 먼저 처리한 뒤 사람은 트레이드오프 판단과 최종 승인에만 집중하게 한다.

## 배경과 문제

- 바이브 코딩에서 확장: 프로젝트가 커지자 AI가 맥락을 모르면 엉뚱한 코드, 파일마다 다른 스타일, 이미 있는 유틸리티 재작성, 팀 컨벤션 무시가 생김.
- 그래서 자리 잡은 방식: 프로젝트 구조와 규칙은 AGENTS.md, 반복 작업 패턴은 SKILL로 문서화, 위험 요소는 Harness(안전 장치)로 관리. 이 Context를 넘긴 뒤 Plan(구현 계획)을 세우고 Subagent에게 코드 생산을 위임. "만들어줘"에서 "이 맥락(플랜)에서 이 방식으로 만들어줘"로 바뀜.
- 효과: 하루 종일 걸리던 기능이 한두 시간이면 PR로 올라옴.
- 새 병목: 리뷰할 사람은 그대로. 아침마다 수백 줄짜리 리뷰 요청이 쌓이고, 리뷰하다 돌아오면 자기 작업 컨텍스트를 잃음. 선택지는 "꼼꼼히 보느라 며칠 열어두기" 또는 "빠르게 훑고 approve", 많은 팀이 후자, 이 팀도 종종 후자.
- 공통 영역 방치: 공통 모듈 PR은 영향 범위가 넓어 리뷰 부담 큼 → 미뤄짐 → 충돌 누적 → 아무도 안 건드림 → "건드리면 안 되는 영역"이 생김. 저자 표현으로 기술부채가 아니라 "리뷰부채".
- 리뷰의 형식화: 800줄 PR을 제대로 읽으려면 한 시간 이상(변경 파일 14개의 맥락 파악, 영향 범위 추적, 설계 의도 이해). 전체를 훑고 눈에 띄는 것만 코멘트. 리뷰가 품질 게이트가 아니라 머지 전 형식 절차로 변질. "누군가 봤으니 괜찮겠지" 착각 확산. 설계 판단이나 트레이드오프가 있는 중요한 PR도 같은 무게로 가볍게 넘어감.

## 구조와 구성요소

### 1) 개발 흐름 전체 (AI 이전 단계 강화)

- 컨텍스트 계층: AGENTS.md(구조, 규칙) + SKILL(반복 작업 패턴) + Harness(위험 요소 관리) → Plan → Subagent가 코드 생산.
- 프로젝트 B의 분해 파이프라인: `설계 문서 → Task 분해 → JIRA subtask → PR`
  - 코드를 쓰기 전에 AI와 함께 설계 문서 작성.
  - AI가 분해된 Task를 의존성 기반으로 정렬: 독립적인 것은 병렬, 의존적인 것은 차례로.
  - 실제 사례: 10개 Task를 5개 Phase로 나누고 각 Phase 안의 구현 순서까지 설계 문서에 포함.
  - 결과물: 설계 문서 하나에서 Task와 Subtask가 계층적으로 분류되고 구현 시작 순서까지 정해진 상태. 사람은 "맞는지" 판단만.

### 2) PR 템플릿 (체크리스트가 아닌 의사결정 문서)

원문 템플릿 항목:
```
# 해결하려는 문제가 무엇인가요?
# 왜 해야 하나요?
# 어떻게 해결했나요?
# 이 PR의 한계 & 트레이드오프
# 기존 기능에 미치는 영향
# Edge Case & 실패 시나리오
# 검토한 대안과 선택 이유
# 리뷰 포인트 (파일/영역별 Risk 🔴🟡🟢)
```
- "왜 해야 하나요?"가 가장 중요. 작성자 자신에게 던지는 질문. AI로 30분이면 되는 리네임, 구조 개선, 패턴 통일 같은 "할 수 있으니까 한다" PR을 걸러냄. AI 이전에는 구현 비용이 필터 역할을 했는데 그 비용이 30분~1시간으로 줄어 "왜?"가 필터를 대신함.
- "한계 & 트레이드오프": 리뷰어가 어디를 집중해서 볼지 알려줌. 비어 있으면 판단할 게 없다는 뜻, 채워져 있으면 사람이 봐야 한다는 신호.
- "리뷰 포인트": 변경된 15개 파일 중 어디가 위험한지 작성자가 먼저 표시.
- AI 코딩 도구가 코드를 만들면서 동시에 템플릿을 채움. 플랜과 구현 중 내린 결정이 PR에 녹아 문서화됨.
- 그림 1(실사례)에는 텍스트 템플릿에 없는 두 섹션이 더 있음: "Assignee 자기검증" 체크리스트 4개, "RCA 룰"(r/c/a 정의). 아래 그림 설명 참고.

### 3) AI 리뷰어 조르깃(Jorgit)

- 인프라: "연구개발 망에 있으며 보안 규정을 준수하는 클라우드 서비스를 활용". 모델명은 원문에 없음.
- 트리거: PR이 열리면 자동 수행. 프로젝트마다 다른 설정.
- 4단계 멀티스텝 리뷰:
```
PR opened → Step 1: 언어 관점
          → Step 2: 프레임워크/인프라
          → Step 3: 도메인/보안
          → Step 4: 최종 검증 → 인라인 코멘트 + 요약
```
- 심각도 태그: [r] 꼭 반영해 주세요 / [c] 웬만하면 반영해 주세요 / [a] 사소한 의견입니다. (그림 1의 RCA 룰에서는 r = Request changes, c = Comment, a = Approve에 대응)
- [r] 예시: "r: 예외 처리 누락: Redis LPUSH 실패 시 warn 로그만 남기고 있는데, 이는 장애 후 복구 메커니즘이 동작하지 않는 심각한 상황입니다."
- 출력 형태: PR 전체 리뷰 코멘트(요약) + 인라인 코멘트 (그림 3, 4).

### 4) AI 리뷰 위에 사람 리뷰를 얹는 구조

```
PR 생성
  ↓ (2분)
jorgit: 구조적 품질 스캔
  ↓
작성자 1차 피드백 반영
  ↓ (2h 50m)
사람 리뷰어: 비즈니스 판단 + 최종 승인
  ↓ (2h 40m)
머지
```
- 팀 룰: AI 리뷰어가 아무리 빨라도 사람 승인 없이는 머지 불가. AI 리뷰어는 approve 할 수 없음.
- 사람 리뷰를 기다리는 2~3시간 동안 AI 피드백을 반영해 두면, 사람이 볼 때는 기계적 지점이 이미 정리된 상태.

### 5) PR 무게 구분 기준

기준 질문: "왜 이렇게 했는가"에 대한 답이 자명한가?

| 변경 유형 | 사람이 판단할 것 | AI만으로 충분한가 |
|---|---|---|
| 리네임/포맷팅 | 빠뜨린 곳이 없는가? | ✅ |
| 테스트 추가 | 기존 동작을 깨뜨리지 않는가? | ✅ |
| 메서드 추출 (동작 동일) | 구조가 나아졌는가? | ✅ |
| 비즈니스 로직 변경 | 이 동작이 맞는가? | ❌ |
| 새로운 패턴 도입 | 이 방향이 맞는가? | ❌ |
| 트레이드오프가 있는 설계 | 이 비용을 수용할 것인가? | ❌ |

- 예: 리네임 PR("왜 state를 statusCode로?")의 답은 "프로젝트 컨벤션" → 판단이 아니라 확인. VO 분리 PR("왜 PK 조회를 추가?")의 답은 "영속성 안전성 vs 성능 트레이드오프" → 확인이 아니라 판단.

## 절차와 규칙

- 책임의 위치를 PR 올리기 전으로 이동.
- 설계 문서가 PR보다 먼저 나온다. 코드 전에 "왜"를 정리하고 AI가 돕는다.
- PR 본문이 의사결정 문서다. "한계 & 트레이드오프" 섹션이 비었는지 채워졌는지로 리뷰어가 시간 배분을 결정.
- 리뷰 포인트를 작성자가 명시한다.
- 작게 쪼갠다. "1 subtask = 1 PR" 규칙. (158줄 PR은 30분이면 리뷰, 800줄은 감이 안 옴)
- AI 리뷰어를 도입해 예외처리 누락, null-safety 같은 기계적 지적을 먼저 처리.
- AI 리뷰어는 approve 불가, 사람 승인 필수(팀 룰).
- 심각도 태그 r/c/a를 모든 코멘트에 붙임.
- 그림 1 기준 PR 작성자(Assignee) 자기검증 체크리스트: 기존 기능을 깨뜨리지 않음 확인 / 실패 시나리오 설명 가능 / 영향 범위 파악해 작성 / 직접 테스트 수행.
- 다음 단계로 구상만 한 것(아직 시도 전): AI 리뷰만으로 머지 가능한 PR을 팀 규칙으로 정의하고, 리뷰어 역할을 "모든 코드를 읽는 것"에서 "트레이드오프에 동의하는 것"으로 재정의.

## 실패, 한계, 주의점

- "AI 리뷰가 머지 시간을 단축해 주진 않았습니다. 머지 시간은 여전히 사람의 가용성에 달려있습니다."
- 반영률 16%. 응답 없이 넘어간 68%에는 "오탐지도 있고 맥락상 해당하지 않는 지적도" 있었음. "전부 유의미한 건 아니었습니다."
- 리드타임 비교는 리뷰 인원 구성이 달라서(A 교차 리뷰 2명, B 1명) AI 효과로 해석하면 안 된다고 저자가 직접 밝힘.
- 500줄 이상 PR은 여전히 존재(테스트 변경 포함).
- AI 리뷰만으로 머지하는 규칙은 "아직 시도 전".
- 저자 자기 인정: 작게 쪼개기, 설계 의도 남기기는 AI 이전부터 알던 원칙인데 비용 때문에 지켜지지 않았을 뿐.

## 그림 설명

1. 템플릿 활용 사례 (img1): 실제 PR 본문 캡처. 문제는 `markDbApplied()`가 호출자 트랜잭션에 참여해 JPA 1차 캐시의 stale 엔티티(RECEIVED)를 읽어 "Invalid state transition: RECEIVED → DB_APPLIED" 발생. 왜: 정상 결제 흐름(TC1) 실패, DB_APPLIED 전환 불가. 어떻게: `@Transactional(propagation = REQUIRES_NEW)` 추가, 새 Persistence Context에서 DB 최신 상태(PG_CALLED) 조회, 다른 mark* 메서드와 일관성 유지. 한계와 트레이드오프 표(영역: 트랜잭션 수 증가 / 제약: REQUIRES_NEW로 별도 트랜잭션 1개 추가 / 수용 이유: 1차 캐시 문제 근본 해결, 다른 mark* 메서드와 동일 패턴). 섹션 안내문: "이 PR에서 해결하지 못한 제약, 의도적으로 수용한 트레이드오프, 또는 리뷰어의 판단이 필요한 불확실한 부분을 공유해주세요." 영향: 범위 markDbApplied() 1개 메서드, 사이드 이펙트 없음, 롤백 가능(REQUIRES_NEW 제거하면 원복). Edge case: 내부 실패 시 호출자 트랜잭션과 독립 롤백. 대안 비교 표 3개(REQUIRES_NEW 추가 선택 / entityManager.refresh() 탈락: 호출부마다 refresh 필요, 일관성 깨짐 / 호출자에서 info 갱신 전달 탈락: 근본적이지 않음, 호출부 책임 증가). 리뷰 포인트 표(PaymentProcessStateService.markDbApplied, Risk 🟢 LOW, 이유: 동일 패턴 mark* 메서드가 이미 REQUIRES_NEW 사용 중). 참고 자료: project-root/tasks/local-test-issues.md (이슈 2). 본문 텍스트 템플릿에 없는 추가 섹션 두 개: "Assignee 자기검증" 체크박스 4개(이 변경이 기존 기능을 깨뜨리지 않음을 확인했다 / 실패 시나리오를 설명할 수 있다 / 영향 범위를 파악하고 위에 작성했다 / 직접 테스트를 수행했다), "RCA 룰"(r: 꼭 반영해 주세요. 적극적으로 고려해 주세요. (Request changes) / c: 웬만하면 반영해 주세요. (Comment) / a: 반영해도 좋고 넘어가도 좋습니다. 그냥 사소한 의견입니다. (Approve)).

## 우리 설계에 쓸 만한 점

- [추론] 기획 역할의 산출물 형식으로 "설계 문서 → Task 분해 → subtask → 산출물 단위" 파이프라인을 채택하고, Task를 의존성 기반으로 Phase화(병렬 가능한 것과 순차인 것 구분)하는 것을 기획 역할의 필수 출력으로 둔다.
- [추론] 오케스트레이터는 기획 역할이 만든 Phase 순서를 그대로 작업 큐로 쓰고, 같은 Phase 안의 독립 Task만 병렬로 제작 역할에 분배한다.
- [추론] 제작 역할의 산출물 단위를 "1 subtask = 1 산출물(PR)"로 고정해 검수 단위를 작게 유지한다. 마케팅 산출물(카피, 캠페인안)에도 같은 단위 규칙을 적용할 수 있다.
- [추론] 모든 제작 산출물에 의사결정형 템플릿(문제, 왜, 어떻게, 한계와 트레이드오프, 영향, 실패 시나리오, 검토한 대안, 리뷰 포인트와 위험도)을 붙이게 하고, 비어 있는 필수 칸이 있으면 Hook으로 제출을 막는다.
- [추론] "왜 해야 하나요?"를 작성 에이전트 자신에게 먼저 답하게 하는 게이트는, AI가 "할 수 있으니까" 불필요한 작업을 만드는 것을 막는 필터로 기획 또는 오케스트레이터 단계에 넣을 가치가 있다.
- [추론] 검수 역할을 조르깃처럼 관점별 다단계(언어, 프레임워크/인프라, 도메인/보안, 최종 검증)로 나누고, 모든 지적에 r/c/a 심각도 태그를 붙이게 한다. 부서별로 관점 단계를 다르게 설정(원문: "프로젝트마다 다른 설정")한다.
- [추론] 검수 에이전트에게는 승인 권한을 주지 않는다. 원문의 팀 룰(AI는 approve 불가, 사람 승인 필수)을 권한 모델로 구현한다.
- [추론] 사람 검토 대상 선별 규칙으로 원문의 변경 유형 표를 쓴다. "한계와 트레이드오프" 칸이 채워졌거나 비즈니스 로직, 새 패턴, 트레이드오프 설계면 사람에게 올리고, 리네임, 포맷, 테스트 추가, 동작 동일 리팩터링은 자동 경로로 보낸다. 단 원문은 자동 머지를 "아직 시도 전"이라고 했으므로 이 부분은 원문 검증이 없는 확장이다.
- [추론] 거절된 AI 코멘트와 그 근거를 문서관리 역할이 의사결정 기록으로 보관한다(원문: 거절 8%가 의사결정 기록이 됨).
- [추론] 모니터링 역할의 지표로 원문 지표를 그대로 쓸 수 있다: 산출물 수, 산출물 크기 중앙값, 생성 → 첫 사람 리뷰 시간, 첫 리뷰 → 승인 시간, 주 리뷰어 편중도(63% 같은), AI 코멘트 반영/거절/무응답 비율.
- [추론] 무응답 68%, 오탐 존재라는 결과를 보면 검수 에이전트 코멘트 수 자체를 성과로 보면 안 되고, 반영률과 오탐률을 따로 추적해야 한다.
- [추론] 사람 대기 시간 동안 AI 피드백을 먼저 반영하는 순서(AI 검수 → 작성자 수정 → 사람 검토)를 파이프라인 순서로 고정한다.
- [추론] "Assignee 자기검증" 체크리스트 4개는 제작 에이전트의 제출 전 자가 검증 항목으로 옮길 수 있다. 다만 자가 체크는 원문에서도 사람이 체크하는 형식이라 에이전트 자기 선언으로 대체하면 신뢰도가 낮다(ai-agent-1 원문의 "완료 선언" 경고와 연결).
