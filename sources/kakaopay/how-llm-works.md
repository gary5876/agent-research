# 백엔드 개발자의 시선으로 풀어본 LLM 내부 동작 원리: 6단계로 쉽게 이해하기

- URL: https://tech.kakaopay.com/post/how-llm-works/
- 게시일: 2025-09-11
- 저자: wi.fi (카카오페이 정산플랫폼팀 백엔드 개발자 "와이")
- 태그: 카페톤, AI, LLM, 자연어처리
- 소속: 카카오페이

## 핵심 한 문장
LLM이 답을 만드는 과정을 토큰화, 임베딩, 위치 인코딩, 트랜스포머와 어텐션, 예측, 루프와 디코딩 6단계로 풀고, 각 단계를 근거로 프롬프트 작성 요령 6가지를 도출한 입문 해설 글이다.

## 배경과 문제
- 프롬프트 작성법을 들었을 때 "왜 그런 방식이 효과적인지 몰랐지만, 동작 원리를 알고 나니 그 이유를 이해할 수 있었"다는 동기.
- 대상: LLM 기반 서비스를 개발하거나 업무에 활용하려는 백엔드 개발자.
- 저자 스스로 "비전문가인 백엔드 개발자의 관점"이라 전문가 시각과 다를 수 있다고 밝힘.
- 이 글은 에이전트/시스템 구축 사례가 아니라 원리 해설이다. 아키텍처, 운영 절차, 도입 결과는 원문에 없음.

## 구조와 구성요소
6단계 표 (원문):
| 단계 | 동작 | 설명 |
|---|---|---|
| 1 | Tokenization | 프롬프트를 토큰 단위로 분리하고 각 토큰에 고유 ID 할당 |
| 2 | Embedding | 토큰 ID를 의미를 담은 벡터로 변환 |
| 3 | Positional Encoding | 순서를 인식하도록 위치 정보를 벡터에 더함 |
| 4 | Transformer & Attention | 문맥을 파악하고 각 단어 표현을 정교하게 다듬음 |
| 5 | Prediction | 다음 토큰 예측 |
| 6 | Loop & Decoding | 예측 토큰을 반복적으로 디코딩해 문장 완성 |

단계별 세부:
- 1단계: Gemini는 SentencePiece 사용. 언어 중립적(공백 기준이 아니라 유니코드 문자열을 통계적으로 묶음, 조사가 붙는 한국어에 효과적), 서브워드 기반. 예제는 `vocab_size=133`, `model_type=bpe`로 훈련 후 "나는 LLM 내부 동작 원리를 공부한다."를 13개 조각으로 분리하고 ID로 변환 후 복원. 토크나이저는 훈련(개발사가 한 번, 수십 테라바이트 데이터)과 추론(메모리에 로드해 즉시 변환) 단계로 분리되어 사용자 입력으로 매번 재훈련하지 않음. BPE(빈도 높은 쌍 병합, bottom-up, GPT/LLaMA/Gemini)와 ULM(큰 어휘에서 시작해 제거, top-down, T5/mBART) 비교.
- 2단계: Embedding Table(토큰 ID별 벡터). 예: Jeans, ID 1423, 768차원. 의미론적 근접성, PCA 2차원 시각화. 예제는 `jhgan/ko-sroberta-multitask`로 "자동차/자전거/행복" 임베딩, 768차원, 코사인 유사도 계산.
- 3단계: 어텐션은 순서를 모르므로 sin/cos 위치 벡터를 임베딩에 더함. 수식 PE(pos,2i)=sin(pos/10000^(2i/d_model)), PE(pos,2i+1)=cos(...).
- 4단계: 인코더(Multi-Head Self-Attention + FFN), 디코더(Masked Multi-Head Self-Attention, 인코더 출력과 함께 보는 Multi-Head Attention, FFN), 출력(Linear로 어휘 크기 차원 변환, 예 [10,768]에서 [10,50000], Softmax로 확률), Add & Norm(잔차 연결, 레이어 정규화).
- 5단계: 확률 계산(Logits, Softmax) 후 Temperature로 분포 조절, 샘플링(Greedy, Top-K, Top-P). Top-P는 "Gemini와 같은 최신 모델들이 주로 사용하는 핵심 전략".
- 6단계: Predict, Append, Loop를 EOS 토큰 또는 최대 길이(예: 100개) 도달까지 반복(자동 회귀). 마지막에 정수 ID 배열을 텍스트로 디코딩.

## 절차와 규칙
원리 기반 프롬프트 요령 6가지 (원문 순서):
1. 풍부하고 구체적인 콘텍스트 제공: "코드에 에러가 나" 대신 버전, 사용 기술, 에러, 코드와 로그 제공. 어텐션(4단계)이 핵심에 집중.
2. 예시를 통한 출력 유도: 예시 한두 개로 출력 형식 유도(재학습이 아니라 어텐션 가중치 유도).
3. 명확한 역할과 형식 지정: "당신은 10년 차 백엔드 개발자입니다. Kotlin Spring 코드로 답변해 주세요." 예측(5단계)의 단어 범위를 좁힘.
4. 복잡한 작업은 단계별로 분해: "A 데이터를 분석해서, 그래프를 그리고, 보고서를 써줘" 대신 1) 특징 분석 2) 그래프 코드 3) 보고서 초안으로 나눠 요청.
5. 부정문 대신 긍정문: "JSON 형식 외에는 출력하지 마" 대신 "반드시 RFC 8259 표준을 준수하는 JSON 형식으로만 출력해줘".
6. 결과를 비판적으로 검토하고 피드백: "그 답변은 ~한 점에서 틀렸어. 그 점을 수정해서 다시 설명해줘." 루프(6단계)를 사용자가 직접 제어.

샘플링 주의 규칙: Temperature가 너무 높으면 일관성 저하, 낮으면 보수적이고 반복적. Top-K는 K가 너무 작으면 반복, Top-P는 P가 너무 높으면 무관한 단어 선택 가능.

## 수치와 결과
- 예제 토큰 ID: "LLM의 내부 동작 원리." 는 [73, 12, 36, 63, 96, 91]
- SentencePiece 예제 vocab_size 133, 출력 ID [89, 93, 113, 11, 8, 9, 44, 89, 107, 97, 131, 116, 91]
- 임베딩 차원 768 (Jeans 예시, ko-sroberta-multitask)
- 코사인 유사도: 자동차와 자전거 0.8315, 자동차와 행복 0.1854
- Linear 출력 예: [10, 768]에서 [10, 50000]
- Softmax 예: 매우 0.15, 복잡 0.12, 정말 0.10, 이렇게 0.07, 어떻게 0.05
- Temperature 예: 원래 0.3/0.25/0.1이 T=2에서 0.1/0.09/0.08, T=0.5에서 0.5/0.35/0.05
- Top-K(K=3) 재정규화 0.45/0.35/0.2, Top-P(70%) 재정규화 0.4/0.32/0.15/0.13
- 최대 길이 예시 100개
- 리뷰어: "단 30분 투자로"
- 시스템 성능이나 도입 성과 수치는 원문에 없음

## 실패, 한계, 주의점
- 저자 스스로 비전문가 관점이라 전문가 시각과 다를 수 있다고 명시.
- 예시는 한글로 설명했지만 실제로는 임베딩부터 디코딩 직전까지 정수 ID 기반 처리라고 주의.
- 샘플링 파라미터별 부작용(위 절차 참조).
- 에이전트, RAG, 도구 호출 관련 한계는 원문에 없음.

## 그림 설명
- 그림 1 Tokenization: "LLM의 내부 동작 원리."가 ['LLM','의','내부','동작','원리','.']로, 다시 [73,12,36,63,96,91]로 변환되는 3단 화살표 도식.
- 그림 2 Tokenizer Algorithm 표: BPE(빈도 높은 문자 쌍 점진 병합, Bottom-up, 적은 토큰으로 압축, 단어 경계 명확한 언어에 효율적, 대표 모델 GPT/LLaMA/Gemini)와 ULM(큰 초기 어휘에서 시작, Top-down, 중요도 낮은 서브워드 제거, 대표 T5/mBART).
- 그림 3 Embedding Table: Jeans 1423, Cotton Pants 3452, Shorts 7465, AI 1234, Robot 1634, Car 7800, Motorcycle 2489, Air Conditioner 4379 각각이 벡터로 매핑.
- 그림 4 PCA 2D 시각화: 의류(Jeans, Shorts, Cotton Pants)는 오른쪽에 모이고, Car와 Motorcycle은 아래쪽에 가깝고, AI와 Robot은 왼쪽, Air Conditioner는 위쪽에 떨어져 있음.
- 그림 5 The Transformer (Attention Is All You Need Figure 1): 인코더 Nx(Multi-Head Attention, Add & Norm, Feed Forward), 디코더 Nx(Masked Multi-Head Attention, Multi-Head Attention, Feed Forward), Linear, Softmax, Output Probabilities.
- 그림 6 Logits & Softmax: 후보 매우/복잡/정말/이렇게/어떻게가 로짓을 거쳐 0.15/0.12/0.10/0.07/0.05 확률로.
- 그림 7 to 9 Temperature: "원리"+"는" 다음 후보 분포(매우 0.3, 복잡 0.25, 정말 0.1)가 T 없음은 그대로, 높은 T(분모 2)에서 0.1/0.09/0.08로 평탄화, 낮은 T(0.5)에서 0.5/0.35/0.05로 뾰족해짐.
- 그림 10 Greedy Search: LLM, 의, 내부, 동작, 원리, 는을 모델이 차례로 거치고 최고 확률 "매우 0.3"만 선택(빨간 박스).
- 그림 11 Top-K: 상위 3개(매우, 복잡, 정말)만 남겨 0.45/0.35/0.2로 재정규화.
- 그림 12 Top-P (도식 제목 오타 "Tok-P"): 누적 70%까지 4개(매우, 복잡, 정말, 좋다) 후보, 0.4/0.32/0.15/0.13로 재정규화.
- 그림 13 Predict-Append-Loop: Time 1에서 7까지 "LLM"에서 "의", "내부", "동작", "원리", "는", "재미있다", <EOS>까지 한 토큰씩 붙여 다시 넣는 과정.

## 원문 인용
- "LLM의 토크나이저는 실시간으로 요청이 들어올 때마다 사용자 입력을 추가로 훈련시키지 않고, 훈련(Training)과 추론(Inference)이라는 두 단계로 명확하게 구분하여 동작합니다."
- "벡터 간의 거리는 의미론적 근접성(Semantic Proximity) 이라는 성질을 통해 단어들 사이의 관계를 수학적으로 이해하고 추론할 수 있게 해줍니다."
- "반면, Temperature가 너무 높으면 문맥과 관련 없는 단어가 선택되어 텍스트의 일관성이 떨어질 수 있음"
- "이 단계는 새로운 계산을 하는 것이 아니라, 5단계에서 설명한 Prediction(다음 토큰 예측) 과정을 자동으로 반복시켜 문장을 완성하는 엔진입니다."
- "LLM의 동작 원리를 이해하면 LLM을 단순한 채팅봇이 아닌, 프로그래밍 가능한 언어 인터페이스로 활용할 수 있습니다."
- "하나의 거대한 프롬프트로 모든 것을 해결하려 하지 마세요."
- "”JSON 형식 외에는 출력하지 마” 보다는 “반드시 RFC 8259 표준을 준수하는 JSON 형식으로만 출력해줘” 처럼 긍정적이고 명확한 지시가 더 좋은 결과를 낳습니다."
- "이는 Prediction(5단계)에서 모델이 선택할 단어의 범위를 효과적으로 좁혀줍니다."
- "이는 Loop(6단계) 과정을 사용자가 직접 제어하며 원하는 결과로 유도하는 효과를 발휘할 수 있습니다."
- "LLM을 사용하는 비전문가인 백엔드 개발자의 관점에서 작성된 것으로, 전문가의 시각과는 다를 수 있습니다."

## 우리 설계에 쓸 만한 점
- [추론] "복잡한 작업은 단계별로 분해"는 오케스트레이터가 요청을 기획, 제작, 검수 단계로 나눠 각 에이전트에 넘기는 근거로 쓸 수 있다. 원문은 한 사람의 프롬프트 분해를 말한 것이지 멀티에이전트를 말하지 않았다.
- [추론] 역할 부여 요령(Prediction 범위 축소)은 부서별 에이전트 시스템 프롬프트에 역할과 출력 언어/형식을 첫 줄에 고정하는 규칙으로 옮길 수 있다.
- [추론] 에이전트 간 전달물은 "반드시 RFC 8259 JSON으로만"처럼 긍정문 형식 지시로 강제하고, 검수 역할이 파싱 가능 여부를 확인하게 할 수 있다.
- [추론] "결과를 비판적으로 검토하고 구체적 피드백" 요령은 검수 에이전트가 틀린 지점을 명시해 제작 에이전트에 재요청하는 루프의 근거가 된다. 반복 횟수 상한은 원문에 없으므로 우리가 정해야 한다.
- [추론] Temperature 설명을 근거로 제작(마케팅 카피 등)은 상대적으로 높게, 검수와 문서관리, 운영 판단은 낮게 두는 역할별 샘플링 설정을 검토할 수 있다. 원문은 구체 권장값을 제시하지 않았다.
- [추론] 임베딩과 코사인 유사도 설명은 지식 저장소(문서관리 역할) 검색의 기본 원리로 참고할 수 있으나, RAG 설계 자체는 이 글에 없다.
- [추론] 구체적 콘텍스트(버전, 로그, 코드) 제공 요령은 운영/모니터링 에이전트가 장애를 넘길 때 필수 필드(버전, 에러 로그, 관련 코드)를 템플릿화하는 근거가 된다.
