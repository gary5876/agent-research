# 에이전트 구현 기본틀 — 01의 4요소를 임의의 agent에 적용 가능한 일반형으로

**Status:** ACTIVE
**Layer:** 2 (설계 — 01/07의 종합) — 층 구분 기준: [CATALOG.md](../CATALOG.md)

`00`에서 시작해 `07`까지 오는 동안, "에이전트 전문성"을 다루는 두 개의 서로 다른 어휘가 이 저장소 안에 따로 존재했다 — `01`의 4요소(정합적 data lake / 좁고 명시적인 인터페이스 / 안전한 응답 필터 / 실패 사례 기반 금지 규칙)와 `07`이 카카오페이 원문에서 가져온 Agent 정의(LLM/몸/Tools·Context·Skills) 및 능력 계층(Tool→MCP→Skill→Plugin→Marketplace). `07 §4`가 이미 이 둘을 대응관계로 연결해뒀었는데(`Tool→MCP→Skill→...`는 요소2의 어휘를 세분화한 것), 이 저장소 자신의 문서 카탈로그(CATALOG.md)를 설계하는 과정에서 그 사실을 놓치고 두 어휘를 별개 문제처럼 다루다가 같은 실수를 세 번 반복했다(§1 참고). 이 문서는 그 둘을 하나의 일반형으로 명시적으로 합친다.

## 핵심 한 문장

"전문성 있는 agent"는 `07`이 정의한 Agent 해부학(LLM+몸, Tools/Context/Skills) 위에 `01`의 4요소를 얹은 것이다 — 둘은 경쟁하는 프레임워크가 아니라 같은 결론의 다른 단면이다.

## 1. 이 문서가 나오게 된 계기 — 같은 실수의 3회 반복

이 저장소 자신의 문서 카탈로그(`CATALOG.md`)를 신뢰성 있게 만들려던 시도가 매번 "일반형 없이 즉흥적으로 설계"해서 실패했다:

1. 문서마다 Layer(1~4)를 매기는 표를 `CATALOG.md`에 손으로 작성 → 문서 자신의 태그와 별도 파일에 같은 사실이 두 벌 존재하는 구조가 됨
2. 그 어긋남을 감지하려고 해시 검증 시스템(line-range sha256)을 추가 → 비평 검토 결과 "관계를 끊은 게 아니라 형태만 바꿔 반복"이라고 확인되어 폐기
3. `write-docs` 스킬 초안에서 "예외 구간을 헤딩 번호(§)로 명시하라"는 새 규칙을 씀 → 실제 문서(`06`)의 예외 구간이 헤딩 경계를 넘어가서 그 규칙 자체가 성립 불가능한 걸 발견

세 번 다 "지금 당장 이 문제만" 해결하려다 이미 이 저장소에 있던 상위 원칙(`01`의 4요소, `07`의 Agent 해부학)을 참조하지 않고 매번 새 개념을 발명한 게 원인이었다. 아래는 그 상위 원칙을 하나로 합친 것 — **agent-research 자신에게 적용하는 건 이 문서의 범위가 아니다**(§3 참고).

## 2. 에이전트 구현 기본틀

### 2-1. Agent 해부학 (`07` §1-1/§1-1a 인용)

> **LLM("머리")**: 입력을 받아 출력을 내는 함수. 상태(State)가 없다. 스스로 정보를 검색하거나 파일을 수정할 수 없고, 직접 실행할 수 없다.
> **Agent("몸")**: 목표만 주면 알아서 계획을 짜고, 필요한 도구를 써서, 처음부터 끝까지 업무를 완수하는 AI 일꾼. 목표를 하위 작업으로 쪼개고, 도구를 호출하고, 결과를 관찰해서 다음 행동을 결정하는 걸 반복한다(ReAct: 추리→행동→관찰→재추리).

몸(런타임)이 매 루프마다 조작하는 손잡이는 셋: **Tools**(외부 시스템 접근용 단일 함수), **Context**(무엇을 넣고 무엇을 버릴지), **Skills**(도구를 어떤 순서로 쓸지 담은 매뉴얼, Progressive Disclosure 3단계로 로드).

### 2-2. "전문성"을 얹는 자리 — `01`의 4요소를 세 손잡이에 배치

| Agent 손잡이 | `01`의 요소 | 일반형 정의 (특정 agent나 도메인에 무관) |
|---|---|---|
| Context의 재료 | 요소1: 정합적인 data lake | 지식 단위 하나하나가 **자기 분류 정보를 스스로 지님** — 별도 인덱스가 대신 기억하지 않는다. 그 지식 전체의 경계(무엇이 이 lake 안이고 밖인지)가 명시돼 있다 |
| Skills | 요소2: 좁고 명시적인 인터페이스 | data lake에 접근하는 통로는 **정해진 몇 개의 이름 붙은 동작**으로 고정한다(자유서술 매뉴얼이 아니다). 최소 두 방향(넣는 동작·찾는 동작)이 **같은 지식 단위 정의를 공유**해야 한다 — 하나가 정의하고 다른 하나가 따르는 게 아니라, 정의 자체가 하나뿐이어야 한다 |
| Skills가 내놓는 응답 | 요소3: 안전한 응답 필터 | 인터페이스가 뭔가 반환할 때 **원본과 파생물을 구분**하고, 원본이 항상 우선한다는 규칙을 갖는다. 파생물/생성물을 원본인 것처럼 인용하지 않는다 |
| 위 셋을 계속 옳게 유지하는 힘 | 요소4: 실패 사례 기반 금지 규칙 | **내용이 아니라 절차만 일반형이다** — 실패 사례는 agent마다, 도메인마다 다르기 때문이다. 절차: "실패가 실제로 발생 → 왜 틀렸는지 한 줄로 진단 → Never 규칙 한 줄로 축적." 목록 자체는 각 agent가 자기 사고 이력에서 채운다(예: `data-lake/amoro-analysis`가 확인한 Iceberg AGENTS.md의 58,000개+ PR 리뷰 코멘트 역추출 사례) |

`07 §4`가 이미 확인했듯, 카카오페이의 `Tool→MCP→Skill→Plugin→Marketplace` 능력 계층은 이 표의 "Skills(요소2)" 칸을 더 세분화한 어휘일 뿐이다 — 별도 프레임워크가 아니다.

## 3. 이 문서의 범위 — 일반형까지만

이 문서는 **스키마**만 정의한다. `agent-research` 저장소 자신을 이 스키마의 Context(data lake)로 놓고, `CATALOG.md`/`write-docs`/`find-docs` 스킬을 이 스키마의 Skills(요소2) 칸에 실제로 채워 넣는 작업은 **다음 문서(09번, 아직 미작성)의 몫**이다. 이번에 그것까지 같이 하려다가 §1의 실패가 반복됐다 — 스키마와 인스턴스를 같은 문서에서 동시에 설계하지 않는다.
