## 1. 무엇이고 왜 인기인가

- 코딩 에이전트용 "개발 방법론"을 스킬 묶음으로 만든 것. 만든 사람은 Jesse Vincent(Prime Radiant). MIT, 스타 약 29.2만(2026-09-29 gh api), 최신 v6.4.2(2026-09-25). Claude Code 공식 마켓플레이스, Codex, Cursor, Gemini CLI 등 10여 개 도구에 들어간다.
- 인기 이유(README 요지): 설치만 하면 스킬이 자동으로 켜져서 에이전트가 바로 코드부터 짜지 않고, 먼저 무엇을 원하는지 묻고, 설계를 끊어서 보여주고, 계획을 세운 뒤, 태스크마다 새 하위 에이전트로 구현하고 리뷰한다. README는 "몇 시간씩 계획에서 벗어나지 않고 자율로 일하는 경우가 드물지 않다"고 쓴다.
- 핵심 철학(README): 테스트 먼저, 추측보다 절차, 단순함, **주장보다 증거**.

## 2. 요청 하나가 들어와서 끝날 때까지

한 화면 그림: [../diagrams/superpowers-flow.png](../diagrams/superpowers-flow.png)

1. **brainstorming**: 코드 전에 요청을 분류(탐색, 소규모, 설계급)하고, 질문은 한 번에 하나, 접근법 2~3개를 비교하고, 설계를 절 단위로 보여주며 매번 승인받는다. 설계급이면 설계 문서를 저장한다. 승인 전에는 구현 행동 금지(HARD-GATE).
2. **using-git-worktrees**: 격리된 작업 공간(새 브랜치)을 만든다. main 브랜치에서 사람 동의 없이 구현 금지.
3. **writing-plans**: 설계를 2~5분짜리 단계로 쪼갠 계획을 쓴다. 태스크마다 정확한 파일 경로, 주고받는 인터페이스(무엇을 쓰고 무엇을 만드는지), 실패하는 테스트, 최소 구현, 검증 명령, 커밋. "TBD", "적절한 에러 처리 추가", "Task N과 비슷" 같은 빈칸 문구는 계획 실패로 규정.
4. **subagent-driven-development(SDD)**: 메인 세션이 컨트롤러가 되어 태스크마다 새 구현 에이전트를 띄우고, 태스크마다 리뷰하고, 끝에 브랜치 전체 리뷰.
5. **finishing-a-development-branch**: 테스트 확인 후 병합, PR, 보관, 폐기 중 사람이 고른다.

## 3. 마스터(컨트롤러)가 하는 일 (SDD 기준)

**컨트롤러는 직접 구현하지 않는다.** "리뷰에서 나온 문제도 컨트롤러가 직접 고치지 않는다. 컨트롤러의 컨텍스트는 조율용으로 깨끗하게 두고, 컨트롤러가 고치면 리뷰를 건너뛰게 된다."

| 하는 일 | 방식 |
|---|---|
| 착수 전 계획 검사 | 태스크끼리, 태스크와 전역 제약이 모순되는지 **표로** 검사해 기록. "검사 결과 깨끗함"만 쓰고 행을 안 채우면 검사를 안 한 것으로 본다 |
| 위임 | 태스크 본문을 별도 파일(brief)로 뽑아 경로만 넘긴다. 지시문에는 5가지만: 프로젝트 안에서의 위치 한 줄, brief 경로, 이전 태스크의 인터페이스, 애매한 점에 대한 결정, 보고 파일 경로. 이전 태스크 요약을 붙이지 않는다(실제 세션에서 지시문 4.2만 자 중 99%가 붙여 넣은 이력이었음) |
| 상태 관리 | 계획별 **장부 파일**(`.superpowers/sdd/<계획>/progress.md`). 대화 기억은 압축되면 사라지므로 장부와 git log를 믿는다. 장부 없이 자기 위치를 잃은 컨트롤러가 이미 끝난 태스크를 통째로 다시 돌린 것이 "관찰된 가장 비싼 실패" |
| 결과 회수 | 구현 에이전트는 전체 보고를 파일에 쓰고, 컨트롤러에게는 15줄 이하(상태 4종: 완료, 우려 있는 완료, 막힘, 정보 부족 / 커밋 / 테스트 한 줄 / 우려)만 돌려준다 |
| 완료 판정 | 에이전트의 "성공" 보고가 아니라 git diff와 리뷰 결과로 판정 |
| 모델 배정 | 역할마다 모델을 명시. 생략하면 가장 비싼 세션 모델을 조용히 물려받는다 |

**실행 중 애매함은 묻지 않고 결정한다("Rulings, not stalls").** 계획 충돌, 모호함, 계획 결함이 나오면 컨트롤러가 결정하고 장부에 `결정 / 이유 / 틀렸을 때의 비용`을 남기고 진행한다. 멈추는 경우는 딱 4가지: 되돌릴 수 없거나 파괴적인 행동, 보안에 민감한 행동, 작업 공간 밖에 영향이 가는 행동(병합, 공유 브랜치 push, 게시), 모든 길이 추측뿐일 만큼 망가진 계획. 끝나면 자기가 사람 대신 내린 결정을 **전부** "Rulings I made" 목록으로 보여준다. 도입 배경 `[재확인]`: 컨트롤러가 스스로 정할 수 있었던 질문 하나에 막혀 한 세션이 거의 9시간 멈춤(릴리스 노트, #2077).

## 4. 위험 검증: 잘못된 결과와 폭주를 어떻게 잡나

- **리뷰 관문**: 태스크마다 새 리뷰 에이전트가 두 가지 판정(명세 준수, 코드 품질)을 모두 내야 통과. 구현자의 자기 리뷰는 리뷰를 대신하지 못한다.
- **리뷰어는 보고를 믿지 않는다**: 리뷰 지시문에 "구현자의 보고를 검증되지 않은 주장으로 취급하라. 'YAGNI라서 남겨뒀다' 같은 이유도 자기 채점이다."
- **리뷰 결과를 미리 깎지 않는다**: 컨트롤러가 리뷰어에게 "이건 지적하지 마"라고 쓰면 그 자체를 금지 신호로 규정.
- **수정 루프 상한(차단기)**: 태스크당 최대 5라운드. 1~3라운드는 같은 구현자에게 이어서 고치게 하고, 4~5라운드는 더 강한 모델의 새 구현자. 5라운드 후에도 남으면 컨트롤러가 항목마다 판정해 장부에 기록. "한 라운드만 더 하면 된다"는 핑계를 명시적으로 막는다.
- **완료 전 검증 법칙**: "새로 돌린 검증 결과 없이 완료를 주장하지 않는다." "~일 것이다", "아마" 같은 말, 검증 전 "완료!"를 위험 신호로 규정.
- **하위 에이전트가 또 하위 에이전트를 부르지 못하게**: 구현자가 스스로 리뷰어를 띄우면 같은 리뷰를 두 번 돈다. 실제 세션에서 그랬기 때문에 금지.
- 한계: 이 통제의 대부분은 **스킬 문서(프롬프트)**다. 도구 호출을 막는 Hook은 없다. 개발자들은 지침이 세션 도중 무너지는 걸 측정할 때마다 일부를 스크립트로 옮겼다(모델 명시 필수, diff를 파일로, 계획별 장부, 빈 리뷰 범위 거부). 자세한 변천은 design-history 문서.

## 5. 비용: 어디서 쓰고 어떻게 줄였나

- 토큰을 가장 많이 쓰는 곳은 컨트롤러다(run 비용의 약 절반, design-history). 그래서 지시문에 이력을 붙이지 않고, 산출물은 파일로 주고받고, 리뷰어에게 테스트를 다시 돌리지 말라고 하고, 같은 모양의 작은 태스크는 한 번에 묶는다.
- 역할별 모델 등급: 계획에 코드가 다 적혀 있는 받아쓰기형 구현은 가장 싼 모델, 여러 파일 통합은 표준 모델, 설계와 최종 리뷰는 가장 강한 모델. 단 "턴 수가 토큰 단가를 이긴다": 가장 싼 모델은 여러 단계 일에서 턴을 2~3배 써서 오히려 비싸다.
- **리뷰를 싼 모델에 맡기면 안 된다** `[재확인]`: haiku 리뷰어는 심어 둔 결함 10개 중 0개를 올바른 심각도로 지적했다(strict-cost 설계 문서).
- 측정치 `[재확인]`: 태스크 단위 리뷰로 바꾼 뒤 한 예제에서 기준 64.9분, 2,120만 토큰, $16.07이 54.1~54.7분, 1,440만~1,660만 토큰, $12.81~14.31로. 메인테이너 자체 측정이다.
- 사용자 불만의 중심도 비용과 속도(이슈 #743, #1152 5시간 한도 소진, #2057 요청 하나에 9시간). design-history 문서.

## 6. 보안

- 설치되는 Hook은 **세션 시작 1개**뿐. 로컬 스킬 파일 하나를 읽어 컨텍스트에 넣는 일만 하고, 네트워크 접근이나 도구 호출마다 도는 Hook은 없다 `[재확인]`. 다른 오케스트레이터(모든 도구 호출에 Hook, 권한 우회 기본값)와 비교하면 표면이 작다.
- 되돌릴 수 없는 행동, 보안 민감 행동, 병합과 push와 게시는 사람에게 묻는다(3절 4가지). main 브랜치 직접 구현 금지.
- 약점(design-history): 브레인스토밍용 시각화 서버는 v6.0.0 전까지 인증이 없어서 다른 localhost 페이지가 이벤트를 주입할 수 있었고, 에이전트는 그걸 사용자 입력으로 읽었다. 이후 강화됨. Windows Hook 실행기의 경로 문제는 dev 브랜치에서 수정 중.

## 7. 가져올 것 (우리 마스터 설계에)

1. **장부 파일**: 상태는 대화가 아니라 파일에. 첫 줄에 어느 계획의 장부인지 적어서 다른 계획의 장부와 섞이지 않게. 압축 뒤에는 장부와 git을 믿는다.
2. **위임 지시문 5요소 + brief 파일**: 요구사항은 파일 하나가 유일한 원본, 지시문에는 경로와 결정만.
3. **보고 계약**: 상태 4종, 짧은 반환, 상세는 파일.
4. **리뷰어 원칙**: 보고를 믿지 않는다, 결과를 미리 깎지 않는다, 리뷰는 싼 모델에 맡기지 않는다.
5. **수정 차단기**: 5라운드, 4라운드부터 새 에이전트와 강한 모델, 이후 판정은 기록.
6. **착수 전 모순 검사를 표로**: 사용자가 정한 "실행 전 모순 해결"과 같은 방향.
7. **모델 명시 필수**: 생략 시 비싼 모델을 물려받는 조용한 비용 누수를 구조로 막음.

## 사용자 결정과 충돌하는 지점 (판단 필요)

사용자 결정(2026-09-28): 실행 중 새 모호함이 생기면 멈추고 다시 묻는다. superpowers는 반대로 실행 중에는 **4가지 외에는 묻지 않고** 컨트롤러가 결정하고 기록한다. 근거는 "틀린 결정은 사람이 보고 되돌릴 수 있는 재작업이지만, 질문에 멈춘 세션은 하루를 통째로 버린다"와 실제 9시간 정지 사례. 대신 모든 결정을 비용과 함께 기록하고 끝에 전부 보여준다. 어느 쪽을 택할지, 또는 섞을지(예: 명세의 의도에 관한 모호함은 멈추고, 구현 세부의 모호함은 결정 후 기록)는 설계 절에서 정한다.
