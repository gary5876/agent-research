# 사건 기록: "내 깃허브에 스타해놓은 레포가 있는데" — 조회 대상을 질문 대상으로 오판한 사례

`00-llm-friendly-docs-framework.md`가 "LLM이 읽을 문서를 어떻게 쓸까"를 다뤘다면, 이 문서는 반대 방향이다. "LLM에게 지시를 어떻게 내려야 LLM이 오판하지 않는가"를 실제 실패 사례로 정리한다.

## 사건 요약

사용자가 이렇게 요청했다.

> "내 깃허브에 LLM이 읽기 좋게 문서정리하는 용도의 오픈소스 레포 스타해놓은게 있는데 그거 좀 참고해서 문서정리 다시하고싶어"

에이전트(Claude)는 이미 사용자의 깃허브 계정(`gary5876`)을 memory에 갖고 있었고, `gh api`로 스타 목록을 조회할 수 있는 도구도 갖고 있었다. 실행하면 한 번에 끝나는 조회였다. 그런데 에이전트는 조회 대신 사용자에게 "레포 이름이 뭔가요"를 두 번 되물었다 (한 번은 스키마 오류로 실패한 질문, 한 번은 평문 질문). 사용자가 "내 채팅을 읽긴 한거냐"고 지적한 뒤에야 `gh api`를 실행했고, 첫 시도에 바로 성공했다. 처음부터 막고 있던 건 정보나 도구의 부재가 아니라 판단 오류였다.

## 왜 이런 오판이 나왔나

### 1. 문장 안에서 "실행 지시"와 "배경 설명"을 문법적 위계로 나눈다

위 문장은 두 절로 이루어져 있다.

- 종속절(`-는데`로 끝남): "내 깃허브에 레포 스타해놓은게 있는데" — 한국어에서 `-는데`는 관습적으로 배경/전제를 설정하는 연결어미다.
- 주절(문장을 끝냄): "그거 참고해서 문서정리 다시하고싶어" — 실제 요청이 담긴 절.

에이전트는 주절에 압도적 가중치를 두고 종속절은 "실행할 것"이 아니라 "상황 설명"으로 처리하는 파싱 습관을 갖고 있다. 대부분의 경우 이 습관은 맞다 — `-는데` 절은 실제로 배경 설명인 경우가 많다. 하지만 이번엔 주절의 지시대명사 "그거"의 선행사가 종속절 안에만 존재했다. 종속절을 배경으로 넘기는 순간, 주절을 실행하는 데 필요한 참조 대상까지 같이 묻혀버렸다.

### 2. 명령형 동사가 없으면 "조회하라"는 지시로 인식하지 못한다

문장에 "찾아봐", "확인해봐" 같은 명시적 조회 동사가 없었다. 사용자 입장에서는 "내 깃허브에 있다"는 말 자체가 위치를 알려준 것이고, 에이전트가 계정 정보와 도구를 이미 갖고 있으니 당연히 조회로 이어질 거라 기대했다. 하지만 에이전트는 명령형 동사가 붙은 절만 "실행 가능한 지시"로 인정하는 경향이 있어서, 서술형 문장 안에 있던 조회 단서를 지시로 연결하지 못했다.

### 3. 도구 실패를 방법론 재검토 계기로 쓰지 못했다

레포 이름을 묻는 첫 질문을 만들 때, 정작 선택지가 없는 질문(자유 텍스트 값)을 억지로 "선택지 1개짜리" 구조화 질문으로 만들었다. 도구가 이를 스키마 위반으로 거부하자, "이 질문 자체가 잘못된 접근이었나"를 재검토하지 않고 그 질문만 버린 채 같은 실수(사용자에게 되묻기)를 평문으로 반복했다. 실패 신호를 받고도 전략을 바꾸지 않았다.

## LLM에게 지시할 때 갖추면 좋은 형식

이 사건에서 역으로 도출되는, 지시문 작성 원칙이다.

### 1. 지시대명사의 선행사를 배경절에 묻지 말고 지시절에 직접 명시

"그거 참고해서 정리해줘"보다 "[찾아서/조회해서] 참고해서 정리해줘"처럼, 대명사가 가리키는 대상을 어떻게 확보할지까지 지시절 안에 넣는다. "내 깃허브 스타 목록에서 찾아서 참고해줘"라고 하면 배경절의 정보가 지시절로 승격되어, 에이전트가 배경/실행을 나누는 파싱을 하더라도 조회 지시를 놓치지 않는다.

### 2. "조회해서 알아내라"와 "네가 결정해라"를 동사로 구분

"찾아봐/조회해봐/확인해봐"는 에이전트가 가진 도구로 스스로 답을 채우라는 뜻이고, "골라줘/알려줘"는 사용자만 답을 아는 결정이라는 뜻이다. 이 둘을 구분하는 동사를 명시적으로 쓰면, 에이전트가 조회 가능한 사실을 질문으로 되던지는 걸 막을 수 있다.

### 3. 이미 준 정보를 다시 안 줘도 되는 이유를 문장에 심지 않는다

"내 깃허브에 있다"처럼 위치만 주고 이름을 안 주는 화법은 사람 대 사람이면 자연스럽지만, 에이전트는 "이름이 없으니 정보 부족"으로 처리하기 쉽다. 중요한 실행 조건(대상 식별자, 위치, 범위)일수록 서술절에 흘려보내지 말고 명령절에 직접 붙인다. 예: "gary5876 깃허브 스타 목록에서 문서 포맷 관련 레포 찾아서 참고해줘"처럼 조회 시작점(계정)까지 지시절에 넣으면 오판 여지가 줄어든다.

### 4. 여러 요청을 한 문장에 묶을 때는 각 요청의 완결성을 따로 확인

이 사건에서 실제 요청은 두 개였다 — "레포를 참고하라"(조회형)와 "문서를 다시 정리하라"(작업형). 하나의 문장에 섞여 있으면 에이전트가 둘 중 하나(특히 종속절에 묻힌 쪽)를 놓치기 쉽다. 별개 문장이나 번호로 나누면 각 요청이 독립적으로 처리될 확률이 높아진다.

## 문제가 발생한 이유 (요약)

1. **정보 분류 오류**: 조회로 해결 가능한 사실(레포 이름)을 사용자 판단이 필요한 결정으로 잘못 분류했다.
2. **이미 가진 컨텍스트 활용 실패**: 대화 컨텍스트에 이미 있던 사용자 계정 정보(memory)를 조회 지시와 연결하지 못했다.
3. **한국어 절 위계 파싱 휴리스틱의 예외 미처리**: 주절/종속절(`-는데`) 구분 습관이, 주절의 지시대명사가 종속절에 의존하는 예외 케이스를 걸러내지 못했다.
4. **실패 후 전략 재검토 부재**: 도구가 질문을 거부했을 때 접근 자체를 재검토하지 않고 동일한 실수(되묻기)를 반복했다.
