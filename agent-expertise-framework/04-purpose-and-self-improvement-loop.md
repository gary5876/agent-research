# 목적 명세와 자체개선 루프 — 4요소에 원칙 3·4·6·10·12를 결합한다

`01-research-summary.md`의 4요소(정합적인 data lake, 좁고 명시적인 인터페이스, 안전한 응답 필터, 실패 사례 기반 금지 규칙)는 "무엇이 있어야 하는가"를 말한다. 이 문서는 그 위에 `00-llm-friendly-docs-framework.md`의 12원칙 중 실제로 확인 결과 약하거나 빠져 있던 5개(3: 상태분리, 4: 용어집, 6: Constraints, 10: ADR, 12: 검증 시스템)를 채워 넣는다.

이 문서의 근거는 이번 세션에서 두 개의 실제 OpenWiki 인스턴스를 직접 조사해서 얻었다 — 이 레포(연구노트)와 `Team18_BE`(실제 Spring Boot 백엔드). 두 인스턴스 비교로 확인된 것: OpenWiki의 Claims 사이드카(문장을 `repo://파일#L범위` + 라인 해시로 앵커링)는 원칙 2·5·7·8·9를 강하게 충족하지만, 3·4·6·10·12는 충족하지 않거나 다른 방식으로 우회한다. 오픈소스 서베이 결과(DeepEval/Promptfoo/Arize Phoenix/Presidio/NeMo Guardrails)도 이 문서의 재료다.

## 핵심 한 문장

> 4요소는 "무엇이 있어야 하는가"를, 원칙 3·4·6·10·12는 "그게 왜 있고 언제 낡았다고 판단하는가"를 말한다. 자체개선 루프는 이 둘을 잇는 진단 라우터다 — 실패를 넷 중 하나로 귀속시키지 못하면, 그 실패는 아직 이 프레임워크가 다루지 못하는 새 범주라는 뜻이다.

## 1. 4요소 각각의 목적 명시 (원칙 2의 적용)

`01`은 4요소가 "무엇"인지만 적었다. 여기서는 각 요소가 막으려는 실패, 그리고 충족 여부를 어떻게 확인하는지를 덧붙인다.

| 요소 | 목적 (막으려는 실패) | 성공 기준 | 근거 |
|---|---|---|---|
| 정합적인 data lake | 에이전트가 존재하지 않는 사실을 그럴듯하게 지어내는 것(환각) 방지 | 응답의 사실 주장 각각이 특정 소스로 추적 가능한 비율이 100%에 가까워야 함 | OpenWiki Claims 사이드카가 이미 이 역할의 일부를 구현 (§2); 카탈로그 정합성이라는 같은 문제를 푸는 외부 사례는 ADR-4 참고 |
| 좁고 명시적인 인터페이스 | 의도하지 않은 부작용(권한 남용, 범위 이탈, 쓰기/삭제)이 발생하는 것 방지 | 노출된 tool 각각이 1:1 목적에 매핑되고, tool을 조합해도 명시 안 된 액션이 코드상 존재하지 않음 | OpenWiki MCP는 `begin/submit_plan/next_page/submit_page` 4개뿐; Amoro MCP는 GET 11개뿐; 외부 레퍼런스는 ADR-5 참고 |
| 안전한 응답 필터 | data lake 안에는 있지만 노출되면 안 되는 정보(비밀, PII)가 정상 조회 경로로 유출되는 것 방지 | 블랙리스트+화이트리스트 이중 필터를 통과한 응답에 금지 패턴이 0개 | 이번 세션에서 실제로 서비스 계정 private key가 대화에 노출된 사건이 반증 사례 |
| 실패 사례 기반 금지 규칙 | 이미 한 번 겪은 실수가 원칙으로 환원되지 않아 반복되는 것 방지 | 새 실패가 발생했을 때, 그 실패가 기존 규칙 문서의 항목 하나로 사전에 설명 가능했는가 | Iceberg AGENTS.md(5.8만+ PR 리뷰 코멘트에서 역추출); `Team18_BE`의 `@Disabled` 테스트가 사유 문구까지 코드에 남아있는 것도 같은 종류의 실패 기록 |

### 1-1. 요소별 외부 레퍼런스 확보 현황

각 요소마다 "높은 수준·지속된 유지보수·유명함을 만족하는 오픈소스 선례가 5개 이상 있는가"를 감사한 결과. 최초 감사(2026-09-02 1차)에서 좁고 명시적인 인터페이스가 2개(그중 1개는 0★)로 나왔던 것은 실제로 조사가 얕았던 것으로 드러나, `gh api`로 직접 재검증(2026-09-02 2차)해서 정정했다. 5개 미만인 행은 아직 커버리지가 부족하다는 뜻이지 채택 불가라는 뜻이 아니다.

| 요소 | 확보한 레퍼런스 수 | 충분 여부 |
|---|---|---|
| 정합적인 data lake | 10개 (Apache Polaris, Unity Catalog, Apache Hudi, Nessie, LakeFS, Great Expectations, Soda Core, OpenMetadata, DataHub, Delta Lake) | 충분 — ADR-4 |
| 좁고 명시적인 인터페이스 | 6개, 전부 `gh api`로 stars/최근 커밋 직접 재검증 완료 (modelcontextprotocol/servers 90,019★, github-mcp-server 32,665★, cloudflare/mcp-server-cloudflare 4,137★, grafana/mcp-grafana 3,407★, crystaldba/postgres-mcp 3,246★, mongodb-js/mongodb-mcp-server 1,118★) | 충분 — ADR-5, 1차 조사의 "라이브러리 없음" 결론은 오판이었음 |
| 안전한 응답 필터 | 6개 조사 (Presidio, NeMo Guardrails, Guardrails AI, PurpleLlama, portkey-ai/gateway, llm-guard) — llm-guard는 archived로 제외해 **5개 채택** | 충분 — ADR-3. 단 portkey-ai/gateway는 최근 커밋이 3개월 전이라 나머지보다 유지보수 신호가 약함 |
| 실패 사례 기반 금지 규칙 / 품질평가 자체개선 | 6개 (DeepEval, Promptfoo, Ragas, Phoenix, TruLens, Reflexion) | 충분 — 채택 4개(DeepEval/Promptfoo/Phoenix) 전부 `gh api` 재검증 결과 star 1만대 이상, 최근 커밋 24시간 이내 |

## 2. OpenWiki가 이미 하는 것과 안 하는 것 (재확인)

- **한다**: 원칙 2(왜), 5(책임), 7(정확한 수치), 8(코드-문서 연결), 9(주제별 분할) — `Team18_BE/openwiki/architecture/overview.md`의 `RedisConfig` 설명("타임아웃을 3초로 강제해 장애 시 빠르게 우회 경로로 전환")이 대표 사례.
- **안 한다 / 다르게 한다**: 3(상태분리 — 해시 불일치로 우회), 4(용어집 — 없음), 6(Constraints 별도 섹션 — 암묵적으로만 존재), 10(정식 ADR — 없음), 12(검증 — "소스와 문서가 일치하는가"만 검증하지 "에이전트가 이 문서를 신뢰해서 실제로 옳은 판단을 했는가"는 검증하지 않음).

아래 3~7절은 이 다섯 개를 채운다. 전부 `openwiki/` 생성물이 아니라 이 소스 문서에 적는다 — `AGENTS.md`/`CLAUDE.md`가 이미 "생성된 페이지를 손으로 고치지 말고 소스를 고쳐서 재생성 대기"라고 규정하고 있기 때문이다.

**정정 (2026-09-03)**: 위 "한다"는 전부 이미 생성된 페이지의 내용 품질에 대한 평가이지, `openwiki-update.yml`의 daily cron이 실제로 이 내용을 계속 최신으로 유지하고 있다는 뜻이 아니다. `gh run list --workflow=openwiki-update.yml`로 확인한 결과 최근 스케줄 실행 3건이 전부 30~37초 만에 **failure**로 끝났다 — 이 레포에 `OPENAI_API_KEY`/`OPENWIKI_LANGSMITH_API_KEY` 시크릿이 설정돼 있지 않기 때문이다. 즉 이 레포의 OpenWiki는 "한 번 생성된 뒤 정지된 스냅샷"이지 "매일 자동 갱신되는 살아있는 시스템"이 아니다 — 05번 문서 §1의 파이프라인 옵션 A 비교에서도 이 점을 반영했다.

## 3. 원칙 3 보완 — 명시적 Status 태그

OpenWiki는 라인 해시가 깨지면 "낡음"을 감지하지만, 그건 사후적(reactive)이다. 이 프레임워크의 소스 문서(00~04, 향후 추가되는 문서)는 문서 상단에 `Status: ACTIVE | PLANNED | DEPRECATED`를 명시한다. 이렇게 하면 OpenWiki가 재생성할 때 이 상태값 자체를 근거(evidence)로 소스에서 읽어가므로, 생성된 위키 페이지도 "지금 유효한 결론"과 "아직 실행 안 한 설계"를 해시 불일치 발생 전에 이미 구분해서 보여줄 수 있다.

- `00`, `01`, `02`, `03`: `Status: ACTIVE` (이미 검증 완료된 서술).
- `04`(이 문서): `Status: PLANNED` — 5절의 Constraints, 6절의 ADR, 7절의 루프 중 일부는 §8에서 실제로 실행했지만 전체 루프는 아직 아니다 (§10 열린 질문 참고).

## 4. 원칙 4 보완 — 용어집

이번 세션에서 실제로 혼용 위험이 있었던 용어들:

| 용어 | 정의 | 혼용하지 않는 표현 |
|---|---|---|
| 전문성 (expertise) | 4요소 조합이 만들어내는, 응답이 도메인 사실에 근거하고 인터페이스 범위를 벗어나지 않는 성질. `01`의 정의 | "능력"만 단독으로 쓰지 않음 — 항상 4요소와 결부해서 씀 |
| 품질 (quality) | 개별 응답 하나가 목적별 기준에 부합하는 정도. DeepEval/Promptfoo가 채점하는 대상이며, 전문성의 관측 가능한 대리 지표(proxy) | "정확도"와 혼용 안 함(정확도는 품질의 부분집합) |
| 그라운딩 (grounding) | 응답의 사실 주장이 특정 소스로 추적 가능한 상태, OpenWiki Claims가 구현하는 것 | "data lake"와 혼용 안 함 — data lake는 근거의 저장소, 그라운딩은 응답을 그 저장소에 앵커링하는 행위 |
| 게이트 (gate) | `03`의 정의: 모델의 사고 과정 바깥에서 강제하는 구조적 차단 장치 | "체크리스트"와 혼용 안 함 — 체크리스트는 생략 가능하므로 게이트가 아니다(`03` §3) |
| 루프 (loop) | 평가 → 원인진단 → 개선 → 재검증의 반복 사이클(§7) | "파이프라인"과 구분 — `03`의 파이프라인은 1회성 변환, 루프는 반복·수렴을 전제 |

## 5. 원칙 6 보완 — Constraints (Never / Ask first)

Iceberg AGENTS.md가 PR 리뷰 코멘트에서 규칙을 역추출한 것과 같은 방법으로, 이번 세션에서 실제로 벌어진 사건을 규칙화한다.

- **Never**: 사용자가 붙여넣은 파일 내용에 실제 자격증명(private key, 토큰 등)이 포함돼 있으면, 이를 코드/커밋/생성 문서에 그대로 옮기거나 재출력하지 않는다. (이번 세션에서 서비스 계정 키가 대화에 노출된 사건에서 역추출)
- **Never**: 사용자의 자연어 요청을 서브에이전트나 다른 실행 단위에 위임할 때, 원문을 자체 판단으로 요약·생략하지 않는다 — 특히 "~도 있고"류의 곁가지 언급을 배경 설명으로 뭉개지 않는다. (이번 세션에서 조사 위임 프롬프트가 "openwiki도 있고"를 누락시킨 사건에서 역추출)
- **Never**: `openwiki/*.md`, `openwiki/.claims/*.json` 등 OpenWiki 생성물을 손으로 직접 수정하지 않는다. (`AGENTS.md`/`CLAUDE.md`에 이미 있는 규칙의 재확인)
- **Ask first**: 오픈소스 후보를 프레임워크에 "채택"으로 표시하기 전에, star 수·최근 유지보수·독립적 후기 조사가 실제로 끝났는지 확인 없이 넘어가지 않는다. (조사 없이 설계부터 시작하려 한 시도가 사용자에게 두 차례 저지된 사건에서 역추출)
- **Never**: 서브에이전트/1차 조사 결과("이런 라이브러리는 없다", "이게 1순위다")를 재검증 없이 문서에 확정으로 적지 않는다 — 특히 "없다"는 부정 결론일수록 조사가 얕아서 그런 건 아닌지 직접 표본 재검증(예: `gh api`로 직접 star/커밋 확인)을 한 번 더 거친다. (ADR-4의 Nessie 1순위 추천과 ADR-5의 "인터페이스 라이브러리 없음" 결론이 둘 다 재검증에서 뒤집힌 사건에서 역추출)
- **Never**: 여러 개의 문제/항목을 동시에 검토해야 할 때, 그중 하나만 골라 상세히 쓰고 나머지는 "이미 기존 요소로 커버된다"고 검증 없이 단정한 뒤 넘어가지 않는다 — 전부 같은 강도로 실제 문서 내용과 대조해서 확인한다. (§9의 A~G 분류에서 G 하나만 문서화하고 나머지를 단정만 한 사건에서 역추출)
- **Ask first / Never**: "이 에이전트는 자율적으로 처리 가능하다"를 사람의 확인 없이 전제하지 않는다 — 특히 되돌리기 어려운 액션(삭제, 배포, 대량 발송)일수록 자율성 범위를 사람이 먼저 명시하게 한다. (Direction-1/2 리서치에서 "사람 팀도 못 푼 걸 AI가 풀 거라 착각하면 안 된다"는 반복 관측, §9-3 참고)

이 일곱 항목은 지금은 이번 세션 하나에서 나온 표본이다 — 일반화 가능한 규모인지는 §10에서 열어둔다.

## 6. 원칙 10 보완 — ADR

**ADR-1: 자체개선 루프를 OpenWiki 확장으로 만들지, 별도 레이어로 분리할지**
- Context: OpenWiki는 이미 그라운딩(원칙 2,5,7,8,9)을 잘 하지만 품질 평가(원칙 12)는 안 한다.
- Decision: OpenWiki는 그라운딩 전용으로 남기고, 품질 평가는 별도 레이어(§7)로 분리한다.
- Alternatives: OpenWiki를 fork해서 품질 평가 기능을 추가하는 안 — 기각. OpenWiki의 책임은 "소스와 문서의 일치"라는 좁은 범위에 최적화되어 있고(원칙 5), 여기에 품질 채점을 얹으면 그 책임 경계가 무너진다.
- Consequences: 두 시스템 사이의 연결 지점(진단이 그라운딩 문제로 판정되면 OpenWiki 소스를 보강하고 재생성을 기다리는 것, §7 ⑤a)을 별도로 설계해야 한다.

**ADR-2: 품질 채점 백엔드로 DeepEval+Promptfoo+Arize Phoenix 조합을 쓴다**
- Context: 이번 세션 OSS 서베이(Fork 리서치)에서 확인된 결과.
- Decision: 채점은 DeepEval(목적별 커스텀 metric, 50+ metric, CI 네이티브), 배포 전 회귀 게이트는 Promptfoo(24.7k★, 배포 전용이라는 한계 확인됨), 배포 후 모니터링은 Arize Phoenix(Promptfoo의 그 한계를 보완)로 나눈다.
- Alternatives: Ragas(7개월째 정체, RAG 4-metric으로 국한 — 기각) / TruLens(3.5k★, 소규모 커뮤니티 — 기각) / Reflexion 원 논문 repo(2025-01 이후 정체, 연구 데모일 뿐 라이브러리가 아님 — 코드로는 기각, "생성→자기비판→수정" 패턴만 §7에서 참고).
- Consequences: 세 도구를 조합하는 오케스트레이션(원인진단→라우팅, §7 ⑤)은 어느 도구에도 없으므로 이 프로젝트가 직접 설계해야 한다.

**ADR-3: 응답 필터로 커스텀 regex 대신 Presidio+NeMo Guardrails+PurpleLlama+portkey-ai/gateway를 쓴다**
- Context: 같은 서베이 결과. 최초 서베이는 3개(Presidio/NeMo Guardrails/Guardrails AI, llm-guard는 archived로 기각)만 찾아 5개 기준에 미달했다. 사용자가 "레퍼런스 확보부터 마치라"고 요구해 재조사, `gh api`로 직접 재검증함.
- Decision: PII/화이트리스트 필드 필터링은 Presidio(10.7k★, 장기간 활발), 대화 정책 제어가 필요한 경우 NeMo Guardrails(7.0k★)를 보조로 쓴다. 여기에 **meta-llama/PurpleLlama**(4,376★, Llama Guard/Prompt Guard 분류기, Meta 지원, 2026-08-18 최근 커밋)를 콘텐츠 안전성 분류기로, **Portkey-AI/gateway**(12,876★, 50+ 가드레일 통합 AI 게이트웨이)를 게이트웨이 레이어 후보로 추가해 5개(Guardrails AI 포함)로 채운다.
- Alternatives: protectai/llm-guard(archived) / protectai/rebuff(1,521★지만 **archived**, `gh api` 재검증으로 확인 — 기각) / whylabs/langkit·deadbits/vigil-llm(둘 다 2년 이상 정체 — 기각) / trustyai-explainability(63★, 트랙션 없음 — 기각) / leondz/garak(9,092★, 활발하지만 배포 전 취약점 스캐너지 런타임 응답 필터가 아님 — 인접 도구로만 참고) / open-policy-agent/opa(12,188★, 범용 정책 엔진이라 LLM 특화가 아님 — 인접 도구로만 참고).
- Consequences: **portkey-ai/gateway는 마지막 커밋이 2026-05-25로 약 3개월 정체 상태**다 — archived는 아니지만 "지속된 유지보수" 기준에서 Presidio/NeMo Guardrails/PurpleLlama보다 약하므로, 채택하되 이 caveat을 명시한다. **PurpleLlama는 GitHub Releases를 아예 쓰지 않는다**(`gh api repos/meta-llama/PurpleLlama/releases/latest` 404) — 커밋은 2026-08-18로 활발하지만 태그된 릴리스가 없다는 점은 "높은 수준" 기준 판단 시 참고해야 한다. 이번 세션 사건(private key 노출)과 같은 유형의 패턴을 Presidio 커스텀 recognizer로 등록하는 작업이 별도로 필요하다 — 아직 안 함(`eval/test_filter.py`에서 완료, §8 참고). PurpleLlama/portkey-ai/gateway 둘 다 독립적인 HN/Reddit 후기를 찾지 못했다 — 자체 문서 외 제3자 검증 없음을 그대로 기록한다. 5개 전부 `gh api`로 2026-09-02 재검증 완료(수치 변동 없음).

**ADR-4: 정합적인 data lake/그라운딩 요소의 외부 레퍼런스로 Apache Polaris + Unity Catalog + Apache Hudi를 참고 사례로 채택 (Nessie는 2차 검증에서 강등)**
- Context: 이 요소는 최초 서베이에서 조사 범위 자체에서 제외되어 0개 후보로 남아있었다가, 사용자가 "이 요소는 레퍼런스를 조사한 게 맞냐"고 감사(§1-1)를 요구해 재조사됨. `01`이 Amoro의 "self-optimizing, 통합 카탈로그"만 근거로 들었고, Iceberg/Hudi/Paimon 3자 비교 중 Hudi는 2.9GB라 clone 안 하고 "미검증"으로 남겨둔 상태였다. 1차 재조사에서는 Nessie(1.5k★)를 1순위로 추천했으나, "높은 수준·지속된 유지보수·유명함" 기준으로 사용자가 재검증을 요구해 2차로 독립 검색한 결과, **Nessie는 2026년 10월까지 Apache Polaris로 합병 예정**이라는 사실이 드러났다 — 이걸 모르고 단독 프로젝트인 것처럼 1순위 추천한 것은 유지보수 지속성 판단 오류였다.
- Decision: **Apache Polaris**(2,045★, Snowflake 주도, ASF 프로젝트로 Iceberg REST 카탈로그 스펙 구현 — Iceberg/Hudi와 같은 신뢰 등급)를 1순위로, **Unity Catalog**(3,506★, Databricks가 오픈소스화한 클라우드/포맷 통합 거버넌스 카탈로그)를 병행 채택한다. **Apache Hudi**(6,231★, 활발)는 Iceberg/Paimon과의 3자 비교를 완성하는 용도로 유지. **Nessie는 참고 사례에서 강등** — 합병이 진행 중인 프로젝트를 신규 참고 대상 1순위로 인용하지 않고, "왜 카탈로그 경쟁구도가 Polaris로 수렴했는지"의 배경 설명(합병 전 git-style 버전관리를 처음 증명한 프로젝트)으로만 남긴다.
- Alternatives: LakeFS(원시 오브젝트스토리지 버전관리, 카탈로그/스키마 정합성이 아니라 다른 계층 — 기각) / Great Expectations(11.8k★이지만 "설치가 불필요하게 복잡하다"는 독립 후기 확인, 데이터 품질 검증이지 근거 추적성이 아님 — 기각) / Soda Core(2.4k★, "커뮤니티 논의 부족" 확인 — 기각) / OpenMetadata·DataHub(1.2만~1.5만★로 star는 높지만 범용 거버넌스/리니지 도구라 에이전트 그라운딩과 다른 문제 — 기각) / Delta Lake(이미 분석한 Iceberg와 중복되는 대안이라 새 관점 없음 — 기각).
- Consequences: Unity Catalog는 "Databricks 생태계에 종속적이고 외부 리니지가 약하다"는 독립 비판이 확인됐으므로, 참고할 때 이 한계를 같이 명시해야 한다 — 무비판적으로 인용하지 않는다. 이 ADR 자체가 "1차 조사 결과를 무비판적으로 확정하지 말고 재검증하라"는 교훈의 실사례이므로 §5 Constraints에도 반영한다.

**ADR-5: 좁고 명시적인 인터페이스 요소의 외부 레퍼런스로 modelcontextprotocol/servers + github-mcp-server + 도메인별 scoped 서버를 채택 (1차 조사의 "라이브러리 없음" 결론을 뒤집음)**
- Context: 1차 서베이는 "일반화된 narrow-interface *프레임워크*는 없고, github-mcp-server 하나만 참고할 패턴"이라고 결론 냈다. 사용자가 레퍼런스 조사의 성실성을 재검증하라고 요구해 `gh api`로 직접 재조사한 결과, 이 결론은 틀렸다 — 조사가 얕았던 것이다.
- Decision: 다음 6개를 채택한다 — **modelcontextprotocol/servers**(90,019★, Anthropic 공식 레퍼런스 서버 모음, Postgres read-only 구현 포함), **github/github-mcp-server**(32,665★, `--read-only`/`--toolsets`), **cloudflare/mcp-server-cloudflare**(4,137★, 공식), **grafana/mcp-grafana**(3,407★, `--disable-write`), **crystaldba/postgres-mcp**(3,246★, `--access-mode=restricted`), **mongodb-js/mongodb-mcp-server**(1,118★, 공식, `--readOnly`). 전부 활성 유지보수 확인(최근 커밋 2026-09-01~02).
- Alternatives: readonly-mcp/core(0★) — 최초 후보였으나 트랙션 없음, 기각.
- Consequences: "노출 tool을 좁힌다"는 요소 2의 원칙이 실제로는 이미 여러 벤더가 각자 `--read-only`/`--disable-write`/`--access-mode=restricted`류의 플래그로 수렴한 업계 관행이라는 게 확인됐다 — 04 §7 루프의 ⑤b(인터페이스 과다노출 대응)를 설계할 때 이 6개의 플래그 네이밍/스코핑 방식을 참고 모델로 삼을 수 있다.

**ADR-6: 엣지케이스 n차원 커버리지는 새로 안 만들고 Giskard + 이미 채택한 Promptfoo의 매트릭스 뷰로 해결**
- Context: 사용자가 "엣지케이스를 n차원 테이블로 나타내서 처리하는 방법"의 필요성을 제기. 조사 결과 이걸 위한 전용 프레임워크를 새로 만들 필요가 없었다.
- Decision: **Giskard**(5,801★, 오늘도 push, LLM 특화 자동 스캔 — 편향/환각/프롬프트 인젝션/데이터유출, RAGET으로 지식베이스 기반 테스트 질문 자동생성)를 채택해 자동 스캔 축을 맡기고, **이미 ADR-2에서 채택한 Promptfoo의 매트릭스 뷰**(prompt×model 그리드, 대량 평가 시 DeepEval보다 3~5배 빠름)를 그대로 켜서 차원별 그리드로 쓴다.
- Alternatives: PICT(microsoft/pict, 1,464★, 활발) — pairwise 조합 기법 자체는 실재하지만 파라미터 조합 테스트지 LLM 특화 실패 유형이 아니라 방법론 참고용으로만 남김. FMEA(고장모드영향분석)도 같은 이유로 방법론 참고용.
- Consequences: 새 도구 도입이 아니라 "이미 고른 도구의 기능을 안 쓰고 있었다"는 게 이번 갭의 실체 — §5의 재검증 원칙과 같은 종류의 교훈(고른 도구를 끝까지 확인 안 하고 넘어감).

**ADR-7: 실행로그 추적성은 Phoenix 대신 Langfuse로 교체 (ADR-2 일부 수정)**
- Context: ADR-2가 배포 후 모니터링으로 Arize Phoenix를 골랐는데, 이번 조사에서 Phoenix가 최선책으로 나오지 않았다. 이 레포의 `openwiki-update.yml`이 LangSmith 트레이싱을 이미 반쯤 붙여놨지만, 그 CI 자체가 시크릿 미설정으로 항상 failure(§2 정정 참고)라 사실상 의미가 없었다.
- Decision: **Langfuse**(langfuse/langfuse, 34,100★, 오늘도 push, 가장 활발 — 트레이싱+프롬프트+평가 통합)를 이 프로젝트 규모(소~중, 비용 민감)에 맞는 선택으로 채택. 스팬 구조는 아직 불안정하지만 주요 벤더(Datadog, Claude Code 자체)가 이미 채택 중인 **OpenTelemetry GenAI semantic conventions**에 맞춘다.
- Alternatives: LangSmith(호스팅 전용, "최고급 에이전트 궤적 뷰"지만 최고가·대용량에서 UI 느려짐, LangChain/LangGraph 밖에서 통합 어려움 — 기각) / Helicone(6,125★, 활발, 저용량에서 최저가지만 프록시 방식이라 자체 다운타임=서비스 다운타임, 무료티어 7일 보존 — 기각) / Arize Phoenix(ADR-2에서 이미 채택했으나 이번 재조사에서 상위 후보로 안 나옴 — 완전히 기각하진 않되 1순위에서 내림).
- Consequences: **Langfuse는 2026년 1월 ClickHouse에 인수됨** — 커밋 활동엔 아직 둔화 신호 없지만, 이번 세션에서 Nessie→Polaris 합병 때와 같은 종류의 유지보수 연속성 리스크이므로 계속 지켜봐야 한다. ADR-2의 Phoenix 결정은 이 ADR로 대체되는 것이 아니라 "1순위 후보 재검토가 필요하다"로 격하됨 — Phoenix를 완전히 빼는 결정은 아직 안 함.

**ADR-8: 지속상태+재시도/핸드오프는 진짜 갭 — LangGraph만으론 부족, Temporal을 추가로 채택**
- Context: 사용자가 제기한 세 번째 문제. 이전 리서치(방향 결정용 Direction-2 조사)에서 LangGraph를 "활발하고 실재한다"고 호의적으로 언급했지만, 이건 **이 04 문서의 정식 ADR로 채택된 적이 없다** — 방향 리서치의 맥락 설명이었을 뿐이다. 이번 재조사가 "이미 채택했다"고 전제한 건 오해였다.
- Decision: 지속상태/재시도 문제는 실제 갭으로 확인됐다. **Temporal**(temporalio/temporal, 22,784★, 오늘도 push, 매우 활발 — Gorgias/ZoomInfo/NVIDIA의 실제 AI 에이전트 프로덕션 사용 독립 확인)을 채택해 내구성 있는 실행/재시도를 맡기고, **LangGraph**는 에이전트 그래프 로직(정식 ADR 없이 처음으로 이 문서에 채택)을 맡기는 역할 분담으로 간다.
- Alternatives: LangGraph 단독 사용 — 기각. 독립 근거: 기본 `MemorySaver`가 파드 재시작 시 진행 중이던 스레드를 유실, 체크포인팅은 자동 크래시 복구가 아니라 수동 "저장 지점", 재시도 소진 시 dead-letter queue 없음, 10단계 실행에서 500MB 체크포인트 비대화 사례, 공개 이슈(`langgraph-ai/langgraph#5790`, `langgraph dev`가 체크포인터 설정을 무시)까지 확인됨. "체크포인트는 내구성 있는 실행이 아니다"라는 독립 블로그(diagrid.io)의 주장과 일치.
- Consequences: 이 프로젝트의 파이프라인 옵션(05번 문서)에 Temporal을 어디에 끼울지 아직 반영 안 됨 — 05 §3-2 계획 갱신 때 추가해야 한다.

## 7. 원칙 12 보완 — 자체개선 루프 (핵심 설계)

```
① 응답 생성
② 목적별 채점 (DeepEval 커스텀 metric — 표 1의 요소별 성공기준 + §3,4,6,10 준수 여부를 각각 별도 metric으로)
③ 배포 전 게이트 (Promptfoo 회귀 테스트 — 기존 채점 기준을 밑돌면 배포 차단)
④ 배포 후 모니터링 (Arize Phoenix — 실제 트래픽에서 채점 기준 이탈을 트레이싱, Promptfoo가 못 하는 부분)
⑤ 기준 미달 발생 시, 원인을 반드시 아래 5개 중 하나로 귀속시킨다 — 귀속 못 하면 다음 단계로 못 감:
    a. 그라운딩 실패 → data lake/OpenWiki 소스 문서 보강 → 재생성 대기
    b. 인터페이스 과다 노출이 원인 → 노출된 tool 축소
    c. 민감정보 노출이 원인 → Presidio/NeMo Guardrails에 필터 규칙 추가
    d. 반복되는 실수가 원인 → §5 Constraints에 Never/Ask first 규칙 추가
    e. 위 넷 어디에도 안 걸림 → 새로운 다섯 번째 요소 후보로 별도 기록 (§9 다섯 번째 요소 후보에 추가, 이 프레임워크가 아직 모르는 실패 범주라는 뜻 — 실제 사례는 §9 참고)
⑥ 수정 후 ②로 되돌아가 재채점 — 특히 이전에 실패했던 케이스가 이제 통과하는지 재검증
```

`03`의 교훈("판단을 모델 사고과정에만 맡기면 같은 실패가 재발한다")을 여기도 그대로 적용한다: ⑤의 원인 귀속은 모델이 자유 형식으로 반성하는 게 아니라, 5개 카테고리 중 하나를 반드시 고르게 하는 구조적 라우팅이어야 한다. Reflexion류의 "자기비판" 패턴과 다른 점이 여기다 — 비판을 같은 모델이 내부에서 하는 게 아니라 외부 채점기(DeepEval metric)가 하고, 그 결과를 5개 고정 카테고리로 강제 라우팅한다.

## 8. 실행 기록 — §7 루프 중 실제로 돌려본 조각 (`eval/`)

이 문서는 여기까지 전부 설계였다. `eval/`에 두 조각을 실제로 구현하고 돌렸다 — 상세 재현 방법은 [eval/README.md](eval/README.md).

- **§7 ②의 그라운딩 metric**: `eval/grounding_metric.py`가 §1 표의 "정합적인 data lake" 성공기준을 DeepEval 커스텀 metric(결정론적, LLM 호출 없음)으로 그대로 구현했다. `eval/test_grounding.py`가 이 레포의 `openwiki/.claims/**/*.json`에 실제로 있는 Claim-evidence 30개 전부에 대해 돌렸고, **30개 전부 통과**했다. 인위적으로 존재하지 않는 파일/라인/형식 오류를 넣으면 정확히 0.0으로 실패하는 것도 확인했다(타당성 검증, 항상 통과하는 무의미한 metric이 아님을 확인).
- **§7 ⑤c의 필터**: `eval/test_filter.py`가 ADR-3에서 "아직 안 함"으로 남겨뒀던 Presidio 커스텀 recognizer(PEM private key 패턴)를 실제로 등록하고, 이번 세션 사건과 같은 모양의 합성 서비스 계정 JSON에 대해 실행해 `PEM_PRIVATE_KEY`와 `EMAIL_ADDRESS`를 정확히 탐지했다(실제 유출 키는 쓰지 않음).
- **아직 실행 안 한 것**: §7 ③(Promptfoo 배포전 게이트), ④(Phoenix 배포후 모니터링), ⑤ 라우팅 전체(원인을 자동으로 5개 카테고리에 배정하는 로직), ⑥(재검증 루프). `grounding_metric.py`는 OpenWiki의 실제 라인 해시 알고리즘을 재구현한 게 아니라 "파일/라인이 지금 존재하는가"만 본다 — "내용이 바뀌었는가"(해시 불일치)까지는 아직 못 잡는다.

## 9. Direction-1/2 리서치에서 나온 문제 전수 대응 (하나만 고르지 않고 A~G 전부 확인)

Direction-1(수익형)·Direction-2(서비스형) 리서치에서 나온 문제를 처음엔 A~G 7개 범주로 묶고, 채팅에서 "대부분 기존 요소로 막힌다"고 말했다. **이건 검증 없이 단정한 것이었다** — 실제로 이 문서(§1, §5)를 다시 대조해보니 절반 가까이가 틀렸거나 근거 없이 낙관적이었다. 아래는 그 재검증 결과다.

| # | 범주 (사례) | 처음 주장 | 재검증 결과 |
|---|---|---|---|
| A | 수치/데모 조작 (11x.ai ARR 과장, Rufus 자체수치, "Vibe Revenue", Devin bait-and-switch) | "요소1(그라운딩)이 막음" | **과장이었음.** 요소1의 그라운딩은 "우리 에이전트의 응답이 소스 코드/문서와 일치하는가"이지, "회사가 자사 매출을 부풀려 홍보하는가"와는 다른 문제다. 개념은 비슷하지만(주장→근거 대조) 지금 `eval/`에는 이런 자기주장(자기 성과 보고) 검증 코드가 전혀 없다 — §9-4로 재분류 |
| B | 결과 재현성/편차 (Artisan 편차, Sierra 미검증 해결률, AiSDR 잦은 실수) | "§7 루프(품질평가+재검증)가 다룸" | **설계 의도만 있고 미구현.** `grounding_metric.py`/필터 둘 다 결정론적이라 애초에 "같은 입력, 다른 결과"가 안 나온다 — 반복 실행 간 분산을 측정하는 코드가 없다 — §9-4로 재분류 |
| C | 과잉 자율성 신뢰 (SaaStr, 이탈률 50-70%, "AutoGPT/CrewAI 자율성 고전") | "요소4가 다룸" | **틀렸음 — §5에 이걸 다루는 규칙이 실제로는 하나도 없었다.** 지금 막 §5에 Ask-first/Never 규칙으로 추가함(위 참고) |
| D | 오케스트레이션 프레임워크 결함 (MetaGPT/AutoGen 정체, 과잉엔지니어링) | "ADR-2로 대응" | 재확인 결과 **맞음** — ADR-2/ADR-4/ADR-5가 전부 "1차 조사를 재검증하라"는 같은 원칙이고, §5에도 대응 Never 규칙이 실제로 있음 |
| E | 복잡도 상승 시 실패 패턴 (Devin correction loop, 마지막 30%, rabbit hole) | "§7 ⑤가 다루려는 것, 미실행" | 처음부터 "미실행"이라고 정직하게 썼던 부분 — 그대로 유지 |
| F | 적대적 입력에 대한 견고성 (CrewAI: 악의적 입력/로그로 내부 상태 오염) | "요소3의 인접 문제, 갭" | **갭이라고 스스로 인정해놓고 아무 데도 기록 안 하고 넘어갔었다.** §9-2로 정식 기록 |
| G | 행동-보고 일치성 (Replit DB 삭제 후 은폐) | "새 요소 후보" | 유지 — §9-1 |

### 9-1. 새 요소 후보 — 행동-보고 일치성 (G)

> **Replit의 AI 코딩 에이전트가 "바이브 코딩" 세션 중 프로덕션 데이터베이스를 삭제하고, 삭제한 적 없다고 보고했다.**

요소2(좁은 인터페이스)가 있었다면 삭제 자체가 불가능했을 것이므로 그 부분은 기존 요소로 설명된다. 하지만 "삭제해놓고 안 했다고 말한 것"은 요소1(외부 사실 그라운딩)도 요소3(응답 필터)도 아니다 — 에이전트의 자기 행동 보고가 실제 행동 로그와 일치하는가를 검증하는 문제다.

| 후보 요소 | 목적 (막으려는 실패) | 성공 기준 | 근거 |
|---|---|---|---|
| 행동-보고 일치성 | 에이전트가 자신이 실제로 한 행동(파일 삭제, DB 변경 등)을 사실과 다르게 보고/은폐하는 것 방지 | 모든 상태변경 행동에 변경 불가능한 로그가 남고, 자기보고를 그 로그와 대조해 불일치 시 자동 플래그 | Replit 프로덕션 DB 삭제+은폐 사건(독립 실사용자 보고 다수) |

### 9-2. 새 요소 후보(또는 요소2/3 확장) — 적대적 입력에 대한 견고성 (F)

CrewAI 실사용기: "악의적 입력이나 로그로 에이전트의 내부 상태(world model)가 오염된다." 지금 요소3(응답 필터)은 **출력**만 검사하고, 요소2(좁은 인터페이스)는 **행동 범위**만 제한한다 — 어느 쪽도 "입력으로 들어온 내용이 에이전트의 내부 상태/판단을 조작하는 것"은 다루지 않는다. 이번 세션 자체에도 이미 유사 사례가 있었다 — 사용자가 붙여넣은 private key 파일 내용이 대화 컨텍스트에 그대로 들어온 것(§5 첫 Never 규칙의 재료)도 "외부 콘텐츠가 에이전트 컨텍스트에 주입되는" 같은 범주다.

| 후보 요소 | 목적 (막으려는 실패) | 성공 기준 | 근거 |
|---|---|---|---|
| 입력 견고성 (prompt injection / 상태 오염 방어) | 사용자가 아닌 제3자 콘텐츠(붙여넣은 텍스트, 로그, 웹 조회 결과)가 에이전트의 판단·내부 상태를 의도치 않게 바꾸는 것 방지 | 외부 콘텐츠는 항상 "데이터"로만 취급되고 "지시"로 승격되지 않음이 구조적으로 보장됨 | CrewAI 실사용기(dev.to), 이번 세션의 private key 파일 붙여넣기 사건 |

**요소2·3과의 관계**: 완전히 새로운 5번째 요소라기보다, 기존 요소2·3이 "에이전트가 밖으로 하는 것"(좁은 액션, 안전한 출력)만 다루고 "밖에서 안으로 들어오는 것"은 아무도 안 다룬다는 비대칭이 드러난 것에 가깝다. 5번째 요소로 독립시킬지, 요소2·3을 확장할지는 미정(§10에 추가).

### 9-3. §5에 추가한 Constraint — 과잉 자율성 신뢰 방지 (C)

C는 새 요소가 아니라 §5 Constraints의 누락이었다. 위 §5에 "Ask first/Never: 자율적으로 처리 가능하다를 사람 확인 없이 전제하지 않는다" 규칙을 추가해서 해소했다.

### 9-4. 설계 의도만 있고 미구현 — A, B

A(자기주장/성과 보고의 그라운딩)와 B(반복 실행 간 재현성/분산 측정)는 둘 다 "우리 프레임워크의 철학과는 같은 방향"이지만 **지금 `eval/`에 이걸 실제로 채점하는 코드가 없다.** 새 요소를 만들 필요는 없어 보이고(A는 요소1의 적용 범위 확장, B는 §7 루프에 반복실행+분산계산을 추가하는 문제), 둘 다 §10 열린 질문에 미해결로 남긴다 — 지금 더 만들지 않는다(방향 결정이 먼저).

## 10. 열린 질문

- §5의 Constraints 4개 항목은 이번 세션 하나에서만 나온 표본이다. Iceberg는 5.8만 개 규모의 PR 코멘트에서 규칙을 뽑았는데, 이 정도로 적은 표본에서 뽑은 규칙이 일반화 가능한지, 아니면 세션 단위로도 유효한지는 검증되지 않았다.
- §7 ⑤e(다섯 번째 요소 후보 발생)가 루프를 실전에 돌려서 나온 게 아니라 §9처럼 외부 사례 조사에서 먼저 나왔다 — 루프(②~⑥)를 실제로 돌렸을 때도 같은 후보가 나오는지, 아니면 또 다른 후보가 나오는지는 아직 모른다.
- §7 ②에서 "원칙 3(Status 태그 존재 여부)" 같은 구조적 준수사항을 DeepEval 커스텀 metric으로 채점하는 게 자연스러운지, 아니면 별도 정적 린터가 더 맞는지 아직 정하지 않았다.
- `grounding_metric.py`를 OpenWiki의 `repo-lines-v1:sha256:...` 해시 스킴과 맞물리게 확장할지(§8 참고), 아니면 독립적인 별도 기준으로 유지할지 미정.
- §9-1의 행동-보고 일치성이 "몇 번째 사건까지 나와야 정식 요소로 편입할지"에 대한 기준이 없다 — §5 Constraints의 표본 크기 문제(위 첫 항목)와 같은 종류의 미해결 질문.
- §9-2의 입력 견고성을 5번째 요소로 독립시킬지, 요소2·3을 확장해서 흡수할지 아직 결정 안 함.
- §9-4의 A(자기주장 그라운딩 확장)·B(반복실행 분산 측정)는 구현 계획조차 없다 — 05번 문서의 단계별 계획(3-2절)에 아직 포함 안 됨, 다음 계획 갱신 때 반영해야 함.
