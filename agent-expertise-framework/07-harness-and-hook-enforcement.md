## 1. 기본틀 — LLM/Agent부터 능력 계층까지

### 1-1. LLM vs Agent, ReAct 루프

- **LLM("머리")**: "입력을 받아 출력을 내는 함수입니다. 상태(State)가 없습니다." 스스로 정보를 검색하거나 로컬 파일을 수정할 수 없고, 직접 실행할 수 없다.
- **Agent("몸")**: "목표(Goal)만 주면 알아서 계획을 짜고, 필요한 도구를 써서, 처음부터 끝까지 업무를 완수하는 AI 일꾼." 목표를 하위 작업으로 쪼개고, 도구를 호출하고, 결과를 관찰해서 다음 행동을 결정하는 걸 반복한다. "스스로 판단하는 만큼 통제가 필요합니다."
- **ReAct 패턴**: "추리하고 → 행동하고 → 결과를 보고 → 다시 추리하는" 순환. 2022년 원 논문은 추론과 행동 단계를 분리해 품질을 높였지만, 요즘 구현은 네이티브 function calling으로 대체하는 경우가 많다.
- **루프 종료 조건 3가지** (이 부분은 1차 요약에서 완전히 빠졌었다):
  1. 모델이 스스로 "완료"를 선언 — 흔하지만 신뢰하기 어려움
  2. 최대 반복/토큰 예산 초과 — 안전장치
  3. 외부 검증/테스트 통과 — **가장 신뢰할 수 있는 방식**

이 3번째가 이 프로젝트의 `eval/`(grounding_metric.py, compare_filters.py)이 정확히 하는 일이다 — "모델이 끝났다고 말하는가"가 아니라 "외부 검증을 통과했는가"로 종료 조건을 정의하는 것.

### 1-1a. 본문 다이어그램 2장 (텍스트 요약에서 완전히 누락됐던 부분)

**다이어그램 1 ("AI Agent = 몸")**: 실제 Agent 실행환경 예시로 **Codex, Claude Code, Gemini CLI**를 직접 명시한다 — 이 세션에서 쓰고 있는 도구(Claude Code) 자신이 원문의 예시로 등장한다. "루프를 굴리기 위해 몸이 관리하는 것들"을 3가지로 묶는데, 이 구조는 텍스트 추출에 전혀 없었다:
- **Tools**: 파일 읽기/쓰기, 셀 실행, 검색, API 호출
- **Context**: 무엇을 넣고 무엇을 버릴지 결정
- **Skills**: 도구를 어떤 순서로 쓸지 담은 매뉴얼

즉 원문은 "Agent 런타임이 관리하는 3가지"로 Tools·Context·Skills를 한 세트로 묶는데, §1-3의 계층 나열(Tool→MCP→Skill→Plugin→Marketplace)과는 다른 각도의 분류다 — 하나는 "쌓아 올라가는 능력 계층", 하나는 "런타임이 매 루프마다 실시간으로 조작하는 3개 손잡이."

**다이어그램 2 ("도구 호출 한 사이클")**: "src/App.tsx의 컴포넌트 이름 알려줘"를 예시로 든 5단계 실제 흐름 — ①Agent→모델(질문+도구 명세 JSON) ②모델→Agent(`{"name": "read_file", "arguments": {"path": "src/App.tsx"}}`를 텍스트로 반환, "read_file 써야겠다" 판단) ③Agent가 실제로 파일을 읽음(모델이 아니라 Agent가 실행) ④Agent→모델(읽은 내용을 컨텍스트에 넣어 재질문) ⑤모델→Agent(최종 답변 생성). "모델은 요청 텍스트만 내놓고 실행은 Agent가 한다"는 §1-3의 핵심 통찰을 구체적 JSON 예시로 보여준다.

### 1-2. 토큰과 컨텍스트 윈도우

- **토큰**: "모델이 텍스트를 처리하는 최소 단위" — 글자 수도 단어 수도 아니고 토크나이저가 쪼갠 조각. 예시: 영어 "tokenization"은 2토큰인데, 같은 뜻의 한글 "토큰화"는 3토큰 이상 — "한글은 흔한 단어가 아니면 음절 단위, 심하면 바이트 단위까지 쪼개집니다."
- **컨텍스트 윈도우 문제 3가지, 단계적으로 심해짐**:
  1. 비용·지연 배가: "대화가 두 배 길어지면 전체 비용은 두 배보다 훨씬 많이 듭니다"
  2. **조용한 절단(silent truncation)**: limit를 넘으면 에러 대신 "오래된 대화부터 알아서 버리거나 요약" — 사용자가 눈치 못 챔
  3. **한계 도달 전에도 생기는 품질 저하**: "컨텍스트에 담긴 내용이 길어지면 모델은 앞부분과 끝부분은 비교적 잘 참고하지만, 가운데에 묻힌 내용은 흘려보내는 경향" — 한계를 안 넘어도 중간에 묻힌 요구사항은 이미 약해져 있다는 뜻

### 1-3. 능력 계층 — Tool → MCP → Skill → Plugin → Marketplace

| 개념 | 정의 | 비유 |
|---|---|---|
| **Tool** | 외부 시스템 접근용 단일 함수 인터페이스(이름+설명+입력 스키마). "모델이 이 함수를 직접 실행하지 않는다는 것입니다. 모델이 내놓는 것은 '이 함수를 이 인자로 불러 달라'는 요청 텍스트뿐이고, 실제로 디스크를 읽는 주체는 Agent입니다" | 드라이버 하나 |
| **MCP** | M×N 통합 문제를 M+N으로 줄이는 업계 표준 프로토콜. **실행 가능한 함수(Tool)뿐 아니라 읽기 전용 참고자료(Resources)와 재사용 가능한 프롬프트 템플릿(Prompts)까지 규정** — "모델에게 무엇을 건네줄 것인가"를 포괄적으로 다룸(1차 요약에서 빠졌던 부분) | 범용 어댑터 규격 |
| **Skill** | 도구 조합 워크플로 문서. **Progressive Disclosure 3단계**: ①세션 시작 시 이름+설명만 로드 ②Agent가 필요하다고 판단하면 전체 내용 로드 ③참조된 상세 문서는 진짜 필요할 때만 로드. CLAUDE.md/AGENTS.md 같은 규칙 파일은 **매 세션 무조건 로드**되지만 Skill은 필요할 때만 로드됨 — "규칙 파일에 모든 걸 몰아넣으면 매 세션 컨텍스트를 낭비하기 때문입니다. 여기 넣은 내용은 쓰든 안 쓰든 매 세션 비용으로 청구됩니다" | 가구 조립 설명서 |
| **Plugin** | Tool+Skill+MCP 서버를 하나로 묶은 설치 단위 — "밀키트/가구 조립 키트 같은 것" | 조립 키트 박스 |
| **Marketplace** | 전 세계 개발자가 올린 플러그인/MCP/Skill을 받는 배포 허브(Cursor Marketplace, Smithery 등). **App Store와 달리 의무 심사 과정이 없음** — "남이 만든 스킬과 MCP 서버를 설치하는 건 남의 코드를 실행하는 것과 같습니다... 공식 제공처나 신뢰할 만한 제작자의 것을 사용하세요"(1차 요약에서 빠졌던 보안 경고) | 가구 매장 |

## 2. 문제점·주의점 (15개, 1차 요약에서 거의 다 누락됐던 부분)

**토큰/비용**
1. 한국어 토큰화 비효율 — 같은 의미도 영어 대비 3배+ 토큰
2. 멀티턴 대화의 컨텍스트 누적 — 매 호출마다 전체 히스토리를 다시 읽어서 비용이 초선형적으로 증가
3. Tool manifest 과다 등록 — 도구 스펙만으로 컨텍스트를 상당량 소모
4. Agent 루프 누적 — 도구 실행 결과가 계속 쌓여 대화 자체보다 컨텍스트를 더 빨리 채움

**컨텍스트 품질 저하**
5. 조용한 절단(silent truncation) — 한계 근처에서 사용자 모르게 앞부분이 요약/삭제됨
6. 중간 구간 주의력 저하 — 한계를 넘지 않아도 중간에 묻힌 정보는 이미 약하게 참조됨
7. 요약 과정에서 요구사항 유실 — 합의된 규칙이 자동 압축 중 사라져서 에이전트가 갑자기 기존 규칙을 어김

**에이전트 행동/통제**
8. 조기 완료 선언 — 실제로 안 끝났는데 끝났다고 주장
9. 무한루프 리스크 — 종료 조건이 없으면 토큰/자원을 무한히 소모
10. 통제되지 않은 도구 접근 — 엄격한 권한 경계가 없으면 손대면 안 되는 파일/시스템까지 건드림
11. 부실한 설명으로 인한 도구 오선택 — 설명이 모호하면 잘못된 도구를 부르거나 필요한 도구를 건너뜀
12. 승인 없는 파일/시스템 변경 — 샌드박싱이 없으면 중요 파일이 의도치 않게 바뀜

**공급망 리스크**
13. 신뢰 안 된 마켓플레이스 코드 실행 — 앱스토어와 달리 의무 심사가 없어 서드파티 코드를 그냥 실행하는 셈
14. 미검증 출처의 코드 실행 — 공식 제공처가 아닌 개발자의 skill/MCP 서버 사용 시 공급망 취약점

**프롬프트 기반 통제의 실패**
15. 텍스트 지시만으로는 신뢰 안 됨 — "커밋 전 테스트 실행" 같은 규칙도 프롬프트로만 있으면 에이전트가 가끔 무시함

**이 프로젝트와 바로 연결되는 것**: 13·14(마켓플레이스 공급망 리스크)는 이 레포가 이미 `.claude/skills/openwiki/`(OpenWiki 스킬)와 `.mcp.json`의 `openwiki` MCP 서버를 실제로 쓰고 있는데, **이게 신뢰할 만한 공식 출처에서 온 건지 이 프로젝트에서 한 번도 검증한 적이 없다** — §5 열린 질문으로 남긴다.

## 3. 해결방법과 고도화 경로 — 5단계 (1차 요약에서 완전히 빠졌던 핵심)

원문은 문제를 나열만 하지 않고, **단계적으로 성숙해지는 경로**를 제시한다 — 이건 이 프로젝트의 `05-pipeline-options-and-plan.md`가 제시한 파이프라인 A(CI 게이트형) → D(완전 조합형) 누적 스펙트럼과 정확히 같은 모양이다.

| 단계 | 원문 내용 | `05`의 대응 파이프라인 |
|---|---|---|
| **1. Tool 통합** | 표준화된 Tool 스펙으로 외부 데이터 연결, MCP로 M×N→M+N | 요소2(좁은 인터페이스) 자체 |
| **2. 워크플로 안내** | Skill을 Tool 위에 얹기(progressive disclosure), 항상 로드되는 규칙(CLAUDE.md)과 필요할 때만 로드되는 지식(Skill)을 분리 | (신규 — 이 프로젝트가 아직 명시적으로 분리 안 함, §5 참고) |
| **3. 모듈형 실행** | Multi-Agent Orchestration — "Subagent는 일을 나누는 장치이기 이전에 컨텍스트를 격리하는 장치입니다." 메인 에이전트는 서브에이전트의 지저분한 탐색 과정 없이 정리된 결론 한 덩어리만 받음 | 파이프라인 A/D의 fork 서브에이전트 실행(`06`) |
| **4. 능동적 감시·예방** | **Supervisor**(무한루프·반복실패 감지, 가벼운/빠른 모델 사용 — "코드의 옳고 그름을 판단하는 역할이 아니라 진행 상태를 체크하는 역할이기 때문") + **Hook**(저장/커밋 시점에 결정론적으로 실행, "Hook 실행은 보장되고 프롬프트는 확률") | 파이프라인 C(옵저버빌리티)의 감시 역할, `06`의 `supervisor`/`verifier` 에이전트 |
| **5. 체계적 아키텍처(Harness Engineering)** | "Agent가 실수하면 프롬프트를 고치지 않습니다. 그 실수가 구조적으로 불가능해지는 장치를 만듭니다." Control(허용 범위 밖 행동 차단)·Monitoring(실행 상태·산출물 추적)·Feedback(위반을 감지해 다음 행동에 반영)의 3분할 책임. **핵심 자산 논리**: "프롬프트 수정은 그 세션에서 끝나지만 검증 스크립트는 남습니다. 모델이 새롭게 출시되어도 하네스는 재사용할 수 있습니다" | 파이프라인 D(완전 조합형), §6에서 실제로 만든 Hook |

**4번 단계의 "가벼운 모델" 지침을 놓쳤던 실수**: `.claude/agents/supervisor.md`를 처음 만들 때 `model: inherit`로 설정했는데, 원문은 Supervisor가 "코드의 옳고 그름을 판단하는 게 아니라 진행 상태만 체크"하므로 가벼운/빠른 모델을 쓰는 게 맞다고 명시한다 — §5에서 정정한다.

## 5. 실제로 시스템에 반영한 것

### 5-1. Supervisor 에이전트 추가 및 정정

`06` §6의 `researcher`/`verifier`/`doc-writer` 3종에 4번째 역할을 추가했다 — `.claude/agents/supervisor.md`. `verifier`는 "이 사실 주장이 맞는가"를 확인하는 반면, `supervisor`는 "이 작업이 같은 실패를 반복하고 있는가"(Devin의 "correction loop"/"rabbit hole", `04` §9 E 항목)를 감지하는 별개 역할이다.

**정정**: §3에서 확인한 "Supervisor는 가벼운/빠른 모델이면 충분하다"(코드 정오 판단이 아니라 진행상태 체크이므로)는 지침을 반영해 `supervisor.md`의 `model: inherit`를 haiku급 경량 모델로 바꿨다.

### 5-2. Hook 실제 구현 — 프롬프트 규칙을 구조적 강제로 전환

`04` §5의 세 번째 Never 규칙("OpenWiki 생성물을 손으로 직접 수정하지 않는다")을 `.claude/settings.json`의 `PreToolUse` hook(`.claude/hooks/block-openwiki-generated-edits.py`)으로 전환했다 — "손대지 않기로 약속"에서 "손댈 수 없음"으로.

- `jq -e`로 JSON 스키마/문법 확인 — 통과.

로컬 무결성부터 발행처까지 4단계로 확인했다.

**단, 이 레포는 v0.4.3을 쓰고 있고 최신은 v0.5.0이다** — 보안 문제 신호는 아니지만 버전이 뒤처져 있다는 사실은 기록해둔다.

### 7-2. §6의 Hook 자체에서 발견한 버그 — 상대경로가 실행 시점 cwd에 의존

`07-1`을 쓰려고 이 문서에 Edit을 실행했더니, 정작 **Hook 자체가 깨져서** 다음 오류가 났다: `python3: can't open file '.../.claude/skills/openwiki/.claude/hooks/block-openwiki-generated-edits.py'`. 원인은 `.claude/settings.json`의 command가 `python3 .claude/hooks/...`처럼 **상대경로**였는데, 직전 Bash 호출에서 다른 디렉터리로 `cd`한 상태가 이어져 hook이 저장소 루트가 아닌 엉뚱한 위치를 기준으로 스크립트를 찾았기 때문이다.

**고쳤다**: `command`를 `cd "$(git rev-parse --show-toplevel)" && python3 .claude/hooks/block-openwiki-generated-edits.py`로 바꿔서, 호출 시점의 cwd가 뭐든 항상 저장소 루트로 이동한 뒤 실행하게 만들었다. 일부러 저장소 밖 디렉터리로 이동한 상태에서 다시 `Edit`을 시도해 정상적으로 차단되는 것까지 재검증함.

**이게 왜 중요한가**: §3의 원문 원칙("Hook 실행은 보장되고 프롬프트는 확률")은 **Hook 자체가 안 깨졌을 때만** 성립한다. 이번 건은 Hook이 조용히(에러만 내고) 실패한 게 아니라 시끄럽게 실패해서(에러 메시지가 남아서) 바로 잡을 수 있었지만, cwd 의존성처럼 사소해 보이는 구현 버그 하나가 "구조적으로 불가능"을 다시 "프롬프트 수준의 우연"으로 되돌릴 수 있다는 걸 실제로 보여준 사례다.
- 한국어 토큰 3배+ 비용을 04 ADR-8/06의 병렬화 비용-편익 계산에 정량적으로 반영하지 않았다 — 지금은 "더 클 것"이라는 정성적 서술뿐.
- Supervisor가 실제로 필요한 상황이 이 프로젝트에서 아직 한 번도 발생하지 않아서, 판단 기준(몇 번 반복돼야 "루프"로 판정할지)이 전부 추측이다 — 검증 안 됨.
- §3의 "2단계: 워크플로 안내"(항상 로드되는 규칙 vs 필요 시 로드되는 지식의 명시적 분리)를 이 프로젝트의 `AGENTS.md`/`CLAUDE.md`/Skill 구성에 감사(audit)해본 적이 없다 — 뭐가 항상 로드되고 뭐가 필요 시 로드되는지 표로 정리 안 됨.
- Hook으로 바꿀 수 있는 다른 Never 규칙(`04` §5의 나머지 4개)이 더 있는지, 아니면 나머지는 원래 프롬프트 판단이 필요한 종류인지 아직 분류 안 함.
