# 당신의 대출을 코치해줄 AI, 나만의 대출 코치 서비스 개발기

- URL: https://tech.kakaopay.com/post/building-ai-loan-coaching-service/
- 게시일: 2025-08-12 (페이지에 2025. 8. 26 날짜도 함께 표시됨, 수정일로 보임)
- 저자: casper.sj(서버 개발), zinna.h(UI/UX 디자인), ray.beam(프론트엔드), tasha.rive(대출 서비스 마케팅), peanut.s(대출 PM)
- 태그: 카페톤, AWS
- 소속: 카카오페이 CreditClan(대출 중개 서비스 팀)
- 리뷰어: jko.me

## 핵심 한 문장
대출 탐색을 "의향 분석, 자산 분석/대출 탐색, 결과 요약" 단계 상태기계로 나누고, Lambda가 단계별 프롬프트를 조립해 Bedrock Agent(상담사)에 넘기며, 특정 단계에서만 보조 Agent(자산분석 및 대출가능성, 선택지 생성)를 추가 호출하는 "단계별 싱글/멀티 에이전트" 구조.

## 배경과 문제
- 대출은 정보가 많고 복잡하며 금융 용어와 절차 때문에 사용자가 불안감을 느낌. 은행에서는 상담원 설명에 의존해 주체적으로 비교, 선택하기보다 정해진 가이드라인을 따라가게 됨.
- 생성형 AI에게는 "너무 당연한 질문이라 싫어하지 않을까" 같은 걱정 없이 질문할 수 있다는 점에 주목.
- 기대 효과 두 가지: (1) 상환방식, 우대조건 등 금융 용어를 쉽게 설명 (2) 사용자 목적과 조건에 맞는 대출 탐색 보조.
- 금융 분야라 할루시네이션이 치명적일 수 있다는 점을 처음부터 설계 조건으로 둠.

## 구조와 구성요소
- 아키텍처: 사용자 요청 -> AWS API Gateway -> AWS Lambda(핵심 서버 애플리케이션) -> AWS Bedrock(Agent) -> AWS S3(Knowledge Base 원천으로 보임). Lambda <-> AWS RDS(사용자 데이터).
- Lambda 함수는 API별로 나뉘고, 각각 "현재 단계에 맞는 적합한 답변 생성을 위한 프롬프트"를 구성. RDS의 사용자 데이터를 결합.
- 서버 코드는 Kotlin(스크린샷 기준): `QueryPromptGenerator.getPrompt(counselorType, userInput, status, asset)`, `getUserPurposePrompt(status: LoanCoachProgressStatus)`, 로그에 `AwsBedrockAgentLambdaClient`.
- 에이전트:
  - "상담사 Bedrock Agent": 기본 Agent. Knowledge Base + 답변 지침 + 페르소나 말투로 답변.
  - "자산분석 및 대출가능성 Agent": 상담사 Agent의 답변과 사용자 자산 정보를 바탕으로 대출 상품 추천. 자산 분석 및 대출 탐색 단계에서 두 Agent가 함께 답변 생성.
  - 보조 Agent(선택지 생성): 자산 분석, 대출 조회 결과 분석 단계일 때 사용자의 추가 선택지(options)를 생성. 원문은 "보조 Agent"라고만 부름.
  - 오케스트레이션 주체는 Bedrock Supervisor가 아니라 Lambda 코드(상태값 기반 분기). "사용자 상태에 따라 싱글 또는 멀티 에이전트 답변을 제공하는 구조".
- Knowledge Base: 기존 대출 서비스 운영에서 쓰던 기획 요건, FAQ, 대출 상품 정보를 문서화해 등록(대출 상품 설명, 한도 및 금리 산출 정보 등).
- 요청 스키마: `input_source`(USER_INPUT 등, 직접 입력인지 예시 선택지인지), `input_type`(TEXT, 음성 등), `status`(ANALYZE_LOAN_NEEDS 등 현재 단계), `counselor_type`(FRIENDLY 등 페르소나), `input`.
- 응답 스키마: `status`, `counselor_type`, `output.text`, `output.options[]`(text, type: ASK_MORE_INFO, ANALYZE_ASSETS 등).
- 상태값 예: ANALYZE_LOAN_NEEDS, READY_TO_INQUIRY_LOAN(스크린샷).
- 모델명: 원문에 없음.

## 절차와 규칙
- 사용자 여정 3단계:
  1. 대출 의향, 목적 분석
  2. 대출 상품 탐색 및 자산 분석(자산 정보로 승인 가능성 있는 상품과 금리, 한도 탐색)
  3. 탐색 결과 요약 및 맞춤 전략 제공(대출 실행 및 상환 계획 가이드)
- 모든 단계에서 음성/채팅으로 모르는 용어를 질문 가능. ChatGPT를 참고한 "답변 선택지"로 다음 단계 진행 또는 재시작.
- 선형 플로우이지만 언제든 이전 단계로 돌아갈 수 있고, 중간에 용어 질문을 할 수 있는 유연성이 필요 -> 단계별 API 분리, 각 API는 같은 사용자 입력을 받되 Bedrock에 넘기는 프롬프트는 단계별로 다르게 설계.
- Lambda 처리 순서: (1) 현재 상태에 따라 요청 처리기 선택 (2) 사용자 입력 + 현재 상태 + 페르소나로 프롬프트 구성해 Bedrock Agent 전달(사용자 입력을 그대로 넘기지 않음) (3) 답변 생성, 자산 분석/대출 조회 결과 단계면 보조 Agent 추가 호출해 선택지 생성 (4) 두 결과를 Lambda에서 조합해 반환.
- 프롬프트 조립 구조(스크린샷): `<답변에 대한 지침>` + "답변 말투에 대해서: {상담사 페르소나 프롬프트}" + {단계별 목적 프롬프트} + {단계별 예시 답변 <example>} + `<사용자 입력>` + {사용자 자산 입력}.
- 단계별 지침 예:
  - ANALYZE_LOAN_NEEDS: 상품명을 직접 추천하기보다 어떤 대출 종류가 이득인지 종합 판단, 금융/대출 목적 이외 질문은 정중히 거절.
  - READY_TO_INQUIRY_LOAN: 자산 정보로 승인 가능성 있는 대출을 찾고, 대략적인 DSR도 계산, 카카오페이에서 대출 비교 가능함을 강조하며 마무리, 시중은행(우리은행, 신한은행)에서 조회하는 방법보다 카카오페이 비교를 추천.
- 가드레일: Bedrock Agent의 "답변 지침"으로 주어진 정보 외 답변 금지. 주제 이탈 입력(예: "오늘 날씨 어때?")에는 "죄송하지만 대출 코치 서비스는 대출 및 금융 관련 질문만 답변 가능합니다." 식으로 통제.
- 페르소나: 시작 시 사용자가 코치 말투/성격을 선택(정중한, 친근한, 차분한, 유쾌한, 핵심만, 공감형, 이성적인, 따뜻한, 전문가, 경험자 등 스크린샷 기준). FRIENDLY 예: "당신은 사용자의 친구로써, 유쾌하고 편안하면서도 전문적인 금융 전문가입니다... 반말을 사용하되 너무 무례한 말투의 답변은 지양해주세요."

## 수치와 결과
- 개발 기간 1박 2일.
- 예시 입력: 비상금 500만 원.
- 스크린샷 속 예시 데이터(목업): DSR 29.1%(40% 이하 조건에 부합), 추정 연소득 5,500만원 등. 실제 성능 수치 아님.
- 정확도, 할루시네이션 감소율, 지연 등 평가 수치는 원문에 없음.

## 실패, 한계, 주의점
- 할루시네이션을 "최대한 예방하고자" 했다고만 쓰고, 측정 결과나 남은 실패 사례는 원문에 없음.
- "AI를 실제 서비스에 본격적으로 활용하려면 얼마나 많은 고민과 학습이 필요한지도 깨달았습니다."
- 선형 플로우와 자유 질문을 동시에 지원해야 하는 긴장이 가장 큰 설계 고민이었다고 명시.

## 그림 설명
- 01: 서비스 대표 이미지로 보임(내용 식별 생략, 장식성).
- 02: 상담사 캐릭터 "금리나(34세), 토마토저축은행 10년 근속, 이성적/분석적/현실적, 따뜻하고 차분한 말투와 쉬운 설명" 소개 화면. 장식성 강한 목업.
- 03: 6개 화면 플로우. 코치 말투 선택 칩 -> 캐릭터 소개 -> 첫 질문과 추천 답변 선택지 -> 500만원 대출 문의 및 자산 불러오기 -> 자산 표(연소득, 현금 자산, 보유대출, 카드, DSR)와 "가능한 대출 알아보기" 버튼 -> 코치 결과(상품별 금리, 한도, 특징 요약과 최적 상품 제시).
- 04 서비스 아키텍처: 사용자 요청 -> AWS API Gateway -> AWS Lambda -> AWS Bedrock, Bedrock -> AWS S3, Lambda -> AWS RDS.
- 05 시퀀스 다이어그램: User Client -> Lambda "답변 API 요청", Lambda -> Bedrock Agent "프롬프트 구성 후 전달", "답변 출력", Lambda -> Bedrock Agent "보조 Agent 필요시 호출", "보조 Agent 답변 출력", Lambda -> Client "답변 및 추가 선택지 응답".
- 06, 08: Kotlin `getUserPurposePrompt` 코드. 상태별 when 분기로 지침 문자열 반환(ANALYZE_LOAN_NEEDS, READY_TO_INQUIRY_LOAN).
- 07: `QueryPromptGenerator.getPrompt` 코드. 지침, 말투, 단계 목적, 예시, 사용자 입력, 자산을 이어 붙이는 템플릿.
- 09: 실제 호출 로그. 사용자 입력 "전세대출에 대해서 설명해줄래?"에 대해 조립된 프롬프트 전문(말투 지침, 단계 가이드, 금융 외 질문 거절, <example> 예시 답변)이 찍혀 있음.
- 10: 카카오페이 기존 신용대출 조회 결과 화면(연계 대상 화면).

## 원문 인용
1. "사용자의 요청을 전달받은 Lambda 함수는 다음과 같은 동작을 수행합니다."
2. "각각의 Lambda 함수는 정해진 API 동작을 수행하며, 현재 단계에 맞는 적합한 답변 생성을 위한 프롬프트를 구성합니다."
3. "나만의 대출 코치를 개발하면서 가장 고민했던 점은, 서비스의 플로우 설계가 의향 분석, 자산 분석, 대출 탐색, 결과 분석의 선형적인 구조로 되어있어야 한다는 점이었습니다."
4. "언제든지 이전 단계로 돌아갈 수 있어야 하고, 프로세스를 진행하는 중 생성된 답변에 존재하는 금융 용어 질문 등을 할 수 있는 유연성을 제공해야 했습니다."
5. "대출 코치에서는 사용자의 응답을 그대로 Bedrock Agent로 전달하는 것이 아니라, 현재 상태에 맞는 프롬프트를 구성하여 전달합니다."
6. "현재 상태가 자산 분석, 대출 조회 결과 분석등의 단계일 경우, AWS Bedrock Agent가 생성한 답변에 추가적인 선택지를 제공하기 위해, 보조 Agent를 호출하여 사용자의 추가 선택지를 생성하는 과정이 포함됩니다."
7. "특히 금융 서비스와 같이 정확한 정보 전달이 중요한 분야에서는 이러한 현상이 치명적일 수 있습니다."
8. "AWS Bedrock의 Knowledge Base 기능과 학습된 Agent의 답변을 제한하는 '답변 지침'을 활용했습니다."
9. "기존 대출 서비스를 운영하면서 사용했던 기획 요건, FAQ, 대출 상품 정보 등을 문서화하여 Knowledge Base에 등록했습니다."
10. "'죄송하지만 대출 코치 서비스는 대출 및 금융 관련 질문만 답변 가능합니다.'와 같이 답변을 통제했습니다."
11. "자산 분석 및 대출 탐색 단계에서는 이 두 Agent가 함께 답변을 생성하도록 구성하여, 사용자 상태에 따라 싱글 또는 멀티 에이전트 답변을 제공하는 구조로 설계했습니다."
12. "디자이너, 기획, 마케팅, 개발 등 다양한 직군의 팀원이 모여, 1박 2일이라는 짧은 시간 안에 공동의 목표를 향해 하나의 프로덕트를 만들어야 했습니다."

## 우리 설계에 쓸 만한 점
- [추론] LLM 라우터 대신 코드가 "현재 상태(status)"로 분기해 에이전트를 고르는 방식은 결정적이고 지연이 적어서, 업무 절차가 정해진 운영 부서 흐름에 먼저 적용할 만하다.
- [추론] 요청에 status, input_source, input_type, persona를 명시하는 스키마는 부서 에이전트 간 메시지 봉투(envelope) 설계에 그대로 참고할 수 있다.
- [추론] 사용자 입력을 그대로 넘기지 않고 "지침 + 톤 + 단계 목적 + 예시 + 입력 + 컨텍스트 데이터" 순서로 조립하는 템플릿을 부서 공통 프롬프트 빌더로 만들 수 있다.
- [추론] 주답변 에이전트와 "다음 행동 선택지 생성" 보조 에이전트를 분리한 점은, 결과물과 후속 작업 제안을 다른 에이전트가 맡는 구조로 응용할 수 있다.
- [추론] 도메인 밖 질문 거절 문구를 에이전트 지침에 고정하는 방식은 부서 에이전트마다 책임 범위를 강제하는 가드레일로 쓸 수 있다.
- [추론] 마케팅 PM이 팀에 포함되어 프롬프트에 "카카오페이에서 비교하라고 추천" 같은 사업 목표를 직접 넣은 점은, 마케팅 에이전트 지침에 사업 KPI를 명시하는 사례로 볼 수 있다. 다만 사용자 이익과 충돌할 수 있어 검토가 필요하다.
- [추론] 평가 방법이 원문에 없으므로 할루시네이션 억제 효과는 검증된 것으로 보면 안 된다.
