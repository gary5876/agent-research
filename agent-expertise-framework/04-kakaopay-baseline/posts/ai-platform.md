## 핵심 한 문장
사람 손을 거쳐야 했던 MLflow 기반 레거시 모델 서빙을 온프레미스 Kubeflow 플랫폼(파이프라인, KServe, 자체 웹 콘솔)으로 바꾸고, H200 GPU용 Infiniband 하이브리드 클러스터, MIG 분할, minReplicas 1 정책, GPU 유휴/할당 모니터링으로 운영 효율을 잡았다.

## 배경과 문제
- 내부 개발자가 AI를 손쉽게 활용하고 서비스에 빠르게 적용할 환경이 없었음.
- 레거시 시스템은 반복적인 수작업에 의존해 개발 속도를 저해하고 서비스 안정성을 위협하는 기술 부채였음.
- 레거시 흐름: 데이터 사이언티스트가 GPU 서버에서 학습, MLflow 모델 레지스트리에 등록, ML 엔지니어가 모델 정보 확인 후 서비스 파일 포함 컨테이너 이미지를 직접 빌드, 운영 GPU 서버에 배포해 컨테이너로 서비스 시작. "각 단계마다 사람의 개입이 필수적인 구조".
- 과거 GPU는 고정 할당이라 미사용 시에도 낭비, 쓰려면 기다리는 "자원의 전쟁".
- 대부분의 서비스가 IDC를 사용해 온프레미스에 직접 구축하기로 결정.
- 이 글은 LLM 에이전트나 RAG가 아니라 모델 학습/서빙 인프라 플랫폼 사례다.

## 구조와 구성요소
도구 검토 (그림 표):
| | Airflow | MLflow | Kubeflow |
|---|---|---|---|
| 주요 목적 | 범용 데이터 파이프라인 오케스트레이션 | ML 실험 추적 및 모델 생명주기 관리 | kubernetes 기반 MLOps 플랫폼 |
| 인프라 기반 | 독립 실행 가능 | 독립 실행 가능 | kubernetes |
| 장점 | 범용성, 성숙도, 강력한 스케줄링 | 단순함, 유연성 | 확장성, 통합 환경, 편의성 |
| 단점 | ML 특화 기능 부족, 데이터 중심 | 오케스트레이션 부재, 확장성 제한 | 높은 복잡도, 초기 설치 및 설정, 무거움 |

Kubeflow 선택 이유 3가지:
- 표준화: 파이프라인은 누가 실행하든 동일한 순서, 컨테이너는 어디서 실행하든 동일한 환경.
- 확장성: 학습 시 필요한 만큼 동적 할당 후 즉시 반납, 서빙 시 트래픽에 따른 Autoscaling.
- 통합: AI 개발 전 과정을 한 플랫폼에 통합해 개발자가 인프라가 아닌 모델에 집중.
- 카카오페이 시스템 대부분이 이미 쿠버네티스 기반이라 운영 일관성 확보에 자연스러움. 초기 학습 곡선과 비용이라는 단점보다 장점이 크다고 판단.

새 아키텍처:
- 사용자 두 종류: AI 전문가(데이터 사이언티스트, ML 엔지니어)와 서비스 개발자.
- Kubeflow 내부: Tracking, Model Registry, Model Training, KServe.
- GPU Server: Inference Service 여러 개, Notebooks.
- Container Registry.
- 자체 개발 Web-console: 서비스 개발자가 Kubeflow 대신 웹 콘솔로 모델을 호출하고 배포.
- 데이터 사이언티스트는 Kubeflow 파이프라인으로 학습부터 모델 등록까지 자동화, ML 엔지니어는 서버 접속 없이 등록된 모델을 코드로 배포.

하드웨어와 클러스터:
- H200 GPU 도입. 고성능 장비는 CPU가 데이터 처리 속도를 못 따라가 병목이 됨.
- RDMA와 Infiniband 네트워크 도입(CPU를 거치지 않는 GPU 간 직접 통신, 대규모 분산 학습 효율).
- 하이브리드 클러스터: 일반 워커 노드는 이더넷(Kubeflow 배포, 모니터링 pod 등 일반 작업, 데이터 처리), GPU 노드는 인피니밴드(RDMA, GPUDirect). 하나의 쿠버네티스 컨트롤 플레인이 양쪽을 관리.
- MIG(Multi-Instance GPU): 물리 GPU 하나를 하드웨어 수준에서 격리된 여러 인스턴스로 분할. 쿠버네티스 정책상 물리 GPU 하나를 파드 하나만 점유하던 비효율을 해소.

서빙:
- KServe와 Knative(쿠버네티스를 서버리스로 사용, 필요할 때만 자원 할당과 회수).

## 절차와 규칙
- 배포 정책: Knative Scale to Zero 대신 minReplicas 1 유지(Always on). 콜드 스타트가 모델 크기에 따라 최대 6분 이상 걸려 서비스에서 허용 불가. 비용 효율 일부를 포기하고 응답 속도를 보장한 트레이드오프.
- GPU 분할 기준 3가지:
  - 사용처: 실시간 추론은 작게 분할된 여러 인스턴스(동시 처리), 공용 모델이나 테스트는 더 큰 인스턴스.
  - 사용 모델: GPT, Gemma 등 모델 아키텍처 특성을 분석해 가장 효율적인 MIG 인스턴스 매칭.
  - 모델 크기: 메모리 요구량을 계산해 낭비 없이 딱 맞는 크기 할당.
- 이 기준으로 "감이 아닌, 데이터에 기반하여" 할당하는 의사결정 체계를 구축.
- 모니터링 주요 지표: GPU 전체 자원 및 할당량, GPU 유휴 자원(Idle Resource), GPU 리소스 사용량 현황(모델/사용자별 실사용 효율). 이 데이터로 GPU 분할 시나리오를 지속 개선.

## 수치와 결과
- 콜드 스타트 최대 6분 이상 (모델 크기에 따라)
- minReplicas: 1 (Scale to Zero는 minReplicas: 0)
- 그림 대시보드 MIG 가용량: nvidia_com_mig_3g_71gb 3개, nvidia_com_mig_4g_71gb 3개, nvidia_com_mig_7g_141gb 4개. 현재 사용량: 3g_71gb 1개, 7g_141gb 2개
- 사용 메트릭 이름: kube_pod_container_resource_limits, kube_node_status_capacity
- 학습 시간 단축률, 비용 절감액, 활용률 개선치 등 효과 수치는 원문에 없음

## 실패, 한계, 주의점
- Kubeflow 단점: 초기 학습 곡선과 비용, 높은 복잡도, 초기 설치 및 설정, 무거움(표).
- "이론적으로 답을 찾는 것과 그것을 저희의 현실에 성공적으로 안착시키는 것은 전혀 다른 차원의 문제"였다고 서술.
- 고성능 GPU에서 CPU가 병목이 되는 문제.
- Infiniband를 기존 쿠버네티스에 통합하는 것이 가장 큰 고민이었음.
- Scale to Zero의 콜드 스타트(최대 6분 이상)로 비용 최적화를 일부 포기.
- "GPU 비용과 같은 현실의 벽"에 부딪혔다고 서술.
- 금융 환경의 제약이 있었다고 하나 구체 내용은 원문에 없음.

## 그림 설명
- 그림 1 레거시 시스템: Data Scientist가 GPU Server에서 Model Training, MLflow(Tracking, Model Registry)에 등록, ML Engineer가 Pull Prod Model 후 Container Registry로 빌드/푸시, 운영 GPU Server가 Model Download 후 Container 안에서 Model Inference. 사람 아이콘이 여러 단계에 등장.
- 그림 2 도구 검토 표: Airflow, MLflow, Kubeflow를 주요 목적, 인프라 기반, 장점, 단점으로 비교하고 Kubeflow 열을 노란 테두리로 강조(위 표 참조).
- 그림 3 새 아키텍처: Data Scientist와 ML Engineer가 Kubeflow(Tracking, Model Registry, Model Training, Kserve)를 사용, GPU Server(Inference Service 3개, Notebooks), Container Registry, 오른쪽에 Developers가 Web-console을 통해 GPU Server의 서비스 이용.
- 그림 4 Infiniband 통합: 왼쪽 H200 GPU 3대가 InfiniBand 버스로 연결(RDMA, RDMA GPUDirect), 가운데 Kubernetes Control plane, 오른쪽 Worker Node 3대가 Ethernet으로 연결(Data Processing, General Tasks).
- 그림 5 MIG 비유: 적용 전 한 차선 구불구불한 길에 차가 줄지어 대기, 적용 후 MIG 톨게이트 아래 여러 차선으로 동시에 통과.
- 그림 6 Knative와 KServe: Scale to zero(X)는 minReplicas: 0, Always on(O)은 minReplicas: 1.
- 그림 7 그라파나 "Nvidia GPU Metrics" 대시보드 예시: GPU 이름(GeForce RTX 2080 SUPER), P-State P8, GPU Utilization 0%, Power Draw 11.5%, Throttle Reasons(Idle Active), 클럭 속도, Memory Allocation, Temperature 그래프.
- 그림 8 주요 지표: kube_pod_container_resource_limits, kube_node_status_capacity 메트릭과 "GPU 전체 가용량"(mig_3g_71gb 3, mig_4g_71gb 3, mig_7g_141gb 4), "GPU 현재 사용량"(mig_3g_71gb 1, mig_7g_141gb 2) 패널.

## 원문 인용
- "데이터 사이언티스트가 모델 학습(Training)을 완료하고, 그 결과를 MLflow 모델 레지스트리에 등록하는 것으로 과정이 시작됩니다."
- "각 단계마다 사람의 개입이 필수적인 구조였습니다."
- "파이프라인은 누가 실행하든 동일한 순서로 작업을 보장하고, 컨테이너는 어디서 실행하든 동일한 환경을 보장합니다."
- "과거에는 GPU를 고정적으로 할당하여 사용하지 않을 때도 자원이 낭비되고, 사용을 위해 기다리는 ‘자원의 전쟁’이 있었습니다."
- "반면, 서비스 개발자는 복잡한 Kubeflow 대신, 저희가 자체 개발한 ‘웹 콘솔’ 을 통해 원하는 모델을 간편하게 호출하고 배포할 수 있습니다."
- "하지만, 이론적으로 답을 찾는 것과 그것을 저희의 현실에 성공적으로 안착시키는 것은 전혀 다른 차원의 문제였습니다."
- "저희가 테스트해 본 결과, 모델의 크기에 따라 이 콜드 스타트 시간이 최대 6분 이상 소요될 수 있음을 확인했습니다."
- "따라서 저희는 비용 효율을 일부 포기하더라도, 서비스 응답 속도를 보장하는 것이 더 중요하다고 판단했습니다."
- "이 기준들 덕분에 저희는 더 이상 감이 아닌, 데이터에 기반하여 각 워크로드에 최적의 GPU 자원을 할당하는 의사결정 체계를 구축할 수 있었습니다."
- "지표를 통해 저희는 현재 플랫폼에서 사용 중인 GPU 자원이 얼마나 되는지, ‘낭비’가 어디서 발생하고 있는지를 명확하게 보여줍니다."

## 우리 설계에 쓸 만한 점
- [추론] "누가 실행하든 동일한 순서(파이프라인), 어디서 실행하든 동일한 환경(컨테이너)" 원칙은 오케스트레이터가 기획, 제작, 검수 단계를 고정 파이프라인으로 정의하고 각 에이전트 실행 환경을 고정하는 근거로 쓸 수 있다.
- [추론] 사용자를 전문가용(Kubeflow 직접 사용)과 일반 개발자용(웹 콘솔)으로 나눈 점은, 부서 담당자에게는 단순한 요청 창구만 주고 내부 에이전트 구성은 플랫폼 팀이 관리하는 이중 인터페이스 설계로 옮길 수 있다.
- [추론] 레거시의 "각 단계마다 사람 개입 필수"를 문제로 본 점은, 사람 검토를 모든 단계가 아니라 필요한 게이트에만 두어야 한다는 반대 방향의 근거로 참고할 수 있다. 어느 게이트에 사람을 둘지는 원문에 없으므로 우리가 정해야 한다.
- [추론] minReplicas 1 결정처럼 비용과 응답 속도의 트레이드오프를 실측(콜드 스타트 6분)으로 결정하고 명시적으로 기록한 방식은, 에이전트 시스템의 상시 가동 대 요청 시 기동 결정을 문서관리 역할이 결정 기록으로 남기는 관행으로 옮길 수 있다.
- [추론] 사용처, 모델, 크기 3가지 기준으로 자원을 배정한 체계는 작업 유형별로 모델 크기와 호출 예산을 배정하는 오케스트레이터 라우팅 규칙(예: 실시간 응답은 작은 모델, 공용/테스트는 큰 모델)으로 응용할 수 있다.
- [추론] 모니터링 역할은 총 가용량, 할당량, 유휴량, 사용자/모델별 실사용량을 기본 지표로 두고, 그 데이터로 배정 규칙을 주기적으로 개선하는 루프를 갖도록 설계할 수 있다. 에이전트 시스템에서는 GPU 대신 토큰, 호출 수, 대기 시간이 대응 지표가 될 것이다.
- [추론] 도구 선정 시 후보를 목적, 기반, 장점, 단점 표로 비교해 기록한 방식은 우리 오케스트레이션 프레임워크 선정 문서의 형식으로 그대로 쓸 수 있다.
