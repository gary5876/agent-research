# 해커톤 경험을 통해 엿본 AI시대에 개발자가 가져야 할 자세 (AI 채용 도우미 AIVA)

- URL: https://tech.kakaopay.com/post/kakaopay-hackathon-aiva/
- 게시일: 2025-06-19 (페이지에 2026. 9. 1 날짜도 함께 표시됨, 수정일로 보임)
- 저자: ian.wizard(API플랫폼팀), jan.nabi(인프라 기획자), billy.j(인프라플랫폼실 클라우드 & OSS 엔지니어), eygon.park(시스템엔지니어), pong.du(사내시스템)
- 태그: 카페톤, AI, AWS
- 소속: 카카오페이 인프라플랫폼실, SE팀, API플랫폼팀 (본문 "인프라플랫폼실의 잔, SE팀의 이곤, 빌리, 퐁, API플랫폼팀의 이안")
- 리뷰어: wade.hong, river.pool

## 핵심 한 문장
이력서 분석용 Bedrock Agent(Resume-agent, 웹 스크래핑 Lambda 도구)와 코드 분석용 Bedrock Agent(Code-agent)를 FastAPI 서버가 기능별로 호출하고, RAG 없이 코드 전체를 컨텍스트로 넣고, 평가 기준을 하나씩 루프로 돌리며, LLM이 만든 테스트 계획을 샌드박스 EC2에서 실행해 LLM이 다시 판정하는 채용 도우미. 최종 판단은 사람이 해야 한다는 결론.

## 배경과 문제
- 카카오페이는 채용에 많은 인원이 긴 시간을 들임. 본업과 병행하며 수많은 이력서를 자세히 보기 어렵고, 객관성을 위해 타 팀 채용에 참여하면 그 팀 업무와 기술 조사가 필요.
- 개발자 기술과제 평가는 한 지원자당 1시간 이상 걸리는 경우가 많고 여러 명이 개별 평가.
- "지원자들이 들인 노력에 비해, 과연 그 정성이 충분히 전달될까?"라는 문제의식. 평가자 부담 감소를 넘어 지원자 강점을 평가자에게 더 잘 전달하는 것이 목표.
- 팀은 "AI 완전 초보자들"이었고, 결과는 4위(본문 말미 "3위안에 들지는 못해").

## 구조와 구성요소
- 아키텍처(그림 11): USER -> ALB -> EC2 BE API. BE API가 Redis(Cache, session Save), S3(Original code & Document, Upload와 Context Load), EC2 FE, EC2 Code sandbox(LLM Code Action), Bedrock Agent "Resume-agent"(-> Lambda Tool Web Scraper -> External Web Source), Bedrock Agent "Code-agent"를 각각 호출.
- 에이전트 분할은 기능 단위(이력서 vs 코드). 두 에이전트 사이 Supervisor나 상호 호출은 없고, API 서버가 화면 기능에 따라 각각 호출(그림 기준). 원문에 "멀티 에이전트"라는 표현은 없음.
- 모델: Claude 3.5 Sonnet(최대 입력 토큰 20만 개).
- BE: Python + FastAPI. LangChain으로 시작했으나 AWS SDK로 Bedrock 파라미터를 직접 지정하는 편이 나아서, LangChain은 문서/파일 loader만 사용하고 LLM은 Bedrock agent로 호출.
- FE: Streamlit(LLM 스트리밍 출력 빠른 프로토타이핑용).
- 배포: API Gateway + Lambda나 ECS 대신 EC2에 쉘스크립트로 배포(빠른 프로토타이핑과 디버깅 편의).
- 초기에는 RAG용 벡터스토어와 데이터 적재 Lambda가 있는 더 복잡한 구조였으나, AWS SA 도움을 받아 RAG를 빼면서 단순해짐.
- 브라우저 VSCode: code-server 임베딩(코드 직접 확인용).
- 도구: Resume-agent에 Lambda로 외부 회사 정보 스크래핑 후 요약.

## 절차와 규칙
- 이력서 분석: 채용공고 + 이력서를 컨텍스트로 제공. 요약, 채용공고 항목별 일치도, 강점과 적합성 등 "인간이 할법한 사고 과정"을 프롬프트로 입력.
- 프롬프트 작성법: "분석해 줘"만으로는 기준과 출력 형태가 일정하지 않음 -> 사람이 직접 어떤 관점으로 분석하는지 1차 정리 -> 그 내용을 다시 LLM으로 정리해 프롬프트 작성.
- 이력서 시스템 프롬프트 요지: 명확성과 간결성, 직무 기술서와의 관련성, 서식 및 구성, 전반적인 인상. markdown 출력, H1 금지, 섹션 제목은 H2 + 아이콘.
- 채팅: 평가자가 "이 사람의 부족한 점은?", "이력서상 의심할만한 것은?" 같은 자유 질문 가능. 채용 경험 부족한 비인사팀 평가자를 위해 추천 질문 제공.
- 기술과제 코드 분석: 전체 코드 + 과제 명세를 컨텍스트로. 기준 목록(과제내용에 대한 구현, 엣지 케이스, 에러처리, 보안, 테스트, 동시성, 효율성, 설계, 기술 스택의 이해도, 코드의 가독성 및 스타일, 문서, 주석, 강점 및 약점, 종합적인 평가)을 `{criteria}`에 하나씩 넣어 루프 호출. 이유: 출력 토큰 한계로 한 번에 많은 기준을 요구하면 상세 내용을 못 만듦.
- 코드 분석 프롬프트 규칙: 과제 명세 기준이 가장 중요, 운영환경용 코드가 아님을 고려(운영 요소 부재는 감점 아님, 있으면 가산), 부족한 부분은 짧은 코드 또는 파일명 제시, 표 형태 선호, 점수 표시 금지, 표 안에서만 👍🏻/👎 표시.
- 추천 질문 프롬프트: 5개만, 그중 1개는 반드시 "가장 부족한/잘 작성된/개선할 수 있는 부분" 범주, 과거 이력의 비슷한 질문 제외, "~에 대해서 알려줘" 형식 고정, 질문 대상은 코드 작성자가 아니라 LLM, 개선 방안/평가성/과제 분석 집중 질문 금지.
  - 그냥 "질문 추천해 줘"라고 하면 코드 작성자에게 할 질문이 나와서 대상과 카테고리를 제한함.
  - 문장 형태를 고정한 이유는 프롬프트 캐싱 적중률(비슷한 의미의 질문이 같은 문장이 되도록).
- 코드 실행(Manus에서 영감): 최소 프로그램만 설치된 서버에서, LLM에게 사용 가능한 리눅스 커맨드, 과제 명세, 코드를 주고 테스트 시나리오와 명령어 목록(JSON: explanation, command, should_evaluate, expected_result)을 생성하게 함 -> API 서버가 명령 실행 -> should_evaluate가 true면 실행 결과와 기댓값을 다시 LLM에 넘겨 정상 여부 판정 -> 종합 평가.
- 캐싱: 코드 최초 분석은 누가 요청해도 같은 결과여도 되므로, 프롬프트 내용 해시값을 키로 한 프롬프트 캐시(Redis)로 즉시 응답.
- RAG 미사용 이유: RAG는 선택되지 못한 자료가 컨텍스트에서 누락될 여지가 있어 코드처럼 디테일한 분석에서 신뢰도를 떨어뜨림. 기술과제 규모면 20만 토큰에 코드 전체가 들어감. 코드는 `<SystemPrompt>`, `<Context><Code path="...">` 마크업으로 구조화.

## 수치와 결과
- 수상: 4위.
- 기술과제 평가: 지원자 1명당 1시간 이상 걸리는 경우가 많음(도입 전 현황).
- Claude 3.5 Sonnet 최대 입력 토큰 20만 개.
- 기존 모델들 출력 토큰 4K(본문 언급).
- 추천 질문 5개.
- 예시 화면에서 이력서 적합도 평가 점수 98/100(API플랫폼팀 공고)과 FE 공고에서는 부적합 판정. 이는 작성자 본인 이력서로 한 시연.
- 정확도나 사람 평가와의 일치율 같은 평가 수치는 원문에 없음.

## 실패, 한계, 주의점
- 추천도/적합도를 평가의 직접 근거로 쓰는 것은 여러 이유로 적합하지 않을 수 있음. 빠른 분석 도구로만 유용.
- 출력 토큰 한계: 원본을 거의 보존해 출력하는 전처리에 취약. 대안(컨텍스트 분할 후 병합, 부분 출력 후 병합, 수정 부분만 출력 후 병합) 모두 특정 상황에서 오동작, 결과가 매끄럽지 않거나 다시 토큰 한계에 부딪힘.
- 출력 형식 제어: "JSON으로만 출력해"라고 해도 ```json 코드펜스로 감싸거나 "네 알겠습니다" 같은 불필요 응답 포함. 생각보다 많은 프롬프트 엔지니어링과 후처리 필요.
- 품질 유도: "LLM을 가지고 업무를 하는 것은 일처리가 빠른 주니어와 일을 하는 것과 같다". LLM에게 계획 생성을 맡기면 의도와 다른 계획이 나와 다시 제한 프롬프트가 필요할 수 있음.
- Streamlit은 선형 UX에는 괜찮지만 비선형 흐름(아래/우측 결과를 위 컴포넌트에 반영)이나 동시 비동기 통신 구현이 어려웠음.
- 코드 실행은 더 고립된 환경 구축과 프로비저닝이 필요. 분석 결과에서 코드 링크 제공은 시간 부족으로 미구현.
- 채팅 질문 정규화로 캐시 히트율 높이기는 미구현.
- 파일 선택 전처리(프롬프트 관련 파일만 넣기)도 시간 관계상 미구현.

## 그림 설명
- 01: 카페톤 공지사항 캡처(장식성).
- 02: Streamlit 화면 "지원자의 이력서를 요약했어요". 좌측 메뉴 서류전형(이력서 분석하기), 과제전형(과제 분석하기), 면접전형(종합 보고서). 기본 정보, 핵심 역량, 주요 경력, 기술 스택 섹션.
- 03: 채팅을 통한 이력서 분석 화면.
- 04: "전직장 정보를 정리했어요". 스크래핑한 회사 정보 요약. 한 회사는 "검색된 회사 정보가 이력서의 내용과 일치하지 않아 정보를 제공할 수 없습니다"라고 표시(검색 결과와 이력서 불일치 시 제공 거부).
- 05: 같은 BE 이력서를 API플랫폼팀 공고(평가 점수 98/100, 요구사항 충족)와 프론트엔드 공고(프론트엔드 전문성 X, 보완 필요)에 넣은 두 보고서 비교.
- 06, 07: 과제 구현, 문서화, 가독성 분석 표와 강점/약점 분석 화면.
- 08: 채팅을 통한 기술과제 분석(추천 질문).
- 09: 계획에 따른 코드 실행 화면. docker-compose 로그, 명령별 예상 결과와 평가 결과(SUCCESS), 마지막 종합 평가(시스템 구동, 잔고 관리, 주문 처리, 장애 대응 등).
- 10: code-server로 브라우저에 띄운 VSCode.
- 11 아키텍처: 위 "구조와 구성요소"에 기술.
- 12: Streamlit FE 화면.
- 13: 일반 RAG 개념도(Prompt + Query -> Search Relevant Information -> Knowledge Sources -> Enhanced Context -> LLM Endpoint). 개념 설명용.

## 원문 인용
1. "이력서 분석의 경우 채용공고와 이력서의 내용을 콘텍스트로 제공하였습니다."
2. "단순히 '분석해 줘'라고 하는 경우에는 분석의 기준 및 출력 형태가 일정하지 않습니다."
3. "직접 이력서 분석을 진행할 때 어떤 관점에서 분석하는지에 대해 고민을 해보며 1차적으로 그 내용들을 정리한 뒤 다시 LLM을 통해 이 내용들을 정리하여 프롬프트를 작성하였습니다."
4. "Bedrock agent에 lambda를 통하여 외부에서 회사 정보를 스크래핑하여 이를 요약하고 출력하였습니다."
5. "이러한 추천도/적합도를 평가에서 직접적인 근거자료로 사용하는 건 (스크린샷에 다 담기지 못한 내용을 포함하여) 여러 이유로 적합하지 않을 수 있습니다. 하지만 채용담당자가 빠르게 분석하는 도구로는 유용합니다."
6. "이는 출력 토큰의 한계 때문에 한번에 많은 기준에 대해 출력을 요구할 경우 상세한 내용을 생성할 수 없기 때문입니다."
7. "만약 이 명령이 실행 결과를 평가해야 하는 경우라면, 명령의 결과와 예상 기댓값을 다시 LLM에게 전달합니다. LLM은 이 정보를 바탕으로 명령이 정상적으로 실행되었는지 평가합니다."
8. "많은 부분에서 굳이 langchain을 사용할 것이 아니라, AWS SDK로 여러 파라미터를 직접 지정해 가며 Bedrock에 접근하는 것이 개발을 하기에 더 좋았습니다."
9. "RAG를 사용하게 되면 LLM에 의해 선택되지 못한 자료는 LLM응답 생성 시의 콘텍스트로 참조하지 못하는 상황이 발생하는, 즉 콘텍스트를 누락할 여지가 있습니다."
10. "최초 생성 시에만 조금은 많은 시간이 소요되고, 이후는 프롬프트 내용을 해싱한 값을 키값으로 하는 프롬프트 캐시를 사용하여 즉각적인 응답을 출력하도록 API를 개발하였습니다."
11. "생각보다도 많은 프롬프트 엔지니어링과 후처리가 필요했습니다."
12. "\"LLM을 가지고 업무를 하는 것은 일처리가 빠른 주니어와 일을 하는 것과 같다\"라는 말을 뼈저리게 느끼게 됩니다."
13. "물론 LLM에게 맡긴 경우에는 서비스 개발자가 의도한 것과는 다른 계획들이 튀어나올 수도 있기 때문에 또다시 이것을 제한하는 내용의 프롬프트가 필요할 수도 있습니다."
14. "그 결과를 해석하고 최종적으로 판단하는 주체는 결국 인간이어야 한다는 점을 다시 한번 깨닫게 되었습니다."

## 우리 설계에 쓸 만한 점
