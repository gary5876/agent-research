# FDS에 지속 성장하는 ML 모델 적용 이야기

- URL: https://tech.kakaopay.com/post/ifkakao2024-fds/

- 저자: cri.spy (크리, 백엔드), lia.ryu (리아, FDS 모델 개발)
- 태그: ifkakao2024, ifkakao, FDS
- 소속: 카카오페이 리스크관리플랫폼팀

## 핵심 한 문장
규칙 기반 탐지만으로 못 막는 새로운 사고 유형에 대응하려고, Airflow로 최신 데이터 주기 재학습 후 MLflow에서 운영 모델과 성능을 비교해 개선 시 배포하는 "지속적 학습"과, "아이템별 최근 사고 비율" 같은 동적 피처로 재학습 전에도 변화를 반영하는 "피처 자가 적응"을 결합해 신규 유형 사고에서 정적 모델 대비 탐지율을 약 30% 개선했다.

## 배경과 문제
- 카카오페이는 하루 1,300만 건, 한 달 4억 건 이상 거래.
- FDS는 송금, 결제 시 정상/사고 위험을 판단하고, 위험 시 계정 일시 정지나 거래 거절 조치.
- 규칙(Rule) 기반 탐지: 짧은 시간 대량 송금, 비정상 IP 로그인 등. 하지만 새로운 유형이나 정상과 유사한 사고는 우회 가능, 정상 거래를 사고로 오인해 고객 불편도 가능.
- 이를 보완하려고 ML 기반 탐지 추가.
- 아이템별 일자별 사고 비율이 꾸준, 감소, 일시 증가 후 감소, 없던 아이템에서 갑자기 발생 등 다양하게 변함. 규칙 기반은 룰 추가/완화, ML 기반은 새 모델 추가 개발이 필요.

## 구조와 구성요소
- 정적 ML vs 적응형(Adaptive) ML: 차이는 모델의 지속적 학습(Continuous Train)과 피처의 자가 적응(Self Adaptation).
- 지속적 학습 파이프라인(그림 4):
  - Schedule(Airflow)이 주기적으로 학습 실행
  - Model training이 Feature Store(HBase, Redis)의 피처 사용
  - 학습된 모델을 Model registry(MLflow)에 업로드
  - MLflow가 분석가에게 학습 결과 알림, 분석가가 학습 결과 확인 후 버전 선택
  - Model Serving(NVIDIA Triton Inference Server)에 모델 배포, FDS가 사용
- 데이터: 하둡(주로 배치성), 피처 스토어 HBase, Redis(준 실시간: 직전 결제 금액, 최근 N일 결제 금액 등).
- 비교 지표: Recall, Precision, FP 등 운영 중 모델과 비교.
- 사고 데이터 자가 적응 경로(그림 8): 금융 안심 센터(상담) → 사고 등록 → FDS Admin → 사고 최신 데이터가 Hadoop에 적재. Services와 FDS 데이터도 Hadoop/Feature Store로. Airflow가 주기적으로 Feature Engineering 실행 → 피처 생성 → Feature Store 적재.
- 동적 피처(Dynamic Risk Feature): 결제아이템종류별 최근 사고비율 = 결제아이템종류별 사고건수(t-h, t) / 결제아이템종류별 거래건수(t-h, t). t는 특정 시간, h는 윈도우 기간.

## 절차와 규칙
- 지속적 학습: "정해진 주기에 따라 최근 데이터를 활용해서 모델을 학습". 운영 모델과 성능 비교 결과를 알려주고, "성능이 개선된 모델이라면 바로 배포하여" Triton에 적용 가능. 본문 표현은 "유의미한 성능 개선이 있다면 새로운 모델을 즉시 배포할 수 있습니다".
- 사람의 역할: 그림 4상 분석가가 학습 결과를 확인하고 버전을 선택. 즉 배포할 모델 버전 선택은 사람 단계로 그려져 있음. 본문은 "바로 배포", "즉시 배포"라고 표현하여 완전 자동인지 사람 선택인지 본문만으로는 명확하지 않음.
- 피처: Airflow로 매일 생성, 피처 스토어에 적재.
- 사고 라벨의 원천은 금융 안심 센터로 유입되어 FDS Admin에 등록된 사고(사람이 등록).
- 적용 시점 판단: "사고 데이터가 어느 정도 쌓이고 지속적 학습 후 업데이트 된 모델 성능이 보장되었을 때 이를 배포".
- 재학습 주기, 윈도우 h 값, 성능 개선 판정 기준 수치는 원문에 없음.

## 수치와 결과
- 하루 1,300만 건, 월 4억 건 이상 거래.
- 적용 대상: 구글 플레이스토어, 애플 앱스토어 결제 사고 탐지(신규 게임 출시, 결제 이벤트로 새 유형 사고가 잦음).
- 신규 유형 사고 발생 후 정적 ML 대비 약 30% 탐지율 개선.
- 그림 9 탐지율(%) 값: D-1 100 수준에서 D+0 85, D+1 적응형 75 / 정적 70, D+2 적응형 50 / 정적 33, D+3 이후 적응형 상승(D+4 95, D+5 97) / 정적은 D+4 57, D+5 84 등.
- 그림 7 예시: C 상품 사고 비율 1.0 → 0.66 → 0.2 → 0.0 → 0.0, Z 상품 0.0 → 0.0 → 0.2 → 0.66 → 1.0.

## 실패, 한계, 주의점
- D+0~D+2 동안은 두 모델 모두 탐지율이 떨어짐. 동적 피처 덕에 적응형이 조금 덜 떨어질 뿐, 재학습 모델이 배포되는 D+3부터 회복. 즉 신규 사고 초기 며칠의 공백은 남음.
- 정적 ML은 데이터 분포가 안정적일 때 효율적이며 반복 패턴 탐지에 강하다고 원문도 인정.
- 동적 피처의 품질은 사고 등록(금융 안심 센터, FDS Admin) 데이터에 의존.
- 실패 사례, 오탐 증가, 롤백 사례는 원문에 없음.

## 그림 설명
- 그림 1: 정상거래는 비밀번호 입력 등 다음 단계 진행, 이상거래는 알림톡 "이상거래가 탐지되어 카카오페이 계정이 정지되었습니다... 365일 24시간 운영되는 카카오페이 금융안심센터로 연락주시면..." 과 함께 계정 일시 정지.
- 그림 2: 일자별 아이템 사고 비율 차트들. 보지 않음(본문 설명: 꾸준, 감소, 일시 증가, 신규 발생 패턴).
- 그림 3: Static ML(Data Set → Model Train → Model Inference 일방향) vs Adaptive ML(양방향 화살표, "모델의 지속적 학습 및 배포", Data Set에 "피처의 자가 적응" 순환 화살표).
- 그림 4: 지속적 학습 및 배포 아키텍처(위 구조 설명 참고). 분석가 노드에 "학습 결과 확인" 자기 루프, MLflow와 "학습 결과 알림 / 버전 선택" 양방향.
- 그림 5: 결제 아이템(최신 데이터) 사고 경험 O(A, B, C, D 상품) / X(E~Z 상품) → 모델 학습 → 모델 서빙 → 사고 탐지. 모델 운영 중 D 상품에서 새로운 사고 발생 → "모델 지속적 학습" 루프로 D 상품이 사고 경험 그룹에 추가.
- 그림 6: 동적 피처 수식(위 구조 설명 참고).
- 그림 7: 시간 구간별 A, B, C, D, Z 상품 사고 비율 표와 선 그래프. C는 감소, Z는 증가.
- 그림 8: FDS 사고 데이터 피처의 자가 적응 아키텍처(위 구조 설명 참고).
- 그림 9: 신규 게임 출시로 인한 gka 결제 모델 비교. 위는 static/adaptive 탐지율 선 그래프, 아래는 A~D 상품 사고 건수 막대(D 상품이 새 유형, D+2~D+3에 급증).

## 원문 인용
1. "카카오페이는 하루 1,300만 건의 거래가 이루어지고, 한달에는 무려 4억 건 이상의 거래가 이루어집니다."
2. "특히 새로운 유형의 사고나 정상 거래와 유사한 사고는 규칙 기반 탐지를 우회할 수 있습니다."
3. "적응형 ML과 정적 ML의 가장 큰 차이점은 모델의 지속적 학습(Continuous Train) 및 피처의 자가 적응(Self Adaptation) 측면입니다."
4. "모델의 지속적 학습에서 가장 중요한 포인트는 최근 데이터를 포함하여 주기적으로 학습을 진행하고 더 좋은 성능의 모델을 바로 배포하는 구조라고 할 수 있습니다."
5. "현재 운영 중인 모델의 성능을 평가하는 것과 더불어, 최신의 데이터를 활용하여 모델을 다시 학습하고 성능을 비교합니다."
6. "이렇게 학습된 모델은 Mlflow로 업로드되고 현재 운영 중인 모델의 성능(Recall, Precision, FP 등)과 비교하여 알려줍니다."
7. "따라서 자가 적응이 가능한 동적 피처란 모델 타깃(사고)이 지속적으로 피처 값에 반영될 수 있게 구성한 피처입니다."
8. "이는 새로운 사고 유형이 발생했을 때 모델 지속적 학습 이전에 피처 측면에서 자연스럽게 사고비율피처 값이 높아지면서 사고를 탐지할 수 있게 됩니다."
9. "아래를 보면 금융 안심 센터로 유입된 사고가 FDS Admin에 등록되고, 이 사고 데이터는 하둡에 적재됩니다."
10. "사고 데이터가 어느 정도 쌓이고 지속적 학습 후 업데이트 된 모델 성능이 보장되었을 때 이를 배포하고, 따라서 신규 사고를 잘 탐지하게 됩니다."
11. "적응형 ML을 통하여 신규 유형의 사고 발생 후 정적 ML 대비 약 30%의 탐지율 개선을 확인할 수 있었습니다."

## 우리 설계에 쓸 만한 점
- [추론] 규칙(빠르고 설명 가능) + 학습 모델(새 패턴) 이중 탐지 구조는 운영 부서 점검(inspection) 에이전트 설계에 그대로 옮길 수 있다: 명시 규칙 검사 먼저, 모델/LLM 판정은 보조.
- [추론] "챌린저 모델을 주기적으로 만들고 운영 모델과 같은 지표로 비교한 뒤 더 나을 때만 교체"하는 챔피언/챌린저 흐름은 에이전트 프롬프트나 정책 교체에도 쓸 수 있다. 비교 지표(Recall, Precision, FP)를 먼저 정해두는 것이 전제.
- [추론] 그림 4처럼 자동 학습, 자동 비교, 결과 알림까지는 자동으로 하고 "버전 선택"은 분석가가 하는 구조가 사람 승인 지점의 좋은 예다. 운영 부서도 "평가 자동, 교체 결정은 사람"으로 시작할 수 있다.
- [추론] 동적 피처 아이디어(최근 윈도 비율)는 재학습 없이도 최신 상황을 반영하는 저비용 적응 장치다. 에이전트 판단 입력에 "최근 N일 실패율, 최근 N일 불만 비율" 같은 롤링 지표를 넣는 것과 같다.
- [추론] 라벨(사고)의 원천이 상담 센터 사람 등록이라는 점: 운영 부서의 고객 접점(CS) 기록을 모니터링과 학습 루프의 입력으로 연결하는 피드백 경로를 설계해야 한다.
- [추론] 신규 이상 발생 후 D+0~D+2 공백이 남으므로, 자동 적응만 믿지 말고 급변 감지 시 사람에게 즉시 알리는 경보 경로를 병행해야 한다.
- [추론] 조치 단계(계정 일시 정지, 거래 거절)와 고객 안내(알림톡, 24시간 센터 연락처)가 한 세트로 설계된 점은, 운영 에이전트가 차단성 조치를 할 때 반드시 사용자 통지와 이의 경로를 함께 둬야 한다는 참고가 된다.
