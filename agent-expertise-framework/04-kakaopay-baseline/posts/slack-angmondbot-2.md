# 분산 시스템 환경에서의 슬랙봇 앙몬드 개발기

- URL: https://tech.kakaopay.com/post/slack-angmondbot-2/
- 게시일: 2024-08-27 (페이지 표기상 수정일 2026-03-24)
- 저자: gady.garden (가디)
- 태그: 슬랙봇, FE
- 소속: 카카오페이 마이데이터클랜 FE 개발 (저자 소개상 "자산관리 서비스의 FE 개발")

## 핵심 한 문장
사내 슬랙봇도 가산, 판교 두 리전에 파드가 하나씩 뜨는 카카오페이 기본 분산 환경에서 돌기 때문에, 크론잡 알림이 두 번 발송되는 문제는 DB 트랜잭션 + SELECT FOR UPDATE 락으로, 서버 인메모리에 저장한 유저별 탭 상태가 튀는 문제는 Redis 중앙 저장소로 해결했다.

## 배경과 문제
- 카카오페이는 서비스 안정성과 장애 영향 최소화를 위해 기본적으로 분산 환경에서 운영. k8s 리전 클러스터(Regional Cluster)로 가산, 판교 두 지역에 클러스터 구축.
- 사내 프로젝트여도 k8s 기반 환경 구성을 신청하면 가산, 판교 각각 하나의 파드가 구동됨.
- 이점으로 고가용성, 부하 분산, 재해 복구를 듦. 단 분산 환경을 이해하지 못한 채 로직을 짜면 예기치 못한 문제가 생김.
- 문제 1: 금요일 오후 7시 미완성 TIL 삭제 예정 알림, 월요일 9시 주간 아카이브 등 크론잡이 두 서버에서 동시에 실행되어 같은 알림이 간헐적으로 두 번 발송.
- 문제 2: 홈의 "오늘 배운 것"/"내 보관함" 탭 선택 상태를 서버 인메모리에 저장해서, 요청이 다른 서버로 가면 기본 탭("오늘 배운 것")으로 되돌아감. CSR 사고방식에 익숙해 문제를 바로 파악하지 못함.

## 구조와 구성요소
- 서버 2대(파드 Pod-gs 가산, Pod-pg/ps 판교). 글에서는 편의상 파드를 "서버"로 표현.
- 크론잡 상태 테이블(Schedule): name, lastStartedAt(마지막 실행 시간), enabled(활성화 여부). 그림상 hostname 컬럼도 있음. 등록된 잡 이름 예(그림 2의 테이블): NOTIFY_UNCOMPLETED_TIL, NOTIFY_UNFINISHED_TODO, DELETE_UNCOMPLETED_TIL, NOTIFY_TIL_RANKING, NOTIFY_AGIT.
- TypeORM QueryRunner로 트랜잭션 관리, lock mode 'pessimistic_write'(SELECT FOR UPDATE).
- Redis: 유저별 홈 탭 정보를 중앙 저장. 서버는 Stateless.

## 절차와 규칙
크론잡 실행 4단계:
1. 크론잡 상태값 읽기(lastStartedAt, enabled)
2. 실행 가능 판단: enabled 이고 마지막 실행 후 1분이 지났을 때만 실행 가능("이미 다른 서버에서 1분 이내에 실행된 크론잡은 실행하지 않는다.")
3. 실행 전 lastStartedAt을 현재 서버 시간으로 업데이트
4. 매핑된 스케줄 로직 실행

executeJobWithLock 흐름(원문 코드 주석 번호):
- [1] queryRunner 생성 → [2] 트랜잭션 시작, pessimistic_write로 스케줄 행 조회 → [3] 실행 불가면 즉시 커밋하고 종료(락, 메모리, CPU 소모를 줄이려고 조기 커밋) → [4] lastStartedAt 갱신 저장 → [5] 스케줄 로직 실행 → [6] 커밋(커밋 후에만 변경이 외부에 공유되므로 바로 커밋) → [7] 에러 시 롤백 → [8] queryRunner 해제.
- DB 갱신과 스케줄 로직 실행은 "모두 성공하거나 실패해야만" 일관성이 보장된다는 전제로 한 트랜잭션에 묶음.

탭 상태:
- 어느 서버로 요청이 가든 일관된 값을 읽도록 모든 서버가 접근하는 중앙 저장소(Redis)에 homeTab 저장.
- DB 대신 Redis를 쓴 이유: 빠른 읽기/쓰기, 트랜잭션 기능을 통한 데이터 일관성, 캐싱으로 DB 부하 감소.

## 수치와 결과
- 리전 2곳(가산, 판교), 리전당 파드 1개.
- 실행 가능 판단 기준 1분.
- 크론 표현식(그림 1): "0 19 * * 1-5 NOTIFY_UNFINISHED_TIL".
- 결과는 정성적: 알림을 한 번씩만 받게 됨, 탭 고정 문제 해결. 발생 빈도 등 수치는 원문에 없음.

## 실패, 한계, 주의점
- 원문 경고: "대규모 서비스에서는 DB LOCK은 지양해야 합니다." DB 테이블 락은 성능 저하를 초래. 앙몬드는 사내 소규모 대상이라 별도 자원 없이 DB 락을 실용적으로 선택.
- 동시성 문제 때는 Redis 도입 계획이 없어서 DB 락을 썼고, 탭 문제 때는 이미 Redis가 있어서 Redis 사용. 즉 해결책 선택이 당시 보유 인프라에 좌우됨.
- 코드 [5]에서 func(now)를 await 없이 호출(원문 코드 그대로). 스케줄 로직의 비동기 실패가 트랜잭션 롤백에 반영되는지는 원문에서 다루지 않음. [추론] 원문 코드상 관찰이며 글쓴이가 언급한 한계는 아님.
- "1분" 윈도는 시간 기반 중복 방지이므로 서버 간 시계 차이 등은 원문에서 다루지 않음.

## 그림 설명
- 그림 1 (알림 중복 발송): Pod-gs와 Pod-ps가 각각 Cronjob Logic을 가지고 동일한 "0 19 * * 1-5 NOTIFY_UNFINISHED_TIL"을 실행, 앙몬드가 "아직 다 작성하지 않은 TIL이 1개 남아있어요 / 오늘 자정까지 작성완료되지 않은 TIL 쓰레드는 자동으로 삭제되어요" 메시지를 두 번 보낸 캡처.
- 그림 2 (해결): Pod-pg는 "Transaction w/ SELECT FOR UPDATE Lock" 박스에 들어가 check schedule status(lastStartedAt >= 1min && enabled) → update schedule status(lastStartedAt = 현재시간 && hostname = os.hostname()) → execute cronjob. Pod-gs는 X 표시로 차단. 하단 문구 "Only One Pod at a time => Race Condition 없음". 우상단에 스케줄 테이블(id, name, lastStartedAt, hostname, enabled)과 자물쇠 아이콘. 알림 1회 발송 캡처.
- 그림 3: 유저가 "내 보관함" 탭 클릭 화면. 확인하지 않음(캡션으로 내용 확인).
- 그림 4 (탭 튐): Pod-gs에는 homeTab = "STORAGE"가 있지만 요청이 Pod-pg로 가서 defaultTab = "TIL"이 적용, 클라이언트 화면이 "오늘 배운 것"으로 되돌아감.
- 그림 5 (Redis 해결): 유저 클릭으로 homeTab = "STORAGE"가 Redis에 저장되고 Pod-gs, Pod-pg 모두 Redis에서 homeTab을 읽어 "내 보관함" 탭이 유지됨.

## 원문 인용
1. "카카오페이는 서비스 안정성을 높이고, 장애 영향도를 최소화하기 위해 기본적으로 분산 시스템 환경에서 서비스를 운영하고 있습니다."
2. "사내 프로젝트더라도 쿠버네티스(k8s) 기반 서비스의 환경 구성을 신청하면 가산, 판교 두 지역에 각각 하나의 애플리케이션 파드가 구동되어 운영됩니다."
3. "크론잡은 지정된 시간에 정확히 한 번만 수행되어야 하는데, 같은 알림이 간헐적으로 두 번 발송되는 문제가 있었습니다."
4. "크론잡이 활성화된 상태이고 마지막 크론잡 실행 후 1분이 지났을 때, 크론잡을 실행 가능한 상태로 판단합니다."
5. "크론잡 로직에 포함된 데이터베이스 갱신 작업과 크론잡에 매칭된 스케줄 로직을 실행하는 작업, 이 두 작업은 모두 성공하거나 실패해야만 데이터 일관성을 보장할 수 있습니다."
6. "트랜잭션이 실행되는 동안 데이터베이스는 Lock, 메모리, CPU 등의 자원을 지속적으로 소비하기 때문에 조기에 트랜잭션을 커밋하면 불필요한 리소스 소모를 줄일 수 있습니다."
7. "대규모 서비스에서는 DB LOCK은 지양해야 합니다."
8. "반면 분산 시스템 환경에서는 유저 요청이 여러 서버에 분산되어 처리되기 때문에, 서버 간 탭 정보 동기화가 어렵습니다."
9. "유저별 홈 탭 정보를 Redis에서 관리함으로써 서버는 Stateless 해질 수 있게 되었습니다."
10. "동시성 문제를 마주했을 때는 Redis까지 도입할 계획이 없어서 위에 소개한 대로 데이터베이스 LOCK으로 문제를 해결했어요."

## 우리 설계에 쓸 만한 점
- [추론] 에이전트 인스턴스를 여러 개 띄우는 순간 정기 작업(주간 리포트, 알림)이 중복 실행될 수 있다. 운영 부서의 스케줄 작업에는 "잡 이름 단위 락 + lastStartedAt + enabled" 같은 단일 실행 보장 테이블을 두는 것이 기본이다.
- [추론] enabled 플래그는 사람이 잡을 끄는 킬 스위치 역할도 한다. 운영 부서가 자동 작업을 일시 중단할 수 있는 수동 제어점으로 설계에 포함할 만하다.
- [추론] hostname 기록은 어떤 인스턴스가 실행했는지 추적하는 감사 로그 역할. 에이전트 실행 기록에도 실행 주체 식별자를 남길 것.
- [추론] 에이전트의 대화/세션 상태를 프로세스 메모리에 두면 인스턴스가 바뀔 때 튄다. 공유 상태는 중앙 저장소(Redis, DB)에 두고 에이전트 워커는 stateless로 설계하는 근거.
- [추론] 해결책의 규모 적합성: 소규모에서는 DB 락으로 충분하다는 원문 판단처럼, 초기 멀티에이전트 시스템은 새 인프라 도입보다 기존 DB로 동시성 제어를 먼저 하는 선택지가 있다.
- [추론] "중복 알림"은 사용자에게 바로 보이는 장애 신호였다. 운영 부서 모니터링에 "같은 잡의 같은 시각 발송 건수 > 1" 같은 중복 감지 검사를 넣을 수 있다.
