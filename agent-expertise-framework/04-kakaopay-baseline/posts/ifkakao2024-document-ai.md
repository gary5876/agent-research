## 핵심 한 문장
휴대폰 보험 수리비 영수증을 Edge Detection(YOLO Segment), Layout Analysis(YOLO Detect), OCR(TrOCR), 규칙 기반 Parsing 4단계로 처리해 사람 검토를 대체하고, confidence 기준, 회전 재시도, 편집 거리 허용 같은 예외 처리 규칙을 덧붙였다.

## 배경과 문제
- 보험금 청구 시 제출 문서를 사람이 검토하기 때문에 입금까지 길게는 하루 이상 걸림.
- 카카오페이손해보험은 Document AI가 검토를 대신해 고객 대기 시간이 10분을 넘지 않음.
- 메타 설명: 보험금 청구를 위한 "일 평균 3,000장의 문서"를 Document AI가 처리.
- 대상 사례: 휴대폰 보험 파손 수리비 보상. 증빙 서류 중 수리비 영수증에서 수리처, 발행일, 결제금액 3개 정보를 인식해야 함. 수리처는 "삼성전자서비스" 고정값, 발행일과 결제금액은 일정 포맷의 가변값.
- 이 글은 LLM이나 에이전트를 쓰지 않는 문서 인식 파이프라인 사례다.

## 구조와 구성요소
Document AI 정의: 문서를 이미지로 입력받아 Key-Value 데이터로 출력. 중간 절차 각각을 Task라 부름. 어떤 Task가 필요한지는 문서와 개발자마다 다름.

일반 Task 4종:
1. OCR: Detection(텍스트 위치)과 Recognition(문자 인식). 결과에 텍스트와 Bounding Box. TrOCR처럼 Recognition만 있는 경우도 있음.
2. Layout Analysis: 제목, 표, 본문 등 영역 검출. 원하는 정보가 특정 영역에만 있으면 그 영역만 OCR해 효율적.
3. Classification: 문서 종류 분류. 용도: 여러 문서 중 필요한 것만 필터링, 필수 문서 누락 시 업로드 단계에서 알림, 문서별 로직/모델 분기 기준.
4. Parsing: 다른 Task 결과를 종합해 서비스 요구에 맞는 Key-Value로. 예: 사업자등록증으로 분류되고 {3자리}-{2자리}-{5자리} 패턴이면 "사업자번호".

수리비 영수증 파이프라인 (순차 4단계):
1. Edge Detection (모델, YOLO Segment): 문서 테두리 점들의 x, y 좌표 검출. 저자가 추가로 배경 제거와 기울기 보정 로직 구현, 보정은 OpenCV Perspective Transform.
2. Layout Analysis (모델, YOLO Detect): 3개 정보 위치와 영역 이름(태그, 예 AMOUNT) 및 confidence 반환.
3. OCR (모델, TrOCR): 각 영역 텍스트와 confidence.
4. Parsing (규칙 기반 로직): Layout 태그와 OCR 텍스트를 합쳐 Key-Value 생성. 결제금액은 정규표현식 `\d+,\d+{3}`로 "amount": 80,000.
- Parsing만 규칙 기반, 나머지 3개는 학습시켜 둔 모델.

모델 세부:
- YOLO: 원래 실생활 객체 탐지용. Segment(다각형 정교 검출)는 Edge Detection에, Detect(사각형 검출)는 Layout Analysis에 사용.
- Segment 학습 데이터: 영수증뿐 아니라 문자가 인쇄된 종이와 배경이 있는 이미지 전부. 다른 문서 인식에도 재사용.
- Detect 학습 데이터: 영수증 이미지만(영수증 특화 구조 분석).
- TrOCR: HuggingFace 공개 사전학습 모델 정확도가 우수해 바로 쓸 수 있는 것도 있음. End-to-End 학습이라 타 OCR 대비 학습이 간편하고 운영 효율이 좋음. 참고 링크 microsoft/trocr-base-printed.

인프라:
- AWS g4dn.xlarge VM, 시간당 800원. 개발, 베타, 운영 3개 페이즈로 분리해 시간당 2,400원.

## 절차와 규칙
- Confidence: 모델이 추론 결과를 얼마나 확신하는지, 0과 1 사이. 신뢰 기준으로 사용(예: 0.7 이상인 경우에만 신뢰). Layout Analysis와 OCR 모두 confidence를 제공해 신뢰 기준을 정할 수 있음.
- 회전 이미지 보정: 가로로 회전된 이미지는 학습하지 않아 일부 객체 미검출 또는 낮은 confidence. 이미지를 90, 180, 270도로 회전시켜 정상 추론이 나올 때까지 입력. 90도 회전에서 정상이면 원본은 -90도로 판단해 보정.
- 비대상 문서 필터링: 세 각도 모두 비정상 결과면 영수증이 아니라고 판단해 이후 프로세스를 진행하지 않음.
- OCR 오인식 보정: 레빈슈타인 디스턴스(편집 거리). 예: "삼성전자서비스"의 "전"을 "진"으로, "서"를 누락하면 거리 2. 거리가 특정 수치 이하면 동일 텍스트로 간주. 구체 임계값은 원문에 없음.
- 모델은 Edge Detection 같은 범용 모델은 재사용하고, Layout은 문서별 특화 학습.

## 수치와 결과
- 일 평균 3,000장 문서 처리 (메타 설명)
- 고객 대기 시간 10분을 넘지 않음 (기존에는 길게는 하루 이상)
- 인식 대상 필드 3개
- 파이프라인 4단계 (모델 3, 규칙 1)
- confidence 신뢰 기준 예시 0.7
- 그림상 OCR confidence: 수리처 0.9238, 발행일 0.9527, 결제금액 0.9612
- 회전 시도 각도 90, 180, 270도
- 편집 거리 예시 2
- 서버 g4dn.xlarge 시간당 800원, 3개 페이즈 합계 시간당 2,400원
- 구현 기간 약 7개월
- 인식 정확도, 자동 처리율, 사람 검토 비율 등은 원문에 없음

## 실패, 한계, 주의점
- 앞 설명은 해피 케이스 기준이며 실제 운영에서는 예외 케이스(회전, 다른 문서, OCR 오인식)가 발생.
- 학습하지 않은 방향(가로 회전)의 이미지는 모델이 일부 객체를 검출 못 하거나 낮은 confidence로 비정상 결과를 냄.
- Layout Analysis는 2단계라 그 시점에는 문서 종류를 알 수 없음(별도 Classification 없이 회전 재시도 결과로 판단).
- OCR은 글자를 틀리거나 누락할 수 있어 편집 거리 허용이 필요.
- 인식 실패 시 사람 검토로 넘기는지 등 fallback 절차는 원문에 없음.
- 저자는 AI를 전공하지 않은 백엔드 개발자라고 밝힘.

## 그림 설명
- 그림 1 OCR: 문서 속 "카카오페이손해보험" 영역을 박스로 잡아 {"text": "카카오페이손해보험"}으로 출력.
- 그림 2 Layout Analysis: 사업자등록증에서 "제목" 영역(사업자등록증, 법인사업자, 등록번호)과 "세부 내용" 영역(법인명, 대표자, 개업연월일, 사업장 소재지)을 색으로 구분.
- 그림 3 Classification: 문서 묶음이 사업자등록증, 카드영수증, 주민등록증으로 분기.
- 그림 4 Parsing: 사업자등록증 제목 영역이 {"문서명": "사업자등록증", "사업자 유형": "법인사업자", "사업자 번호": "620-88-02208"}로 변환.
- 그림 5: 실제 삼성전자서비스 카드영수증 원본(발행일 2022.11.18, 공급가 72,728, 세액 7,272, 합계 80,000, 스마트폰 손상/파손 관련 수리).
- 그림 6: 영수증에서 인식 대상 3곳(삼성전자서비스(주), 2022.11.18, 80,000)만 하이라이트. OCR 원문 품질이 흐려 "삼성전지서비스"처럼 보임.
- 그림 7: 영수증, 1단계 Edge Detection, 2단계 Layout Analysis, 3단계 OCR, 4단계 Parsing, 인식 결과 JSON으로 이어지는 흐름도.
- 그림 8: 책 위에 기울어져 놓인 영수증 사진, 테두리 검출(노란 사각형), 배경 제거와 직각 보정 후 결과 3단 비교.
- 그림 9: 영수증에서 수리처, 발행일, 결제금액 영역이 라벨과 점선으로 연결됨.
- 그림 10: 세 영역을 OCR에 넣어 text와 confidence(0.9238, 0.9527, 0.9612) JSON을 얻음.
- 그림 11: 세 OCR 결과가 Parsing을 거쳐 {"provider": {"type":"TEXT","value":"삼성전자서비스"}, "publishedAt": {"type":"DATE","value":"2022.11.18","format":"yyyy.MM.dd"}, "amount": {"type":"MONEY","value":80000,"unit":"WON"}}로 정규화. 필드마다 타입, 값, 포맷/단위를 가진 구조.
- 그림 12: Segment(구겨진 수리비명세서를 카펫 배경에서 다각형 노란 외곽선으로 검출)와 Detect(카드영수증에서 수리처, 발행일, 금액을 색이 다른 사각형으로 검출) 비교.

## 우리 설계에 쓸 만한 점
- [추론] 검수(inspection) 역할은 모델 판단과 규칙 기반 판단을 섞는 구조가 적합하다. 이 글처럼 인식은 모델에, 최종 구조화와 형식 검증(정규식, 타입, 포맷)은 결정적 규칙에 맡기는 분리를 에이전트 산출물 검증에도 적용할 수 있다.
- [추론] 각 단계 결과에 confidence(또는 이에 준하는 자기평가 점수)를 붙이고 임계값 이상만 자동 통과시키는 규칙은 오케스트레이터가 자동 진행과 사람 검토로 분기하는 기준으로 쓸 수 있다. 원문은 임계값 미만 처리 절차를 밝히지 않았으므로 사람 검토 큐는 우리 쪽 설계다.
- [추론] "세 각도로 다 해봐도 비정상이면 대상이 아니라고 판단하고 중단" 규칙은 입력이 해당 부서 에이전트의 처리 대상인지 판정하고 아니면 다음 단계로 넘기지 않는 입구 필터(기획 단계의 입력 검증)로 옮길 수 있다.
- [추론] 필수 문서 누락을 "업로드 단계에서 알려주기"는 요청 접수 시점에 필수 입력 체크리스트를 검사해 바로 요청자에게 돌려주는 규칙으로 옮길 수 있다.
- [추론] 최종 출력 스키마가 필드별 type, value, format/unit을 갖는 형태(그림 11)는 에이전트 간 전달 데이터 계약의 예시로 쓸 만하다.
- [추론] 편집 거리 허용처럼 "고정값과의 근사 일치"를 규칙으로 허용하는 방식은 검수 에이전트가 고유명사, 제품명 표기를 확인할 때 과도한 오탐을 줄이는 근거가 된다.
- [추론] 범용 전처리 모델(Edge Detection)은 재사용하고 문서별 모델만 따로 학습한 구조는, 공통 도구(MCP)는 부서 공용으로 두고 부서별 특화 로직만 분리하는 설계와 대응된다.
- [추론] 개발, 베타, 운영 3개 페이즈를 분리해 운영한 점은 에이전트 시스템도 같은 환경 분리를 두고 비용을 페이즈 수만큼 잡아야 한다는 근거가 된다.
