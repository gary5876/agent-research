## 핵심 한 문장

Agent는 LLM("머리")에게 판단만 맡기고 실제 실행과 루프, 컨텍스트, 도구를 관리하는 "몸"이며, 실무에서 이를 안전하게 쓰려면 능력을 넓히는 장치(Tool, MCP, Skill, Plugin, Marketplace)와 실행을 통제하는 장치(Multi-Agent Orchestration, Supervisor, Hook, Harness)를 구분해 배치해야 하고, 그 핵심 규율은 "Agent가 실수하면 프롬프트를 고치지 말고 그 실수가 구조적으로 불가능해지는 장치를 만든다"이다.

## 배경과 문제

- Codex, Claude Code, GitHub Copilot 등을 쓰는 사람이 많아졌고, 프로젝트가 커지면서 "이 기능 통째로 구현해 줘" 같은 큰 미션을 맡기기 시작하자 "구조적인 한계와 모호함"에 부딪히는 사람이 많아짐.
- 독자가 가진 질문: "내가 쓰던 ChatGPT랑 Agent는 뭐가 다르지?", "MCP, Skill, Harness... 이 수많은 키워드는 다 뭐고 어디에 위치해야 하는 걸까?"
- 글의 목적: AI Agent를 개발 워크플로우에 처음 도입하려는 사람이 알아야 할 핵심 개념과 아키텍처 키워드를 저자 나름대로 정리.
- 4장 도입부 문제 제기: "Agent에게 수천 줄짜리 프로젝트를 통째로 맡기면 컨텍스트에 과부하가 걸려 품질이 떨어지는 코드를 짜기 시작합니다." 이를 막기 위한 "시스템적 보완 장치"가 4장의 내용.

## 구조와 구성요소

### 1) LLM과 Agent (머리와 몸)

- LLM: 방대한 데이터를 학습해 언어를 이해하고 요약, 번역, 생성하는 모델. 예시로 든 모델: OpenAI GPT 계열(ex. GPT-5.6), Anthropic Claude 계열(ex. Claude Sonnet 5), Google Gemini 계열(ex. Gemini 3.1 Pro).
  - 작동 방식: "입력을 받아 출력을 내는 함수". 상태(State)가 없음.
  - 흔한 오해 정정: "LLM은 단발성이고 Agent는 대화를 기억한다"는 설명은 정확하지 않음. 챗봇이 멀티턴 대화를 잘 하는 건 매 호출마다 이전 대화 기록 전체를 다시 보내주기 때문이고, 모델 자체는 매번 백지 상태에서 시작.
  - 한계: 스스로 검색하거나 로컬 파일을 수정할 수 없음. 대답은 하지만 직접 실행은 못 함.
- AI Agent: "목표(Goal)만 주면 알아서 계획을 짜고, 필요한 도구를 써서, 처음부터 끝까지 업무를 완수하는 AI 일꾼". 예시: Codex, Claude Code, Gemini CLI.
  - 작동 방식: 목표를 실행 가능한 작업으로 쪼갠 뒤 도구 호출, 결과 관찰, 다음 행동 결정의 반복. 중간에 정보를 넣어 주지 않아도 스스로 굴러감.
  - 한계: 스스로 판단하는 만큼 통제가 필요. 루프가 길어지면 컨텍스트가 차오르고 비용이 누적되며, 권한을 좁혀 두지 않으면 건드리면 안 되는 것까지 건드림.
- 그림 1(아래 그림 설명 참고)은 Agent가 루프를 굴리기 위해 관리하는 것을 Tools, Context, Skills 세 가지로 묶음.

### 2) Agent 루프 (ReAct)

- 순환 구조: 목표 설정 → 정보 획득 → 작업 구현.
  - 목표 설정: 유저 목표를 실행 가능한 작은 작업(Task)들로 쪼개고 순서를 배치.
  - 정보 획득과 구현: 지식이 부족하면 LLM으로 먼저 추리(Reasoning), 답할 수 없으면 등록된 Tool들의 설명(Description) 텍스트를 읽고 행동(Action). 가져온 정보가 부족하면 질문을 다시 정의하고 다른 툴 호출.
- ReAct(Reasoning + Action): 2022년 논문에서 제안. 원 논문은 추론 단계와 행동 단계를 분리해 품질을 높이는 패턴이지만 "지금 도구들이 그대로 쓰지는 않습니다". 요즘은 모델이 함수 호출을 네이티브로 지원(tool calling)해서 구현이 달라졌지만 "판단 → 행동 → 관찰 → 재판단"이라는 뼈대는 그대로. "오늘날 Agent 루프의 원형".
- 루프 종료 기준 3가지 (없으면 무한히 돌거나, 다 끝나기 전에 멈춤):
  1. 모델이 스스로 완료 선언: 가장 흔하지만 다 안 됐는데 됐다고 하는 경우가 있음.
  2. 최대 반복 횟수 / 토큰 예산 초과: 실행 폭주를 막는 안전장치.
  3. 외부 검증 통과: 테스트가 통과하면 종료. "가장 신뢰할 만합니다".

### 3) 토큰과 컨텍스트 윈도우

- 토큰: 모델이 텍스트를 처리하는 최소 단위. 글자 수도 단어 수도 아닌 토크나이저가 쪼갠 조각 수. 처리 속도와 비용의 기준.
  - 언어별 차이: 토크나이저 대부분이 영어 데이터 기준. 영어는 흔한 단어 하나가 토큰 하나인 경우가 많고, 한글은 흔한 단어가 아니면 음절 단위, 심하면 바이트 단위까지 쪼개짐.
  - 예시(원문이 "정확한 수치는 아니고 참고용 예시"라고 명시): "tokenization" → token / ization (2 토큰), "토큰화" → 토 / 큰 / 화 또는 그보다 더 잘게 (3 토큰 이상).
  - 결론: 같은 의미라도 한글로 쓰면 "영어보다 토큰이 몇 배로 늘어날 수 있습니다". 정확한 수치는 모델과 토크나이저 버전에 따라 다르므로 비용이 민감하면 각 모델의 토큰 카운팅 API로 직접 재볼 것.
  - 과금: API 직접 호출 시 입력 토큰과 출력 토큰에 각각 다른 단가가 붙는 토큰 단위 과금이 일반적. 단 월 정액 구독형은 토큰이 아니라 사용량 한도로 제한, 이미지나 음성은 장수나 재생 시간 기준인 경우도 있음, 프롬프트 캐싱처럼 같은 토큰도 단가가 달라지는 옵션 있음. "토큰을 줄이면 비용이 줄어든다"는 대체로 맞지만 실제 청구서는 요금제와 입력 형태에 따라 다름.
- 컨텍스트 윈도우: 한 번의 호출에서 볼 수 있는 토큰 총량. 시스템 프롬프트, 대화 기록, 도구 목록, 도구 실행 결과, 생성할 답변까지 전부 이 안에 들어가야 함.
- 컨텍스트가 많아지면 차례로 나타나는 문제 3가지:
  1. 비용과 응답 시간 증가: 매 호출마다 이전 기록을 처음부터 다시 받음. 10턴째 호출은 앞선 9턴을 다시 읽음. 대화가 두 배 길어지면 전체 비용은 두 배보다 훨씬 많이 듦. 도구 실행 결과가 계속 쌓이는 Agent 루프에서는 이 격차가 더 벌어짐. 프롬프트 캐싱으로 앞부분 비용은 낮출 수 있지만 읽어야 하는 양 자체가 줄지는 않음.
  2. limit를 넘으면 앞부분이 잘림: 대부분의 도구는 에러 대신 오래된 대화부터 알아서 버리거나 요약하고 이어감. 이 정리가 조용히 일어나서, 초반에 합의한 요구사항이나 코딩 규칙이 요약 중 사라져도 사용자는 모름. "Agent가 갑자기 아까 정한 규칙을 어기기 시작한다면 대개 이것이 원인입니다."
  3. limit 전에도 품질 저하: 길어지면 앞부분과 끝부분은 비교적 잘 참고하지만 가운데 묻힌 내용은 흘려보내는 경향. 그래서 "아직 여유가 있으니 괜찮다"고 보기 어려움. 지금 작업과 상관없어진 내용은 그때그때 덜어내는 편이 좋음.

### 4) 확장성 키워드 (능력을 넓히는 쪽)

- Tool: LLM이 모르는 최신 데이터(실시간 주가, 최신 문서 등)가 필요할 때 구글 검색 엔진, Yahoo Finance API 같은 외부 애플리케이션에 접근하도록 연결한 인터페이스.
  - 원리: 모델에게 "이런 함수들이 있고, 각각 이런 일을 하고, 이런 인자를 받는다"는 명세와 설명을 넘김. 모델은 사용하기로 한 함수 이름과 인자를 텍스트로 agent에게 전달.
  - 원문 예시 명세(read_file):
    ```
    {
      "name": "read_file",
      "description": "주어진 경로의 파일 내용을 UTF-8 텍스트로 반환한다",
      "input_schema": {
        "type": "object",
        "properties": {
          "path": { "type": "string", "description": "읽을 파일의 경로" }
        },
        "required": ["path"]
      }
    }
    ```
    name = "이런 함수가 있고", description = "이런 일을 하고", input_schema = "이런 인자를 받는다".
  - 모델은 함수를 직접 실행하지 않음. 요청 텍스트만 내놓고, 디스크를 읽는 주체는 Agent.
  - description 품질이 중요: 모호하면 엉뚱한 도구를 부르거나 필요한 도구를 지나침. 도구를 수십 개 등록하면 명세만으로 컨텍스트를 상당히 차지하므로 지금 작업에 필요한 도구만 켜둘 것.
- MCP (Model Context Protocol): 개발자와 Tool 제공자가 스펙을 일일이 맞추지 않고 업계 표준 프로토콜로 소통하도록 만든 오픈소스 규약.
  - 문제: 프레임워크(LangChain, CrewAI 등)와 Tool이 늘면 SDK를 따로 만드는 부담이 커짐. 클라이언트 M개, 도구 N개면 연동 MxN개. 예: Slack 연동을 Codex용, Claude Code용으로 각각 만들고 다음 도구가 나오면 또 만듦.
  - 해법: 표준 규약 하나로 MxN을 M+N으로. MCP 서버를 하나 만들면 Claude든 Codex든 코드 수정 없이 Plug & Play로 파일, 슬랙, DB를 연결.
  - 범위: 실행 가능한 함수(Tools)뿐 아니라 읽기 전용 참조 자료(Resources), 재사용할 프롬프트 템플릿(Prompts)까지 규정. "모델에게 무엇을 건네줄 것인가" 전반을 다루는 규약.
- Skill: Agent가 특정 목표를 위해 Tool들을 어떤 순서로, 어떻게 조합해 써야 하는지 담은 가이드라인이나 프롬프트 파일. "도구를 다루는 '판단력과 워크플로우'".
  - 규격: 폴더 하나에 SKILL.md 파일을 두고 이름과 설명을 적는 구조.
  - 핵심 설계, 점진적 공개(Progressive Disclosure): (1) 세션 시작 시 이름과 설명만 컨텍스트에 올라감 (2) Agent가 필요하다고 판단하면 본문 전체를 읽음 (3) 본문이 참조하는 상세 문서는 정말 필요할 때만 읽음.
  - 규칙 파일(CLAUDE.md, AGENTS.md) vs Skill: 규칙 파일은 항상 읽히고 스킬은 필요할 때만 읽힘. 상시 규칙(예: "이 프로젝트는 pnpm을 쓴다")은 규칙 파일에, 특정 작업 지식(예: "PDF에서 표를 추출하는 방법")은 스킬에. 규칙 파일은 최대한 짧게. 몰아넣으면 매 세션 컨텍스트 낭비이고 "쓰든 안 쓰든 매 세션 비용으로 청구".
- Plugin: 특정 서비스나 기능을 바로 쓸 수 있게 관련 Tool, Skill, MCP 서버 등을 하나로 묶은 것(밀키트, 가구 조립 키트 비유). 예: '슬랙 플러그인' 설치로 메시지 읽기/전송 기능과 가이드라인이 통째로 탑재.
- Marketplace: 플러그인, MCP 서버, AI 스킬을 다운로드하거나 구매하는 허브(예: Cursor Marketplace, Smithery). 경고: 남이 만든 스킬과 MCP 서버 설치는 남의 코드를 실행하는 것과 같고, 심사 절차가 있는 앱스토어와 다르니 공식 제공처나 신뢰할 만한 제작자 것을 사용.
- 원문 비교표 (MCP는 표에 없음):

| 키워드 | 개념 | 비유 |
|---|---|---|
| Tool | 하나의 함수 | 드라이버 한 자루 |
| Skill | 도구 사용 매뉴얼 | 가구 조립 설명서 |
| Plugin | 도구 + 매뉴얼 + 설정 묶음 | 조립 키트 한 박스 |
| Marketplace | 묶음들의 유통 채널 | 가구점 |

### 5) 안전장치와 제어 장치 (실행을 통제하는 쪽)

- Multi-Agent Orchestration: 혼자 다 하려던 AI에게 전문 분야를 가진 AI 팀원을 붙이고 협업을 지휘하는 패턴. 플러그인 형태로 패키징된 것도 있고 직접 구성도 가능.
  - 페르소나 분할: "같은 모델에 서로 다른 지시를 줘서" "깐깐한 아키텍트", "손 빠른 주니어", "악독한 QA" 같은 역할로 나눔.
  - Main Agent가 명령을 쪼개 작업 큐(Queue)와 흐름을 제어하고, 대화 중 맥락이 유실되지 않게 중심에서 공통 메모리(State)를 관리.
  - Main Agent는 Subagent에게 작업을 넘기고 "결과만" 받아 최종 처리. Subagent는 자기만의 컨텍스트 윈도우를 씀. 파일 20개를 뒤지고 검색을 다섯 번 돌려도 메인에게는 정리된 결론 한 덩어리만 돌아감. 탐색 잡음이 메인 컨텍스트를 오염시키지 않음.
  - "Subagent는 일을 나누는 장치이기 이전에 컨텍스트를 격리하는 장치". 탐색이나 조사처럼 과정은 지저분하고 결론은 짧은 작업일수록 효과가 큼.
- Supervisor: 작업하는 Agent를 관찰하다가 무한 루프에 빠지거나 같은 실패를 반복하면 개입하는 별도 Agent.
  - 모델 배치: 보통 상대적으로 무거운 모델이 실무를 처리하고, 가볍고 빠른 모델을 감독관으로 세움.
  - 개입 방식: 정체되면 깨우고(Nudge), 안 되면 인간에게 에스컬레이션(Escalate).
  - 가벼운 모델로 충분한 이유: 코드의 옳고 그름을 판단하는 게 아니라 진행 상태를 체크하는 역할이기 때문.
- Hook: "파일을 저장할 때", "커밋 직전에" 같은 시점에 자동 실행되는 스크립트. 린터 실행, 테스트 실행, 금지된 파일 수정 차단.
  - 장점: LLM 판단에 의존하지 않음. 프롬프트로 "커밋 전에 항상 테스트를 돌려"라고 하면 대개 지키지만 가끔 잊음. Hook으로 걸면 조건이 맞을 때 무조건 실행.
  - 결론: 지켜야 하는 규칙은 프롬프트가 아니라 Hook으로 강제.
- Harness Engineering: 하네스는 말에 채우는 마구. 힘을 억누르는 게 아니라 원하는 방향으로 쓰게 하는 장치. "모델을 더 똑똑하게 만드는 대신, 모델이 일하는 환경을 설계하는 패턴".
  - 위치: Subagent(컨텍스트 격리)의 "위층". 격리된 컨텍스트 안에서 무슨 일이 벌어지든 결과물이 통과해야 할 관문을 미리 깔아두는 것. "일을 어떻게 나눌지가 오케스트레이션이고, 나뉜 일이 무엇을 통과해야 하는지가 하네스".
  - Hook, Supervisor, Subagent는 따로 노는 기법이 아니라 하나의 구조를 이루는 부품.
  - 3역할 표(원문 그대로):

| 역할 | 하는 일 | 예시 |
|---|---|---|
| 제어(Control) | 허용된 범위 밖의 행동을 막는다 | hook, 권한 모델, 린트 룰, 의존성 체크 |
| 감시(Monitoring) | 동작 상태와 출력을 추적하고 기록한다 | supervisor, 실행 로그, 검증 게이트 |
| 개선(Feedback) | 오류를 감지해 다음 동작에 반영한다 | 위반 시 수정 지시를 컨텍스트로 되돌림 |

  - 핵심 규율: Agent가 실수하면 프롬프트를 고치지 않고, 그 실수가 구조적으로 불가능해지는 장치를 만듦.
  - 자산 관점: 프롬프트 수정은 그 세션에서 끝나지만 검증 스크립트는 남음. 모델이 새로 나와도 하네스는 재사용.

## 절차와 규칙

- 루프에는 반드시 종료 기준을 둔다. 신뢰도 순: 외부 검증 통과 > 반복 횟수/토큰 예산 > 모델 자기 선언.
- 비용이 민감하면 토큰 수는 추정하지 말고 모델별 토큰 카운팅 API로 직접 잰다.
- 지금 작업과 상관없어진 내용은 컨텍스트에서 그때그때 덜어낸다.
- Tool description은 명확하게 쓴다. 지금 작업에 필요한 도구만 켜둔다.
- 상시 규칙은 규칙 파일(CLAUDE.md, AGENTS.md)에 짧게, 특정 작업 지식은 Skill로 분리한다.
- 마켓플레이스 플러그인, MCP 서버, 스킬은 공식 제공처나 신뢰할 만한 제작자 것만 쓴다.
- 지저분한 탐색, 조사 작업은 Subagent에 넘기고 결론만 받는다.
- 감독(Supervisor)은 가벼운 모델로 진행 상태만 본다. 정체 시 Nudge, 해결 안 되면 사람에게 Escalate.
- 지켜야 하는 규칙은 Hook으로 강제한다.
- Agent 실수에 대한 대응은 프롬프트 수정이 아니라 구조적 차단 장치 추가.
- 도입 순서(마치며): 한 번에 다 도입하려 하지 말고 "마켓플레이스에서 플러그인 하나 설치해 Tool부터" 붙여 시작. 더 좋은 모델을 기다리기보다 지금 도구의 실행 환경을 다듬는 쪽이 빠름.
- 키워드 분류 기준(마치며): 어떤 키워드든 "Agent의 능력을 넓히는 쪽인지, 실행을 통제하는 쪽인지"로 구분.

## 수치와 결과

- 원문은 개념 설명 글이라 실측 결과는 없음. 등장하는 숫자는 모두 예시:
  - "tokenization" 2 토큰, "토큰화" 3 토큰 이상 (원문이 "정확한 수치는 아니고 참고용 예시"라고 명시).
  - 10턴 대화에서 10번째 호출은 앞선 9턴을 다시 읽음.
  - MxN 연동이 M+N으로 줄어듦.
  - Subagent 예시: 파일 20개, 검색 5번을 해도 결론 한 덩어리만 반환.
  - ReAct 논문 연도 2022년.

## 실패, 한계, 주의점

- Agent는 스스로 판단하는 만큼 통제가 필요. 루프가 길면 컨텍스트와 비용 누적, 권한을 좁히지 않으면 건드리면 안 되는 것까지 건드림.
- 모델 자기 완료 선언은 "다 안 됐는데 됐다고 하는 경우"가 있음.
- 종료 기준이 없으면 무한 루프 또는 조기 종료.
- 한글은 토큰이 몇 배로 늘 수 있음. 요금제에 따라 "토큰 감소 = 비용 감소"가 그대로 성립하지 않을 수 있음.
- 컨텍스트 초과 시 조용한 요약, 삭제로 초반 합의 규칙이 사라짐. limit 전에도 중간 내용은 흘려보냄.
- 모호한 description은 도구 오선택, 도구 과다 등록은 컨텍스트 점유.
- 규칙 파일 비대화는 매 세션 비용.
- 마켓플레이스 코드는 심사 없는 남의 코드 실행.
- 수천 줄 프로젝트를 통째로 맡기면 컨텍스트 과부하로 품질 저하.
- 프롬프트 지시는 "대개 지키지만 가끔 잊음". 대문자 강조는 "확률".
- 한 번에 다 도입하려 하면 지치기 쉬움.

## 그림 설명

1. 그림 1 (본문 1장 끝, "AI Agent = 몸"): 바깥 상자 제목 "AI Agent = '몸'", 부제 "Codex, Claude Code, Gemini CLI: 루프를 돌리는 실행 환경". 안쪽 위에 보라색 상자 "LLM = '머리': 다음에 뭘 할지 판단만 하는 함수 (상태 없음, 루프 없음, 손발 없음)". 그 아래 초록 상자 "Agent loop: 판단 → 도구 실행 → 결과 관찰 → 다시 판단 → ... (종료 조건을 만날 때까지)". 두 상자 사이 화살표: Agent loop에서 LLM으로 "판단 요청", LLM에서 Agent loop로 "행동 결정". 하단 제목 "루프를 굴리기 위해 몸이 관리하는 것들" 아래 3행: Tools(파일 읽기/쓰기, 셸 실행, 검색, API 호출), Context(무엇을 넣고 무엇을 버릴지 결정), Skills(도구를 어떤 순서로 쓸지 담은 매뉴얼). 텍스트에는 없는 "Agent 런타임이 관리하는 3요소" 분류와 "루프 없음, 손발 없음"이라는 LLM 정의가 그림에만 있음.
2. 그림 2 (Tool 절, "도구 호출 한 사이클"): 사용자 입력 "src/App.tsx의 컴포넌트 이름 알려줘". 5단계: (1) Agent → 모델: 질문 + 도구 명세(위 JSON) 전달 (2) 모델 → Agent: "read_file 써야겠다" 판단, 호출 요청을 텍스트로 반환, `{ "name": "read_file", "arguments": { "path": "src/App.tsx" } }` (3) Agent: 파일을 실제로 읽음 (모델이 아니라 Agent가 실행) (4) Agent → 모델: 읽은 내용을 컨텍스트에 넣어 재질문 (5) 모델 → Agent: 내용을 보고 최종 답변 생성. 초록 칸은 Agent 주체, 보라 칸은 모델 주체로 색이 구분됨.

## 원문 인용

1. "모델 자체는 매번 백지 상태에서 시작합니다."
2. "스스로 판단하는 만큼 통제가 필요합니다. 루프가 길어지면 컨텍스트가 차오르고 비용이 누적되며, 권한을 좁혀 두지 않으면 건드리면 안 되는 것까지 건드립니다."

4. "작업 초반에 합의했던 요구사항이나 코딩 규칙이 요약 과정에서 사라져도 사용자는 알 수 없습니다. Agent가 갑자기 아까 정한 규칙을 어기기 시작한다면 대개 이것이 원인입니다."
5. "모델이 내놓는 것은 “이 함수를 이 인자로 불러 달라”는 요청 텍스트뿐이고, 실제로 디스크를 읽는 주체는 Agent입니다."
6. "규칙 파일은 항상 읽히고, 스킬은 필요할 때만 읽힙니다."
7. "여기 넣은 내용은 쓰든 안 쓰든 매 세션 비용으로 청구됩니다."
8. "다만 남이 만든 스킬과 MCP 서버를 설치하는 건 남의 코드를 실행하는 것과 같습니다."
9. "Subagent는 일을 나누는 장치이기 이전에 컨텍스트를 격리하는 장치입니다. 탐색이나 조사처럼 과정은 지저분하고 결론은 짧은 작업일수록 효과가 큽니다."
10. "모니터링을 가벼운 모델로 시켜도 괜찮은 이유는 코드의 옳고 그름을 판단하는 역할이 아니라 진행 상태를 체크하는 역할을 하기 때문입니다."

14. "“반드시 XYZ 해라”라고 대문자로 써두는 건 확률이지만, 어기면 빌드가 깨지는 건 보장입니다."

## 우리 설계에 쓸 만한 점

- [추론] 오케스트레이터는 원문의 Main Agent 역할(명령 분해, 작업 큐와 흐름 제어, 공통 State 관리)로 정의하고, 부서 에이전트(마케팅/개발/운영)와 기획/제작/검수/모니터링/문서관리 역할 에이전트는 Subagent로 두어 "결론 한 덩어리"만 오케스트레이터에 반환하게 한다.
- [추론] 원문 표현대로 Subagent를 "컨텍스트 격리 장치"로 보면, 조사가 많은 기획 역할과 로그를 많이 읽는 모니터링 역할이 격리의 이득이 가장 크다. 이 두 역할의 반환 형식(요약 스키마)을 먼저 고정한다.
- [추론] 페르소나 분할은 "같은 모델에 서로 다른 지시" 방식이 원문 기준. 검수 역할은 원문의 "악독한 QA", 제작은 "손 빠른 주니어", 기획/설계 검토는 "깐깐한 아키텍트"에 대응시킬 수 있다.
- [추론] 모니터링 역할은 원문의 Supervisor처럼 가벼운 모델로 두고 "옳고 그름"이 아니라 "진행 상태"(무한 루프, 같은 실패 반복, 정체)만 보게 한다. 대응은 Nudge 후 사람에게 Escalate의 2단계로 고정한다.
- [추론] 검수 역할의 판정은 가능한 한 외부 검증(테스트, 스키마 검사, 린트)으로 두고, 역할 에이전트의 "완료 선언"은 종료 기준으로 쓰지 않는다. 원문의 종료 기준 신뢰도 순서(외부 검증 > 예산 > 자기 선언)를 그대로 채택.
- [추론] 모든 역할 루프에 최대 반복 횟수와 토큰 예산 상한을 하네스 레벨에서 건다(원문 종료 기준 2번).
- [추론] 하네스 3역할 표를 그대로 설계 체크리스트로 쓴다. 제어(hook, 권한 모델, 린트 룰, 의존성 체크), 감시(supervisor, 실행 로그, 검증 게이트), 개선(위반 시 수정 지시를 컨텍스트로 되돌림).
- [추론] 부서별 금지 파일/금지 행동(예: 마케팅 에이전트가 코드 수정, 개발 에이전트가 운영 설정 수정)은 프롬프트가 아니라 Hook과 권한 모델로 차단한다.
- [추론] "개선(Feedback)" 역할을 구현하려면 Hook 위반 메시지를 그대로 해당 에이전트 컨텍스트로 되돌려 재시도하게 하는 경로가 필요하다.
- [추론] 문서관리 역할은 규칙 파일과 Skill의 분리를 관리한다. 모든 부서 공통 상시 규칙은 짧은 규칙 파일로, 부서별 작업 지식은 Skill(SKILL.md, 점진적 공개)로 둔다.
- [추론] 컨텍스트 요약 과정에서 초반 합의 규칙이 조용히 사라진다는 원문 경고 때문에, 합의된 요구사항과 규칙은 대화가 아니라 파일(State)로 저장하고 매 단계 다시 읽게 한다.
