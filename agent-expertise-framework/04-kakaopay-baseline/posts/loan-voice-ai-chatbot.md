# 생성형 AI와 금융의 만남, 대출 음성 상담 챗봇 서비스

- URL: https://tech.kakaopay.com/post/loan-voice-ai-chatbot/
- 게시일: 2025-05-16 (페이지에 2026. 9. 1 날짜도 함께 표시됨, 수정일로 보임)
- 저자: jko.me(대출 플랫폼 백엔드, 제이코), greg.ss(대출 플랫폼 백엔드, 그렉), dore.mi(대출 플랫폼 FE, 도레), finn.tech(데이터분석팀 겸 크레딧클랜 대출 데이터 분석, 핀), joel.ove(크레딧클랜 PM, 조엘)
- 태그: 카페톤, AI, AWS

## 핵심 한 문장
음성 입력을 Transcribe, Bedrock(Claude), Polly로 잇는 실시간 파이프라인을 Kotlin 코루틴 채널로 구성하고, 가명 대출 데이터 대신 코풀라 기반 합성 데이터를 RAG 지식 베이스에 넣은 대출 상담 에이전트이며, 과제가 선형적이라는 이유로 멀티 에이전트가 아닌 싱글 에이전트를 의도적으로 선택함.

## 배경과 문제
- 비대면 금융 이용은 늘지만 불확실성 때문에 직접 상담을 선호하는 경향, 대출에서 특히 두드러짐.
- 온라인 대출 중개에 필요한 것은 "개인의 상황을 깊이 이해하는 맞춤형 상담"이라고 봄.
- 은행 창구처럼 쌍방향 대화 UX를 위해 텍스트가 아니라 음성을 택함. "아직 존재하지 않은 시장".
- 핵심 기능 3가지: 자연스러운 음성 인터페이스, 개인 맞춤형 상품 추천(최적 조건 금융기관 연결), 데이터 기반 개선 제안(유사 사용자 비교로 신용 관리 방안 제시).

## 구조와 구성요소
- 데이터 흐름 7단계(그림 02): 1 FE->BE 음성(WebSocket 스트리밍) / 2 BE->Transcribe 음성, 텍스트 수신 / 3 BE->FE 텍스트(사용자가 인식 결과 확인) / 4 BE->Bedrock 텍스트, 응답 텍스트 / 5 BE->FE 응답 텍스트 / 6 BE->Polly 텍스트, 음성 수신 / 7 BE->FE 음성.
- FE: 볼륨 임계값 이상일 때만 음성 전송(잡음, 네트워크 절약).
- BE: Kotlin + 코루틴. WebSocket 메시지에 `type` 필드(USER_TEXT, AGENT_TEXT, AGENT_VOICE)로 목적 구분.
- 서비스별(Transcribe, Bedrock, Polly) 업스트림/다운스트림 채널 쌍과 전용 코루틴, 클라이언트. Transcribe 결과가 `isPartial == false`일 때만 Bedrock 업스트림으로 전달.
- 세션 ID별 채널 맵(ConcurrentHashMap<SessionId, Channel<...>>), 세션 종료 시 채널 close 및 맵 제거.
- 모델: 본문은 "Anthropic Claude". 그림 11에는 Claude 3.5 Haiku(Parsing tabular data)와 Claude 3.7 Sonnet(LLM Model).
- Polly: 한국어 여성 음성.
- AI 에이전트 파이프라인(그림 11):
  - 상단: 사용자 -> kakaopay -> Credit Service -> Hadoop -> (가명 데이터 선별 도구 아이콘) -> "컬럼 단위 분포 정보 생성, 변수간 논리적 제약 조건" -> Output.
  - 하단(AWS): EC2 -> Synthetic Data(합성 데이터) <-> 데이터 품질 검증 -> S3 -> Claude 3.5 Haiku(Parsing tabular data) -> Embedding(User Embedding, Item Embedding) -> Vector Store -> Knowledge Base -> Q&A. Claude 3.7 Sonnet(LLM Model) -> Prompt Engineering(Stage 1/Stage 2) -> Q&A -> Text 2 Voice.
- 지식 베이스: 청킹 후 임베딩, 벡터 스토어는 OpenSearch Serverless(자동 확장/축소, 튜닝 없이 대량 저장 검색).
- 에이전트: 싱글 에이전트. 세션 히스토리 기억, 고객 정보는 세션 기반으로 30일 저장.

## 절차와 규칙
- 합성 데이터 생성: 하둡 내 가명 처리된 대출 및 마이데이터에서 필요한 데이터 선별 -> 컬럼별 분포 정보 생성 -> 변수 간 상관관계와 다변량 분포(공분산 행렬 등) 추출 -> AWS 환경에서 샘플링, 코풀라(Copula)로 종속 구조 보존 -> 결측치와 이상치 반영(강건성) -> 대출 도메인 변수 간 논리적 제약 조건 반영.
- RAG 채택 이유: 상품 조건과 고객 데이터가 계속 바뀌어 파인튜닝은 비용 효율이 낮음. 이상적으로는 모니터링 후 정기 파인튜닝이지만 일정상 RAG.
- 청킹 이유: 임베딩 모델 입력 길이 제한, 테이블 데이터의 의미론적 맥락 보존, RAG 효율과 정확도.
- 싱글 에이전트 선택 이유 2가지: (1) 태스크의 명확성과 단순성, 절차가 선형(고객 정보 수집 -> 조건 검토 -> 상품 추천 -> 고객 맥락에 맞는 상담), 역할 분담이나 에이전트 간 협업 불필요 (2) 일관된 사용자 경험, 멀티 에이전트는 통신, 역할 분담, 정보 공유 관리 요소가 많아 혼란이나 정보 중복, 누락 가능. 역할이 커지거나 다른 금융 서비스와 연계되면 멀티 에이전트로 변경 필요.
- 사용자 유형 분류(프롬프트): 신규 대출 희망자, 기존 대출 갈아타기 희망자, 추가 대출 희망자, 단순 상품 정보 탐색자.
- 에이전트 단계별 목표: 1 개인 맞춤형 상품 추천 / 2 조건 및 금리 비교 / 3 절차 및 필요 서류 안내 / 4 전문 상담 연결 유도 / 5 잠재 고객 확보.
- 추천 규칙: 지식 베이스 상품 임베딩으로 실시간 필터링, 유사 금융 특성 고객 클러스터를 식별해 특정 금융 행동으로 더 유리한 조건을 쓸 수 있음을 안내. 음성이라 추천 개수를 제한, 신용도 기준 최적 2개 상품만 추천하고 금리, 한도, 상환 방식을 비교.
- FE 트러블슈팅: 응답 음성이 커서 한 번에 처리하면 지연과 음질 저하 -> 오디오 큐로 순차 재생. 사용자가 말을 멈춰도 서버가 인식 못해 응답 지연 -> 샘플 절대값 100 초과를 음성으로 보고, 300ms 무음이면 무음 데이터(Int16Array 2048)를 서버로 전송, 100ms 주기 체크. 전송은 CHUNK_SIZE 4000으로 분할.

## 수치와 결과
- 데이터 흐름 7단계.
- 고객 정보 세션 저장 30일.
- 추천 상품 수 2개.
- 무음 판정 300ms, 체크 주기 100ms, 음성 임계값 100, 청크 4000, 무음 버퍼 2048.
- 개발 기간 1박 2일.
- 그림 01 예시 페르소나: 신용점수 750 금리 19% 500만원(저신용자) vs 신용점수 900 금리 3% 6400만원(고신용자). 설명용 예시.
- 품질, 정확도, 지연 측정 수치는 원문에 없음.

## 실패, 한계, 주의점
- 다중 사용자 테스트 중 "A 팀원의 음성을 변환한 텍스트가 B 팀원에게 표시" -> 세션 ID별 채널 분리로 해결.
- 핸들러 방식은 비즈니스 로직이 여러 핸들러로 파편화되어 흐름 파악이 어려움 -> 채널로 메인 로직을 한 곳에 모음.
- 파인튜닝이 이상적이지만 일정 제약으로 RAG 채택.
- 싱글 에이전트는 역할 확대나 타 서비스 연계 시 멀티 에이전트로 변경 필요하다고 스스로 한계 명시.
- 대출 데이터는 원본을 AI 학습 및 추론에 쓸 수 없음(개인정보).

## 그림 설명
- 01: 저신용자(신용점수 750) 대비 고신용자(900) 비교 일러스트. 데이터 기반 개선 제안 기능 설명용.
- 02: 7단계 시퀀스 다이어그램(Frontend, Backend, Transcribe, Polly, Bedrock).
- 03~09: 02의 각 단계를 하나씩 강조한 같은 다이어그램으로 보임(내용 중복, 개별 확인 생략).
- 10 백엔드 정리도: Frontend <-> Backend 사이 메시지(audio ByteArray, type USER_TEXT, AGENT_TEXT, AGENT_VOICE). Backend 안에 Transcribe, Bedrock, Polly 각각의 upstream channel -> coroutine -> client -> AWS 서비스, client -> downstream channel. Transcribe downstream의 text에 isPartial false 표시.
- 11 LLM 데이터 파이프라인: 위 "구조와 구성요소"에 기술. 데이터 품질 검증 단계가 합성 데이터에서 EC2로 되돌아가는 화살표(재생성 루프)로 그려짐.
- 12: 마무리 일러스트 "단순히 정보를 제공하는 챗봇을 넘어, 사용자의 금융 생활 전반을 케어하는 진정한 금융 상담 파트너"(장식성).

## 우리 설계에 쓸 만한 점
- [추론] 이 글은 멀티 에이전트를 쓰지 않을 조건(선형 절차, 제한된 도구, 일관된 페르소나 필요)과 전환 조건(역할 확대, 타 서비스 연계)을 명시한 드문 자료라서, 부서별로 멀티 에이전트가 정말 필요한지 판단하는 체크리스트로 쓸 수 있다.
- [추론] 멀티 에이전트의 위험으로 든 "정보 중복 또는 누락", "고객 혼란"은 부서 간 에이전트 핸드오프 설계에서 공유 상태와 단일 대화 창구를 두어야 한다는 근거가 된다.
- [추론] 서비스별 업스트림/다운스트림 채널 + 세션 ID 매핑 패턴은 에이전트 간 메시지 버스를 설계할 때 세션 격리의 구체 예시가 된다(세션 섞임 버그가 실제로 났음).
- [추론] 부분 결과(isPartial)는 사용자에게만 보여주고 확정 결과만 다음 에이전트로 넘기는 규칙은, 파이프라인 단계 간 전달 조건으로 옮겨 쓸 수 있다.
- [추론] 민감 데이터는 원본 대신 통계적 성질을 보존한 합성 데이터로 에이전트를 개발, 테스트한다는 접근은 운영 데이터 접근 권한이 없는 초기 개발 단계에 참고할 만하다.
- [추론] 에이전트 프롬프트를 "사용자 유형 분류 -> 유형별 단계 목표"로 짜는 방식은 마케팅 에이전트의 고객 세그먼트별 응대 설계에 응용할 수 있다.
- [추론] 출력 채널 특성(음성)에 맞춰 추천 개수를 2개로 제한한 것처럼, 부서 에이전트 출력량을 소비 채널에 맞춰 제한하는 규칙을 둘 만하다.
