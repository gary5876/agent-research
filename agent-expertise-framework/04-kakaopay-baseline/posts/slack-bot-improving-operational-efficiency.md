# 배포 효율화를 위한 자동화 슬랙봇 개발

- URL: https://tech.kakaopay.com/post/slack-bot-improving-operational-efficiency/
- 게시일: 2023-06-09 (페이지 표기상 수정일 2025-09-17)
- 저자: ari.a (아리)
- 태그: SRE, 자동화
- 소속: 카카오페이 SRE팀 RE(Release Engineering)파트

## 핵심 한 문장
개발자와 배포자(운영자)가 법적으로 분리된 핀테크 환경에서, 배포 요청서가 생성되면 슬랙봇이 담당자를 누적 배포 횟수 기준으로 자동 배정하고, 배포통제시스템(VROOM)의 상태 변경을 추적해 슬랙 공유를 대신하게 만들어 수작업 준비 절차와 커뮤니케이션 누락을 줄였다.

## 배경과 문제
- 2022년 한 해 카카오페이 배포 횟수는 11,156건.
- 전자금융감독규정 제26조(직무의 분리)에 따라 프로그래머(개발)와 오퍼레이터(운영) 직무를 분리해야 하므로, 카카오페이는 개발 조직과 운영(배포) 조직을 분리 운영한다. 전사 대고객 서비스 배포는 SRE팀 RE파트 담당.
- 배포 현황을 한눈에 볼 대시보드나 배포자가 쉽게 인지할 알림 시스템이 없었다.
- 배포 요청이 오면 담당자 지정, 배포 순서 확인, 배포 일정 조율 등 준비 절차를 수작업으로 진행. 업무 시간 내내 긴장 상태 유지, 피로도 높음.
- 휴먼 에러, 커뮤니케이션 미스로 배포 지연 또는 누락 위험.
- 담당자 지정 문제: 배포는 파트 전원이 맡는 공통 업무. 공통 업무를 소홀히 하는 것(방관자 효과)을 막으려고 배포 건수를 성과 평가 가산점으로 넣었더니, 이번엔 하나의 요청서를 여러 명이 가져가려는 경쟁이 생기고 "건 수는 채워야 하니" 계속 긴장 상태로 대기하게 되어 피로도가 올라갔다.
- 커뮤니케이션 문제: 한 가지 상태 변경에 두 가지 동작(VROOM 처리, 슬랙 공유)이 필요했다. 둘 중 하나만 하면 상대방이 대기하게 된다.
  - ex1. 모듈 배포 종료 공유 O, 종료 처리 X: 요청자가 검증 진행 불가(VROOM에서 종료 처리는 배포 담당자만 가능).
  - ex2. 종료 공유 X, 종료 처리 O: 요청자가 공유를 계속 기다림.

## 구조와 구성요소
- VROOM 배포통제시스템: IT 내부 통제 관점에서 절차와 권한에 맞게 프로그램 변경(애플리케이션 배포)이 이뤄지도록 하는 시스템. 배포 요청서(티켓)와 상태(승인, 배포 시작, 배포 종료, 검증 종료 등)를 가진다.
- 슬랙봇 (VROORE / VROORE 알리미, 앱 홈 설명 "RE 매뉴얼 업무 자동화"):
  - 기능 1. 배포 담당자 자동 배정
  - 기능 2. 배포 커뮤니케이션 효율화 (요청서 상태 변경 추적 후 슬랙 자동 공유)
- 앱 홈 화면: 주번 표시(업무 외 시간 배포 문의는 매주 돌아가며 맡는 주번 담당), 가능/불가능 토글 버튼.
- 참여자: 배포 요청자(개발자), VROOM, Slack, 배포 담당자(RE파트).

## 절차와 규칙
배포 절차 시퀀스(예외 없는 이상 케이스, 그림 6 기준):
1. 요청자가 VROOM에 배포 요청서 작성
2. VROOM이 Slack에 신규 요청서 알림
3. (자동화) 담당자가 신규 요청서 확인
4. (자동화) 팀 내 배포 담당자 결정
5. (자동화) 배포 진행 스레드 생성
6. (자동화) 요청자에게 배포 시각/순서 확인 요청
7. 요청자가 배포 시각/순서 확인 (사람)
8. (자동화) 요청서 승인 상태 확인, 승인될 때까지 반복
9~15. 모듈 수만큼 반복: 모듈 배포 시작 처리(사람) → 시작 공유(자동화) → 배포 진행(사람) → 종료 처리(사람) → 종료 공유(자동화) → 요청자의 모듈 검증 종료 처리(사람) → 검증 종료 공유(자동화)
16. 요청서 배포 종료 처리 (사람)

즉 "처리"(VROOM 상태 변경)와 실제 배포, 검증은 사람이 하고, "공유/확인/배정"만 자동화했다. 요청서 "승인"은 봇이 상태를 확인할 뿐 승인 자체는 자동화 대상이 아니다.

규칙:
- 배정 알고리즘: 담당자별 누적 배포 횟수를 기반으로, 누적 횟수가 하위권인 크루 중에서 랜덤 배정.
- 담당 요청서가 너무 많거나 회의, 휴식 시간 등으로 배포가 불가능하면 슬랙봇에서 "불가능" 상태로 바꿔 신규 요청서를 받지 않는다. 앱 홈 안내 문구상 "자동으로 복구되지 않아요. 일정이 완료되면, 가능 버튼을 눌러주세요."
- 요청서 오픈 알림은 "정규 업무 시간 배포 요청서 오픈"과 "시간 외 배포 요청서 오픈"으로 구분되어 발송(그림 10).
- 배정 후 스레드에서 봇이 요청자에게 "원본 메시지에서 배포 순서와 시작 시각을 선택해주세요", "특이사항이 있다면 댓글로 알려주세요"를 안내하고, 요청자가 드롭다운으로 배포 순서/요청 시각을 선택(그림 12).
- 상태 변경 시 사람은 요청서에서 상태 변경 처리만 하면 슬랙 공유는 자동.

## 수치와 결과
- 2022년 배포 11,156건.
- 효과는 정성적으로만 서술: "RE파트의 모든 크루가 균등하게 배포를 진행", "배포 준비 절차의 피로를 줄일 수 있었습니다", "공유 누락 같은 단순 실수로 인한 배포 지연을 방지".
- 칭찬 메시지를 최근 한 달 동안 "매주 하나씩 받은 것 같습니다".
- 소요 시간, 지연 건수 등 정량 전후 비교는 원문에 없음.

## 실패, 한계, 주의점
- 성과 평가 가산점이라는 인센티브 설계가 오히려 경쟁과 긴장 대기를 만든 사례(자동 배정 도입의 동기).
- 시퀀스는 "배포 실패나 롤백 등 예외 케이스가 없는 이상적인 케이스"만 다룸. 실패/롤백 처리 방식은 원문에 없음.
- 불가능 상태는 자동 복구되지 않음(사람이 다시 켜야 함).

## 그림 설명
- 그림 1 (기존 배포 절차의 문제점): 두 개의 원. "수작업으로 진행되는 배포 절차"가 "인력, 시간 소요, 피로도"를 낳고, "휴먼 에러, 커뮤니케이션 미스"가 "배포 지연, 누락"을 낳는 구조.
- 그림 2 (배포 담당자 지정): 슬랙에서 RE파트 크루들이 "5시 10분 자산관리 할게요", "6시 증권플랫폼 할게요"처럼 손으로 담당을 선언하는 캡처.
- 그림 3 (배포 일정 조율): VROOM 티켓 링크 공유 후 "배포 필요하실 때 말씀 부탁드려요", "혹시 동시 배포 가능한 건일까요?" 같은 수동 조율 스레드(댓글 12개).
- 그림 4 (휴먼 에러): 요청자가 "브룸에서 배포완료 처리 부탁드려요~ 검증진행하게요", 담당자가 "앗 깜빡했네요 완료처리했습니다" 하는 캡처. 처리 누락으로 검증이 막힌 사례.
- 그림 5: AS-IS(수작업 배포 절차, 휴먼 에러/커뮤니케이션 미스) → TO-BE(배포 절차 자동화, 배포 커뮤니케이션 효율화).
- 그림 6: 위 "절차와 규칙"의 16단계 시퀀스 다이어그램. 검은 화살표는 직접 수행, 파란 화살표는 자동화된 절차. "승인 될 때까지 반복", "모듈 수 만큼 반복" 두 루프가 빨간 박스로 표시.
- 그림 7, 9: 그림 6의 일부 확대(준비 구간 1~7, 커뮤니케이션 구간 9~15).
- 그림 8: 밈 이미지. 하이에나 무리("배포 담당자")가 사자 한 마리("배포 요청서")를 둘러싼 사진. 요청서 하나를 여러 담당자가 서로 가져가려는 경쟁 상황을 풍자.
- 그림 10 (자동 배정): "VROORE 알리미" 앱의 "시간 외 배포 요청서 오픈"(주황 바, 배포일시 21:00), "배포 요청서 오픈"(파랑 바, 15:30) 카드. 필드는 제목, 요청자, 배포일시, 담당자, 메모("동시 배포 가능합니다.").
- 그림 11 (가능/불가능 설정): 앱 홈. 주번 안내, 가능/불가능 버튼, 자동 복구 안 됨 안내.
- 그림 12 (커뮤니케이션 효율화): 세 단계 캡처. (1) "배포요청서 배포준비" 카드: 티켓정보, 배포일시(시작 정보 없음), 요청서 작성자, 배포 담당자, 배포 순서/요청 시각 드롭다운, 스레드에 담당자 안내. (2) "배포요청서 배포진행" 카드와 스레드에 요청자가 고른 값("순차적으로 하나씩 배포해주세요", "특이사항이 있어요", "배포 요청 시각에 시작해주세요") 기록. (3) 알리미가 "요청서 승인(배포대기) 처리 됐습니다", "배포순서: 모든 모듈이 동시 배포가 가능해요", "배포시각: 지금 시작해주세요", "배포 시작 처리 됐습니다", "배포진행", "배포완료", "검증종료 처리 됐습니다"를 순서대로 게시.
- 그림 13: 사내 칭찬 메시지 목록(2023/04/04~05/02, "최고예요", "고마워요", "전문가예요" 등 배지).

8. "즉, 상태 변경이 발생했을 때 배포 요청서에서 상태 변경 처리만 하면 슬랙 공유는 자동으로 되게 했는데요."
9. "배포 담당자 자동 배정 기능을 통해 RE파트의 모든 크루가 균등하게 배포를 진행하게 되었고, 배포 준비 절차의 피로를 줄일 수 있었습니다."
10. "VROOM 배포통제시스템은 카카오페이의 IT 내부 통제 관점에서 절차와 권한에 맞게 프로그램 변경(애플리케이션 배포)이 이뤄질 수 있도록 하기 위한 시스템입니다."

## 우리 설계에 쓸 만한 점
- [추론] 개발 부서와 운영 부서의 직무 분리를 규제처럼 강제하는 모델: 개발 에이전트는 배포 요청서만 만들고, 실제 반영은 운영 부서 에이전트만 할 수 있게 권한을 나누면 카카오페이 구조와 같다.
- [추론] "상태 변경 = 단일 진실 원천(요청서), 알림 = 파생"으로 설계: 에이전트는 티켓 상태만 바꾸고, 슬랙 같은 공유는 상태 변화 이벤트에서 자동 발행되게 하면 "처리했는데 공유 안 함" 류 누락이 구조적으로 사라진다.
- [추론] 자동화 경계를 그림 6처럼 명시: 확인, 배정, 공유, 폴링은 자동; 승인, 실제 배포, 검증 종료, 최종 종료 처리는 사람(또는 권한 있는 주체). 우리 운영 부서도 단계별로 "자동/사람" 표를 먼저 만들 것.
- [추론] 작업 배정은 "누적 처리량 하위권 중 랜덤" 같은 단순 공정 규칙과 "가능/불가능" 수동 토글 조합으로 충분하다. 에이전트 풀에도 부하 기반 배정과 수동 일시정지(자동 복구 없음)를 둘 수 있다.

- [추론] 인센티브(건수 평가)가 경쟁과 긴장 대기를 만든 사례는, 에이전트 평가 지표를 처리 건수로만 잡으면 작업 쟁탈이나 과잉 처리 유인이 생길 수 있다는 경고로 읽을 수 있다.
