## 사용자 결정 (2026-09-27)

> 카카오페이만큼 발전된 시스템을 구성하고 싶다. 필요하면 그 이상으로 발전시킨다. 베이스(바닥선)가 카카오페이다.

## 무엇을 바닥선으로 치는가

- **바닥선 = 카카오페이가 실제로 운영하는 것.** 운영 기록이 있는 글(PR 리뷰, SDD 실전기, 춘시리, 배포 봇, Dr.Pym, FDS, MCP Toolkit)의 관행.
- **하네스 개념의 바닥선 = 1편(kp: ai-agent-1).** 개념 설명 글이라 실측은 없지만, 카카오페이가 공개적으로 정리한 에이전트 운영 원칙이다.
- **해커톤 글은 바닥선이 아니라 참고.** 1박 2일 시제품이고 정량 평가가 없다. 다만 "언제 멀티에이전트를 쓰나"에 대한 판단 근거(음성 챗봇, 페이지니)는 가져온다.
- **그 이상 = 카카오페이 글에 없거나 약한 부분 중 외부 근거가 있는 것.** 근거 없이 늘리지 않는다.

## 영역별 바닥선과 그 이상

### A. 기획과 명세

| 카카오페이가 하는 것 | 우리 바닥선 | 그 이상 |
|---|---|---|
| spec-kit: constitution, specify, clarify(최대 5문항, 추천안 제시), plan, tasks, analyze, implement. analyze에서 CRITICAL 0이어야 구현. 산출물이 틀리면 직접 고치지 않고 specify로 돌아감 (kp: ifkakao-agentic-coding) | 모든 작업은 명세 문서에서 시작. 최상위 원칙 문서(constitution) 하나, 명세와 계획과 태스크 사이 일관성 검사 게이트 | 태스크에 넘기는 제약과 금지사항을 요약하지 않고 필드로 넘김. 요약 인계에서 금지 행동 54.2%, 구조화 시 0% (11 §5-6) |
| 설계 문서에서 태스크 분해, 의존성 정렬(10 Task를 5 Phase로), 1 subtask = 1 PR. 200줄 이하 PR 37%에서 60% (kp: kakaopayins-slow-pr-fast-dev) | 태스크는 의존성 순서와 병렬 가능 표시를 가짐. 결과물 하나 = 검토 단위 하나 | 흐름이 정해진 단계는 LLM 판단이 아니라 코드(workflow 스크립트)가 순서를 쥠 (11 §4) |
| 원칙 위반을 analyze가 잡음(첫 tasks가 TDD 위반). 단 implement 중 constitution을 가끔 무시 (kp: ifkakao-agentic-coding) | 원칙 위반 검사를 계획 단계에서 한 번 | 구현 단계에서도 원칙을 Hook이나 검사 스크립트로 강제(1편의 "구조로 막는다"를 구현 단계까지 확장) |

### B. 제작

| 카카오페이가 하는 것 | 우리 바닥선 | 그 이상 |
|---|---|---|
| 컨텍스트 계층: AGENTS.md(구조, 규칙) + SKILL(반복 작업) + Harness(위험 관리) + Plan + Subagent (kp: kakaopayins-slow-pr-fast-dev) | 규칙 파일은 짧게, 작업 지식은 Skill로 분리(kp: ai-agent-1) | 규칙 파일에 무엇이 들어갔는지 주기적으로 점검 |
| Subagent는 컨텍스트 격리 장치, 결론 한 덩어리만 반환 (kp: ai-agent-1) | 조사성 작업은 하위 에이전트에 넘기고 결론만 받음 | 나누는 기준은 일의 종류가 아니라 맥락 경계. 기능을 만든 에이전트가 그 테스트도 씀 (11 §2-1). 쓰기는 한 곳에서만 (11 §4) |
| 복잡한 지시는 성능 저하, 하나씩 쪼개 호출 (kp: kakaopay-hackathon-ai-finance-glossary, kakaopay-hackathon-aiva) | 한 호출에 한 가지 일 | |

### C. 검사

| 카카오페이가 하는 것 | 우리 바닥선 | 그 이상 |
|---|---|---|
| AI 리뷰어 조르깃: PR 열리면 4단계(언어, 프레임워크/인프라, 도메인/보안, 최종 검증), 모든 코멘트에 r/c/a 심각도 태그. **approve 불가**, 사람 승인 없이 머지 불가 (kp: kakaopayins-slow-pr-fast-dev) | AI 검사는 단계별 관점 + 심각도 태그. AI는 승인하지 못함 | 검사 모델을 제작 모델과 다른 계열로 두는 것 검토(같은 계열은 실수가 겹침, 11 §5-2) |
| PR 템플릿이 결정 기록: 왜, 한계와 트레이드오프, 영향, 실패 시나리오, 검토한 대안, 파일별 위험도. 작성자 자기검증 체크리스트 4개 (kp: kakaopayins-slow-pr-fast-dev) | 모든 산출물에 결정 기록 양식을 붙임. 트레이드오프 칸이 비었는지로 사람 검토 강도 결정 | |
| 루프 종료 기준: 외부 검증 통과 > 반복/토큰 상한 > 모델 자기 선언 (kp: ai-agent-1). SQL을 별도 호출로 검증 (kp: transaction-summary-and-search-with-ai) | 완료 판정은 외부 검증(테스트, 스키마, 원문 대조)으로. 모델의 "끝났다"는 종료 기준으로 쓰지 않음 | LLM 검사자는 실패작 약 절반을 통과시켰고(11 §6-2) AI 판정은 2.3~2.9배 과대평가(11 §6-1). 기계적 검사 먼저, 최종 품질은 사람 샘플링 |
| 조르깃 코멘트 188건 중 반영 16%, 거절 8%, 무응답 68% (kp: kakaopayins-slow-pr-fast-dev) | 검사 코멘트의 반영/거절/무응답 비율을 기록 | 무응답과 오탐을 줄이는 방향으로 검사 규칙을 주기적으로 조정 |

### D. 감독과 모니터링

| 카카오페이가 하는 것 | 우리 바닥선 | 그 이상 |
|---|---|---|
| Supervisor: 무거운 모델이 일하고 가벼운 모델이 진행 상태만 봄. 정체되면 Nudge, 안 되면 사람에게 Escalate (kp: ai-agent-1) | 감독 에이전트 1개(가벼운 모델), 옳고 그름이 아니라 진행 상태만. 2단계 대응 | |
| Hook: 저장, 커밋 직전에 린터, 테스트, 금지 파일 수정 차단. 지켜야 할 규칙은 Hook으로 (kp: ai-agent-1) | 반복 횟수, 토큰 예산 상한, 금지 행동을 Hook으로 강제 | |
| 하네스 3역할: 제어(hook, 권한, 린트, 의존성), 감시(supervisor, 실행 로그, 검증 게이트), 개선(위반 시 수정 지시를 컨텍스트로 되돌림) (kp: ai-agent-1) | 이 표를 설계 체크리스트로 사용 | |
| 배포 이벤트 전량 수집 대시보드(소요 시간, 실패율, 롤백 빈도) (kp: slack-bot-improving-operational-efficiency-2) | 에이전트 실행을 전량 기록 | 공식 OpenTelemetry 실행 기록으로 에이전트 호출 트리까지 시각화. 실패를 MAST 분류(명세, 에이전트 간 어긋남, 검증)로 라벨링 (11 §5-5) |

### E. 문서와 지식

| 카카오페이가 하는 것 | 우리 바닥선 | 그 이상 |
|---|---|---|
| 춘시리: 위키가 원본, 1시간마다 변경분만 다시 임베딩, 답변에 참고 문서와 수정일. 틀린 답은 `학습/`으로 위키부터 고침. `exclude` 라벨, 민감정보 발견 시 보안 채널 알림 (kp: choonsiri) | 원본 저장소 한 곳. 에이전트 답변과 산출물에 출처와 수정일. 정정은 원본부터 | 에이전트 사이 인계는 요약본 대신 원본 경로 + 구조화 필드 (11 §5-6) |
| 주간보고: 각자 확인, 팀 요약, 리더 버튼으로 게시 (kp: choonsiri) | 외부로 나가는 문서는 사람이 확정 | |

### F. 도구, 권한, 보안

| 카카오페이가 하는 것 | 우리 바닥선 | 그 이상 |
|---|---|---|
| MCP Toolkit: 도구마다 권한(actions) 정의, 허용 목록으로 노출 제한, LLM이 뽑으면 안 되는 값은 코드가 주입 (kp: kakaopay-mcp-agent-toolkit) | 에이전트별 허용 도구 목록. 식별자, 금액 같은 민감 값은 코드가 넣음 | 부서별 금지 행동을 권한과 Hook으로 차단 |

### G. 사람 승인 경계

| 카카오페이가 하는 것 | 우리 바닥선 |
|---|---|
| 배포 봇: 배정, 공유는 자동, 승인과 배포는 사람 (kp: slack-bot-improving-operational-efficiency). Dr.Pym: 추천까지 자동, 적용은 담당자가 선택하고 승인 (kp: ifkakao2024-dr-pym-project). FDS: 배포 버전은 분석가 선택 (kp: ifkakao2024-fds). ### H. 운영 자동화

| 카카오페이가 하는 것 | 우리 바닥선 |

## 카카오페이 내용 중 대체하는 것

바닥선을 낮추는 게 아니라, 근거가 더 나은 방법으로 바꾸는 것들이다.

| 카카오페이 내용 | 대체 | 이유 |
|---|---|---|
| 1편의 페르소나 분할("깐깐한 아키텍트", "손 빠른 주니어", "악독한 QA", 같은 모델에 다른 지시) | 역할을 명세(목표, 출력 형식, 도구, 경계)와 권한으로 정의. 페르소나 문구는 붙여도 되지만 기대하지 않음 | 1편은 개념 예시이고 실측 없음. 페르소나는 추론 모델에서도 정확도 효과 없음(11 §5-3). 일의 종류로 나누면 인계마다 맥락 손실(11 §2-1). 카카오페이 실사례도 이렇게 만들지 않음 |
| 부서마다 기획, 모니터링, 제작, 검사, 문서관리 에이전트 (처음 구상, 1편 페르소나 분할과 가까움) | 부서는 에이전트로 나눌 수 있으나, 5역할은 공정 단계(A~E)로 구현 | 위와 같음. 모니터링은 Supervisor 1개 + Hook, 문서관리는 저장소 + 양식 |
| 춘시리의 PR diff 전체를 한 프롬프트에 | 파일 단위로 나눠 검사 | 큰 diff에서 가드레일 스로틀링 발생(kp: choonsiri), 긴 입력은 길이 자체로 성능 저하(11 §5-7) |

## 아직 정하지 않은 것

- 부서별 도구와 권한이 실제로 다른지(J의 나누는 조건), 되돌릴 수 없는 행동 목록(G)이 무엇인지는 적용 대상이 정해져야 채울 수 있다.
- 첫 번째로 만들 "한 부서의 한 작업".
