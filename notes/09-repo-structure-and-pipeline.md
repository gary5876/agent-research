# 저장소 구조와 작업 파이프라인: 08 스키마를 이 저장소에 적용

[08-agent-implementation-schema.md](08-agent-implementation-schema.md)는 스키마만 정의하고 "이 저장소에 채워 넣는 일은 09번 몫"이라고 미뤘다. 이 문서가 그 09번이다. 2026-11-02 사용자 요청: "목적은 추후에 계속된 조사와 발전을 위한 폴더구조와 작업파이프라인 확보야."

## 핵심 한 문장

> 폴더는 자료의 종류(원문, 정리, 실험)로만 나누고, 주제와 상태는 문서 자신의 머리말에 둔다. 색인은 그 머리말에서 만들고 손으로 고치지 않는다.

## 1. 바꾼 이유: 질문이 바뀌었는데 구조는 그대로였다

2026-09-06에 폴더를 "에이전트 하나의 전문성 4요소"별로 짰다. 09-25 이후 연구 질문이 "여러 에이전트를 조율하는 조직과 마스터 에이전트"로 넘어가면서 다섯 가지 문제가 생겼다.

| 문제 | 증상 |
|---|---|
| P1 분류 기준 혼재 | 00~03 폴더는 4요소, 04와 05 폴더는 프로젝트 주제. 오케스트레이션 외부 조사(10~12)가 "금지 규칙" 폴더에 들어감 |
| P2 번호 겹침 | 폴더 번호(00~05)와 문서 번호(00~15)가 한 경로에 겹침. 09는 빈 채로 남고 studies, sources 안 파일은 번호가 없음 |
| P3 손 색인 4곳 | 문서 하나 추가 때 폴더 README의 트리와 표, 루트 README, CATALOG, JOURNEY를 손으로 고쳐야 함. 루트 README는 08에서 멈춤 |
| P4 다음 할 일 분산 | 08의 "09 미작성", 15의 "다음 번호 문서", 16 끝의 충돌 지점, JOURNEY의 열린 결정이 따로 있음 |
| P5 자료 종류 혼재 | 원문 노트, 공부 노트, 설계 판단, 구현 실험, 진행 기록이 같은 폴더 단위에 섞임 |

재편 중에 두 가지 고장도 확인했다.

- `eval/`의 테스트가 저장소 루트를 `../..`로 찾는데, 09-06 재편 때 eval이 한 단계 깊어져서 루트 대신 `agent-expertise-framework/`를 가리키고 있었다. 04, 05 문서의 "30 passed"는 그 재편 전 결과다.
- OpenWiki 예약 워크플로는 08-31 설치 때 OpenWiki 예제를 복사한 것으로, 모델 API 키 시크릿이 필요했다. 키를 넣은 적이 없어서 63번 실행이 모두 같은 단계에서 실패했다. 로컬 `openwiki/.last-update.json`은 09-06 재생성이 `interrupted`로 끝났음을 보여 주고, 그래서 위키가 00~03 네 문서만 다뤘다.

비교한 세 안과 점수(3점 만점)는 다음과 같다. A는 현 트리 유지와 최소 수선, B는 자료 종류별 층, C는 프로젝트별 폴더(PARA, spec-kit 방식).

| 기준 | A | B | C |
|---|---|---|---|
| 주제가 바뀌어도 안 깨짐 (P1) | 1 | 3 | 2 |
| 식별자 안정 (P2) | 2 | 3 | 2 |

B를 골랐다(사용자 승인 2026-11-02). 기존 번호는 그대로 식별자로 남겼다. 12, 14번이 `(10 A-2)`, `(11 §2-1)`처럼 번호로 다른 문서를 인용하기 때문에, 번호를 바꾸면 그 인용이 전부 깨진다.

## 4. 규칙

**폴더**

- `notes/NN-slug.md`: 우리가 쓰는 모든 정리 문서. 번호는 가장 큰 번호 + 1. 한 번 붙인 번호는 바꾸지 않는다.
- `sources/<주제>/`: 외부 자료 한 건당 노트 하나. 쓴 뒤에는 고치지 않는다. 그 폴더의 목차는 notes 문서가 맡는다(13이 `sources/kakaopay/`, 15가 `sources/master-orchestrator/`).
- `experiments/<이름>/`: 실행되는 코드. 폴더마다 README.
- `notes/diagrams/<이름>/`: 그림 원본(html)과 렌더 결과(png), `render.sh`.

**머리말** (notes 문서마다 필수, `check.py`가 검사)

```yaml
---
status: ACTIVE          # DRAFT | ACTIVE | PLANNED | DEPRECATED
layer: 2                # 1 원본 | 2 설계 | 3 구현 | 4 생성물
layer_note: "..."       # 선택. 층이 섞일 때 예외 구간
topic: [orchestration]  # scripts/build_index.py의 TOPICS 중에서
date: 2026-09-25        # 처음 쓴 날
summary: "..."          # 한 줄. index.md에 그대로 들어간다
---
```

**손으로 관리하는 것은 둘뿐이다.** [decisions.md](../decisions.md)(방향 결정)와 [JOURNEY.md](../JOURNEY.md)(진행 기록). 나머지 목록은 전부 `build_index.py`가 만든다. 문서 안의 연구 질문은 "열린 질문" 절에 두면 색인이 개수와 함께 모아 보여 준다.

## 5. 작업 파이프라인

1. **질문 등록.** 방향을 정하는 결정이면 `decisions.md`에 `open` 행을 단다. 문서 하나 안의 질문이면 그 문서의 "열린 질문" 절에 둔다.
2. **조사.** researcher 에이전트. 외부 자료 한 건의 원문 노트는 `sources/<주제>/`에 남긴다.
3. **검증.** 문서에 들어갈 주장, 특히 "없다"는 결론, 1순위 추천, 수치는 verifier로 다시 확인한다.
4. **정리.** `notes/NN-slug.md`에 머리말과 함께 쓴다.
5. **마감.** 결정이 났으면 `decisions.md` 행을 바꾼다. 큰 단계가 끝났으면 JOURNEY에 덧붙인다.
6. **색인과 검사.** `python3 scripts/build_index.py`, 그다음 `python3 scripts/check.py`.
7. **커밋.** 로컬 커밋. `.claude/hooks/check-before-commit.py`가 `git commit` 직전에 `check.py`를 돌려 실패하면 막는다.
8. **위키.** 필요할 때 로컬 Claude 세션에서 OpenWiki 스킬로 재생성하고 커밋한다. CI 예약 실행과 API 키는 쓰지 않는다(decisions D16).
9. **배포.** push는 따로 확인받는다.

## 8. 실행 결과

venv를 `experiments/eval/.venv`에 새로 만들고(Python 3.12.14) `requirements.txt`를 설치한 뒤 돌렸다.

| 테스트 | 결과 |
|---|---|
| `test_filter.py` | 통과. PEM 키와 이메일 탐지 |
| `compare_filters.py` | 이전 기록과 같음. regex 기준선 recall 0.75(3/4, AWS 키 누락), Presidio 1.00(4/4), 둘 다 오탐 0 |
| `test_grounding.py` | 24개 중 21개 실패, 3개 통과. 실패는 전부 Claim 근거가 옛 경로(`agent-expertise-framework/...`)의 파일을 가리켜서다. 통과 3개는 이동하지 않은 `AGENTS.md`와 `.mcp.json`을 가리킨다 |

그라운딩 실패는 이 테스트가 원래 잡으려던 것(근거가 사라진 Claim)을 정확히 잡은 결과다. OpenWiki를 로컬에서 다시 생성하면 Claim이 새 경로를 가리키게 된다. 04, 05 문서와 `experiments/eval/README.md`의 "30개 evidence", "30 passed"는 09-06 재편 전 기록이다.

같은 날 OpenWiki를 로컬에서 다시 생성했다(14개 페이지, 새로 쓴 것 8개). 그 뒤 `test_grounding.py`는 95개 전부 통과했다.

재생성 중 하나를 더 고쳤다. 생성 위키 수정을 막는 Hook(`.claude/hooks/block-openwiki-generated-edits.py`)이 OpenWiki 자신의 페이지 쓰기까지 막고 있었다. 09-06 재생성이 `interrupted`로 끝난 것도 이 때문이었을 가능성이 있다. 이제 `openwiki/.run.json`이 생성 단계이고 대상이 계획에 있는 대기 중 페이지일 때만 쓰기를 허용한다. Claims 파일, 생성 색인, 계획 밖 페이지는 그대로 막힌다.

## 열린 질문

- `sources/` 노트가 "쓴 뒤 고치지 않는다"를 지키는지는 지금 규칙으로만 있고 검사하지 않는다. 고친 이력이 생기면 Hook으로 막을지 정한다.
- topic이 한 문서에 둘 이상 붙는 경우(09, 16) 색인에 두 번 나온다. 이게 찾기에 도움이 되는지 방해가 되는지는 문서가 더 늘면 다시 본다.
- `decisions.md`에 행을 하나 끼워 넣자 그 아래 행을 줄 번호로 인용하던 위키 Claim 4개가 한 줄씩 어긋났는데, OpenWiki의 stale 검사는 이를 잡지 못했다(2026-11-02, 손으로 고침). 손으로 관리하는 표에 행을 추가할 때는 표 끝에 붙이거나, 추가 뒤 `grep -rho "repo://decisions.md#L[0-9-L]*" openwiki/.claims`로 인용 줄을 다시 확인한다. 이 확인을 `check.py`에 넣을지는 정하지 않았다.
