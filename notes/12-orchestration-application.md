# 오케스트레이션 설계 판단 (10, 11번 근거 적용)

**Status:** DRAFT
**Layer:** 2 (설계, 10과 11을 재료로 한 판단). 층 구분 기준: [CATALOG.md](../../CATALOG.md)
**작성일:** 2026-09-25 (같은 날 2026년 근거 반영)
**성격:** 판단과 제안. 근거 원문은 [10-orchestration-evidence-2023-2025.md](10-orchestration-evidence-2023-2025.md)(주로 2023~2025년)와 [11-orchestration-current-2026.md](11-orchestration-current-2026.md)(2026년 재확인)에 있고, 여기서는 `(10 A-2)`, `(11 §2-1)`처럼 절 번호로 가리킨다. 두 문서가 다르면 11을 따른다. 출처 없이 추론한 문장은 **[추론]**으로 표시한다.

## 출발점: 처음 구상

- 부서 3개: 마케팅, 개발, 운영
- 부서마다 역할 5개: 기획, 모니터링, 제작, 검사, 문서관리
- 전체를 조율하는 오케스트레이터
- 부서별 전문화를 위해 업무를 더 자세히 정의할 계획

이 구조는 총괄 1, 부서장 3, 워커 15로 약 19개 LLM 역할, 3단계 계층형이다.

## 0. 2026년 근거로 바뀐 점 요약

- **역할(직무)별로 나누는 것 자체가 명시적 문제로 지목됐다.** Anthropic 2026-01 글: 기능 작성, 테스트, 리뷰를 다른 에이전트가 맡으면 넘길 때마다 맥락이 손실된다. 나눌 거면 맥락이 실제로 분리되는 경계로 나눈다 (11 §2-1). 5역할 구조는 정확히 이 경우다.
- **3단계 계층은 도구가 지원하지 않는 경우가 있다.** Managed Agents는 코디네이터가 한 단계 아래에만 위임할 수 있고, Claude Code agent teams는 팀원이 팀원을 못 만든다 (11 §2-1, §4). Claude Code 하위 에이전트는 기본 3단계까지 되지만(10 D-1), 공식 제품들이 1단계 위임을 기본으로 설계했다는 점 자체가 신호다.
- **실제 운영 현장의 모습은 "계층형 에이전트 조직"이 아니었다.** DoorDash 월 13만 건 운영은 결정적 단계(일반 코드)와 에이전트 단계를 섞은 플레이북이었다 (11 §3). AI가 매장을 직접 운영한 2026년 사례는 전부 단일 관리자 에이전트 + 사람 직원이었고, 모두 아직 적자다 (11 §3-1). 조직도형으로 실제 사업을 운영한 공개 사후분석은 찾지 못했다.
- **오케스트레이터를 코드로 짜는 쪽으로 이동했다.** LLM이 매 턴 누구에게 맡길지 판단하는 대신, 스크립트가 흐름을 정하고 LLM은 각 단계만 한다 (11 §4). LLM은 500개 중 75개만 보고 끝났다고 할 수 있지만 코드 루프는 그러지 않는다 (11 §2-4).
- **모델이 좋아지면 구조를 걷어낸다.** Anthropic은 Opus 4.6에서 작업 분해 단계를 없애고 QA를 1회로 줄였다. "하니스의 모든 구성요소는 모델이 혼자 못 한다는 가정을 담고 있다" (11 §2-1). 구조는 한 번 짜고 끝이 아니라 모델이 바뀔 때마다 줄일 대상이다.
- **최신 모델에서 약해진 것**: 자기 교정이 무조건 해롭다는 결론(일부 추론 모델은 괜찮음, 11 §5-1), 긴 입력 중간 놓치기(단순 찾기는 거의 해결, 11 §5-7).
- **최신 모델에서도 그대로인 것**: 같은 비용이면 단일 에이전트가 대체로 이김(11 §5-4), 인계 시 정보 손실(11 §5-6), 페르소나 무효과(11 §5-3), 판정자 편향(11 §5-2).

## 1. 공식 가이드가 공통으로 하는 말

단일 에이전트로 시작하고, 실패가 관찰됐을 때만 나눈다. Anthropic(10 A-1), OpenAI(10 A-3), Microsoft(10 A-5), Google(10 A-6), LangChain(10 A-4)이 모두 같은 말을 한다. 2026년 자료에서도 이 입장은 바뀌지 않았다(11 §2). 계층형은 Google이 가장 복잡하고 비싼 유형으로 분류하고(10 A-6), LangChain도 먼저 평탄화하라고 권한다(10 A-4).

나누는 게 정당한 신호
- 도구를 계속 잘못 고르거나 복잡한 지시를 못 따라올 때 (10 A-3)
- 병렬로 나눌 수 있는 탐색형 작업일 때 (10 A-2). 2026년엔 쓰기 작업도 파일, 워크트리, VM 단위로 격리하면 병렬이 됨 (11 §4)
- 맥락이 실제로 분리될 때. Anthropic 2026 기준은 컨텍스트 보호, 병렬화, 전문화 세 경우 (11 §2-1)
- 권한이나 보안 경계를 분리해야 할 때 (10 A-5)
- 어느 경우든 측정해서 개선이 확인될 때만 (10 A-1)

나누면 안 되는 신호
- 에이전트들이 같은 컨텍스트를 공유해야 하거나 서로 의존이 많을 때 (10 A-2, A-7)
- 전문성이 실제로 다르지 않은데 역할만 나눌 때 (10 A-5 안티패턴)
- 작업 가치가 늘어나는 토큰 비용을 감당하지 못할 때. 2025년 수치 약 15배(10 A-2), 2026년 Anthropic 수치 3~10배(11 §2-1)
- 일의 종류(작성, 테스트, 리뷰)로 나누려 할 때 (11 §2-1)
- 순차 의존이 강한 작업일 때. 멀티에이전트가 39~70% 악화 (10 C-2)

## 2. 5역할은 전문 분야가 아니라 공정 단계다

**[추론]** 기획, 모니터링, 제작, 검사, 문서관리는 도메인 전문화가 아니라 한 작업 흐름의 단계다. Anthropic 2026-01 글이 "일의 종류로 나누기"를 넘길 때마다 맥락이 손실되는 구조로 지목했는데(11 §2-1), 5역할 분할이 바로 그 형태다. 역할극형 멀티에이전트는 TheAgentCompany에서 완수율 4.0%로 단일 에이전트 8.6%의 절반이었다(11 §6-1). 부서마다 5개를 모두 독립 에이전트로 두면 "의미 있는 전문화가 없는 에이전트 추가"(10 A-5)에 해당할 가능성이 크다. 15개를 대칭으로 찍어내는 구조는 조사한 연구 어디에서도 근거를 찾지 못했다. MetaGPT, ChatDev도 역할은 5개 안팎이고, 과제 하나의 파이프라인 단계에 맞춰 정했다(10 B-1, B-2). 그 원조 프로젝트들은 2026년에 정체되거나(MetaGPT) 동적 오케스트레이션 플랫폼으로 방향을 바꿨다(ChatDev 2.0, 11 §6-3).

근거에 맞게 옮기면

| 원래 역할 | 근거에 맞는 구현 | 근거 |
|---|---|---|
| 기획 | 별도 에이전트가 아니라 오케스트레이터의 일. 계획은 필드가 정해진 양식으로 남긴다. 흐름이 고정된 일이면 오케스트레이터 자체를 코드(스크립트, 플레이북)로 짠다 | lead가 계획을 세워 Memory에 저장 (10 A-2). 과업 명세 위반 11.8%, 명확화 질문 안 함 6.8% (10 C-1). 코드가 오케스트레이터 (11 §4), DoorDash 플레이북 (11 §3) |
| 제작 + 검사 | 제작은 맥락을 가진 한 에이전트가 끝까지 맡는다(기능 작성과 그 테스트를 같은 에이전트가). 검사는 따로 두되 기계적 검사(테스트, 스키마, 체크리스트, 원문 대조)를 먼저, LLM 검사는 제작 쪽 추론 없이 명세와 결과물만 받는다 | evaluator-optimizer, maker-checker (10 A-1, A-5). 외부 신호 없는 자기검증은 역효과 (10 C-3). 컨텍스트를 분리한 리뷰어가 효과 (10 A-7). 맥락 경계로 나누기, 검증 에이전트는 예외로 인정 (11 §2-1). 검증자가 실패작의 약 절반 승인 (11 §6-2) |
| 모니터링 | LLM이 아니라 규칙. 최대 반복 횟수, 토큰 상한, 같은 호출 반복 감지, 제한 시간을 Hook이나 코드로 건다. 전체 실행 로그를 남긴다 | 같은 단계 반복 15.7%, 종료 조건 인지 못함 12.4%로 실패 유형 1, 2위권 (10 C-1). 출처들은 모니터링을 트레이싱 인프라로 다룸 (10 A-2, A-5) |
| 문서관리 | 에이전트가 아니라 공유 저장소 + 문서 양식. 원본은 파일로 두고 경로만 넘긴다. 제약과 금지사항은 요약하지 않고 필드로 원문 그대로 넘긴다 | 결과를 파일에 쓰고 참조만 전달 (10 A-2). 요약 인계 시 금지 행동 54.2%, 구조화 시 0% (10 C-4). MetaGPT의 공유 메시지 풀 (10 B-1) |

## 3. 부서 분리는 조건부로 정당하다

**[추론]** 마케팅, 개발, 운영은 쓰는 도구와 권한이 실제로 다를 가능성이 크다. 그러면 부서 단위로 나누는 건 OpenAI의 도구 과부하 기준(10 A-3)이나 Microsoft의 보안 경계 기준(10 A-5)에 맞고, Anthropic 2026의 "맥락이 실제로 분리되는 경계"(11 §2-1)에도 맞을 수 있다. 부서 간 공유가 적을수록 정당하다. 반대로 부서 안에 팀장 계층을 하나 더 두는 건 "중간 조정이 정말 필요할 때만 중첩"(10 A-4)에 해당하는지 따로 따져야 한다.

부서 간 인계는 요약이 여러 번 겹치는 지점이다. **[추론]** 부서 A 산출물이 오케스트레이터를 거쳐 부서 B로 갈 때 요약본이 아니라 공용 저장소의 경로를 넘긴다. 중앙 검증이 없으면 오류가 더 번진다(10 C-2).

## 4. 검사 에이전트 설계 지침

- 검사 에이전트를 따로 둘 가치가 있는 조건 (11 §2-1): 오케스트레이터 모델이 약할 때, 검사에 특수 도구가 필요할 때, 검사 체크포인트를 강제하고 싶을 때. 오케스트레이터가 최신 상위 모델이면 별도 검사 단계 없이 직접 평가하는 쪽이 늘고 있다
- LLM 검사자를 믿지 않는다. 검증자 역할이 실패작의 약 절반을 승인했고(TeamBench, 11 §6-2), AI 판정자는 실제 업무 완수율을 2.3~2.9배 과대평가했다(RLI, 11 §6-1)
- 제작 쪽 추론 과정은 넘기지 않고 명세와 산출물만 준다 (10 A-7 컨텍스트 분리)
- 실행형 검사 도구(테스트, 스키마 검증, 원문 대조)를 쥐여 준다 (10 C-3 Stechly, Kamoi)
- 판정 모델을 제작 모델과 다른 계열로 두는 걸 고려한다. 같은 계열은 실수가 겹치고(10 C-3, 11 §5-2 Kim et al.), 자기선호는 모델마다 방향이 다르다(Claude Sonnet 4.5는 자기 답을 오히려 깎음, 11 §5-2). 다른 회사 모델이라도 크고 정확할수록 오류가 겹친다는 결과가 있어 완전한 해결책은 아니다
- 검사 결과는 제작 쪽이 사용자 의도에 비춰 거른다. 무조건 반영하면 의도한 것까지 "버그"로 고친다 (10 A-7 Cognition 필터 단계)
- 최종 품질은 사람이 샘플을 뽑아 따로 본다. SEO 편향은 사람만 잡았다 (10 A-2)
- 같은 모델로 상사와 부하를 만들어 감독을 기대하지 않는다. Project Vend CEO는 요청을 거절보다 약 8배 많이 승인했다 (10 B-6). 2026년 Andon Market에서도 관리자 에이전트가 21회 전부 부적격 지원자 채용을 승인했다 (11 §3-1)
- 자기 교정 단계는 최신 추론 모델에서는 해가 줄었다(11 §5-1). 다만 이득이 나려면 새 오류를 만들어 넣는 비율이 0에 가까워야 하므로, 외부 신호 없는 "다시 검토해" 루프에 품질을 기대하지 않는다

## 5. 역할 정의는 직함이 아니라 명세로

- "당신은 마케팅 전문가입니다" 같은 페르소나는 정확도 근거가 약하다 (10 B-5). o3-mini, o4-mini 같은 추론 모델에서도 마찬가지 (11 §5-3)
- 효과가 있었던 것: 책임 범위, 절차, 산출물 양식 명세. 역할 명세 개선만으로 +9.4%p (10 C-1, 2025년 초 모델 기준). 역할을 OS 권한으로 강제하든 프롬프트로 나누든 팀 통과율 차이는 없었다(11 §6-2). 역할 경계보다 명세 내용이 중요하다는 방향이다. 위임 시 목표, 출력 형식, 도구 안내, 작업 경계 4가지 (10 A-2)
- **[추론]** 처음 구상의 "각 분야 전문화를 위해 업무를 더 자세히 정한다"가 실제로 효과를 내는 지점이 바로 여기다. 직함 대신 이 4가지와 실제 사고에서 나온 금지 규칙을 채운다. agent-research의 `.claude/agents/` 4개가 그 방식의 예시다.

## 6. 마케팅, 운영 부서는 사람 확인을 더 촘촘히

가상 회사 벤치마크(TheAgentCompany)에서 논문 시점 최고 에이전트는 약 30%였고, 리더보드 검증 1위는 42.86%(2025-11)다. 2026년 최신 모델로 검증된 등재는 없다(11 §6-1). 행정, 재무, 데이터 업무가 가장 어려웠고, 담당자를 못 찾자 다른 사용자 이름을 바꿔 "해결한 척"한 사례도 있다(10 B-6).

2026년 벤치마크로 보면 짧은 과제는 대부분 포화됐지만, 사람이 1시간 넘게 걸리는 업무는 최고 모델도 약 15~20%만 완수한다(OSWorld 2.0 20.6%, Remote Labor Index 15.8%, 11 §6-1).

마케팅에서 AI가 잘한 측정 결과는 모두 사람이 검수한 조건이었다. 사람+AI 팀은 광고를 50% 더 만들었지만 이미지 품질은 사람 팀이 나았고(11 §6-5), AI 광고 CTR이 높았던 실험도 브랜드 기준 검수와 현장 테스트는 사람이 했다. 자율 발행 실험(Andon FM)에서는 평판 사고가 났고, 가격과 할인 결정을 맡긴 매장(Andon Café, Vend)은 손해를 봤다(11 §3-1).

**[추론]** 개발 부서보다 마케팅, 운영 부서에 사람 확인 단계를 더 둔다. 특히 외부 발행, 가격, 할인, 예산, 채용 같은 결정은 사람 승인을 건다. 되돌릴 수 없거나 위험한 행동에는 사람 승인을 건다(10 A-3). 실무 조사에서도 68%의 에이전트가 10단계 안에 사람 개입을 받는다(11 §6-4).

## 7. 권장 경로

1. 한 부서의 한 작업을 에이전트 하나 + 도구로 만든다. 실제 요청 20개쯤으로 평가 세트를 만들어 기준 점수와 토큰을 잰다 (10 A-2). DoorDash도 코드리뷰 하나로 좁게 시작해 신뢰를 쌓은 뒤 넓혔다 (11 §3)
2. 흐름이 정해진 부분은 에이전트가 아니라 코드(플레이북, 스크립트)로 고정하고, 판단이 필요한 단계만 에이전트에게 맡긴다 (11 §3, §4)
3. 품질 문제가 확인된 곳에만 검사를 붙인다. 기계적 검사가 먼저, LLM 검사는 그다음
4. 도구가 섞여서 잘못 고르는 문제가 보이면 부서별 에이전트로 나눈다. 총괄 하나가 부서 에이전트를 도구처럼 부르는 manager 구조 (10 A-3)
5. 부서 안 하위 계층은 마지막 수단. Claude Managed Agents와 agent teams는 1단계 위임만 지원한다. 반면 Claude Code 하위 에이전트는 기본 3단계, OpenAI Responses 멀티에이전트는 깊이 제한이 없다 (10 D-1, 11 §2-1, §2-2, §4)
6. 단계마다 점수와 토큰을 기록하고, 같은 예산의 단일 에이전트 기준선과 비교해서 좋아졌을 때만 다음으로 간다 (10 C-2, 11 §5-4)
7. 모델을 바꿀 때마다 기존 구조 중 걷어낼 수 있는 게 있는지 다시 잰다 (11 §2-1)

## 8. 실행 수단 (Claude Code 기준)

- 1~4단계는 Claude Code 하위 에이전트(`.claude/agents/`)로 충분하다. 중첩 3단계, 동시 20개, CLAUDE.md는 받고 대화 기록은 못 봄 (10 D-1)
- 흐름을 코드로 고정하는 부분은 Claude Code workflows(스크립트가 오케스트레이터)가 맞다 (11 §4)
- agent teams는 아직 실험 기능이고, 순차 작업과 같은 파일 수정에는 공식 문서가 하위 에이전트나 단일 세션을 권한다 (11 §4)
- 모니터링 규칙은 Hook으로 강제한다 ("Hook은 확정, 프롬프트는 확률", agent-research 07번 문서)
- 주기적으로 돌 작업은 `/loop`(세션 열려 있어야 함, 7일 만료)이 아니라 Routines나 Desktop 예약 작업 (10 D-2)
- 제품으로 올릴 때 Agent SDK나 Managed Agents 검토. Managed Agents는 1단계 위임만, 로스터 20개, 동시 스레드 25개 (11 §2-1, 재확인 완료)
