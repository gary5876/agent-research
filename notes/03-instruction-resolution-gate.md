# 요구사항 해석 게이트 — 전문화된 에이전트를 위한 자연어→실행 지시 변환 레이어

**Status:** ACTIVE
**Layer:** 2 (설계) — 층 구분 기준: [CATALOG.md](../../CATALOG.md)

`02-instruction-clarity-incident.md`에서 다룬 사건을 재료로, 전문화된 에이전트들을 쓰기 위해 사용자와 에이전트 사이에 둬야 할 레이어를 설계한다. 사용자의 결론: "정말 전문화된 agent를 쓰려면, 내 자연어를 LLM이 받아들이기 좋은 형태로 분석·재조립하는 레이어가 필요하다." 이 문서는 그 레이어가 뭘 해야 하는지, 왜 모델의 판단에만 맡기면 안 되는지를 정리한다.

2026-09-21 보강: 사용자가 이 레이어를 "사람의 애매한 말을 정교한 프롬프트로 조립해 나가는 번역 레이어"로 다시 정리했다. 조립에 필요한 재료는 사람의 대답만이 아니라 검색도 있어야 하고, 둘이 번갈아 돌면서 프롬프트를 완성해 나간다는 것이다. 처음 버전은 "조회 시도 → 안 되면 질문"이라는 한 방향 직선이었는데, 이 보강으로 2절 파이프라인을 루프로 바꾸고, 어떤 슬롯이 필요한지를 정하는 분야별 슬롯 스키마(3절)와 완성 프롬프트 확인 단계(5절)를 추가했다.

## 핵심 한 문장

> 이 레이어의 목적은 "질문을 없애는 것"이 아니라, "조회로 풀리는 애매함"과 "사용자만 답을 아는 애매함"을 구분해서, 전자를 질문으로 던지는 걸 막는 것이다.

## 1. 애매함은 두 종류다

- **조회형 애매함**: 답이 이미 세상에 존재하고, 에이전트가 가진 컨텍스트(대화 메모리, 이전 발화)나 도구(API, 파일시스템, 웹 조회)로 확정할 수 있는 것. 예: "내 깃허브에 있는 레포" — 계정 정보와 `gh api`만 있으면 조회로 끝난다.
- **결정형 애매함**: 후보가 여러 개거나, 사용자의 취향·우선순위·판단이 답 그 자체인 것. 예: "이 워크스페이스의 어떤 디렉토리를 정리할까" — 정답이 세상에 있는 게 아니라 사용자 의도가 정답이다.

이 레이어의 존재 이유는 이 둘을 섞지 않는 것이다. 조회형을 결정형처럼 취급해서 사용자에게 되던지면 오늘 같은 사건이 나고, 반대로 결정형을 조회형처럼 취급해서 에이전트가 임의로 확정해버리면 사용자 의도와 다른 작업이 실행된다.

## 2. 파이프라인: 검색과 질문이 맞물리는 루프

```
사용자 발화
  → 요청 분야 판별 → 그 분야의 슬롯 스키마 로드 (3절)
  → 빈 슬롯이 남아 있는 동안 반복:
      빈 슬롯 하나를 고른다
      ├ 대화 컨텍스트/메모리에 값이 이미 있음 → 채움
      ├ 조회형 슬롯 → 스키마에 적힌 출처로 검색
      │    ├ 결과가 하나로 확정 → 채움
      │    └ 결과 없음 또는 후보 다수 → 검색 결과를 선택지로 붙여 확인 질문
      └ 결정형 슬롯 → 이미 채운 슬롯과 검색 결과로 선택지를 만들어 확인 질문
      방금 채운 값이 다른 슬롯의 검색 단서가 되면 그 슬롯을 다시 검색 대상으로 돌린다
  → 완성된 프롬프트를 사용자에게 한 번 보여주고 확인 (5절)
  → 실행
```

처음 버전과 다른 점은 검색과 질문이 순서만 다른 두 단계가 아니라 서로의 재료가 된다는 것이다.

- **검색이 질문의 재료가 된다.** "어떤 레포요?"라고 빈손으로 묻지 않고, 스타 목록을 먼저 검색해 후보를 추린 다음 "이 중 어느 거예요?"라고 묻는다. 사람은 빈칸을 채우는 것보다 선택지를 고르는 걸 훨씬 정확하게 한다. 질문을 하더라도 검색을 거친 질문이어야 대답이 정교해진다.
- **대답이 새 검색을 부른다.** 사용자가 "두 번째 거"라고 답하면, 그 레포의 README를 읽어야 다음 슬롯(정리 기준)이 채워진다. 그래서 검색 한 번, 질문 한 번으로 끝나지 않고 슬롯이 다 찰 때까지 루프를 돈다.

루프로 바뀌어도 불변 조건은 그대로다. 조회형 슬롯에서 "확인 질문 생성"은 항상 검색 시도 이후에만 온다. 검색을 시도하지 않은 채로 조회형 슬롯의 질문 단계에 도달하는 경로는 구조적으로 없어야 한다.

## 3. 분야별 슬롯 스키마

처음 버전은 파이프라인 첫 단계를 "슬롯 추출"이라고만 적고, 어떤 슬롯이 필요한지는 정하지 않았다. 매번 모델이 발화를 보고 즉석에서 슬롯을 뽑으면 두 가지가 흔들린다. 필요한 슬롯을 빠뜨리는 것, 그리고 슬롯마다 조회형인지 결정형인지를 매번 새로 판단하는 것이다. 02 사건은 뒤쪽이 틀린 사례였다.

그래서 슬롯 목록은 분야별로 미리 적어 둔다. 슬롯마다 세 가지를 붙인다.

| 붙이는 정보 | 뜻 |
|---|---|
| 유형 | 조회형 / 결정형 |
| 조회 출처 | 조회형이면 어디서 찾는지 (메모리, 파일, API, 웹). 결정형이면 선택지를 만들 재료를 어디서 가져오는지 |
| 의존 | 이 슬롯이 채워져야 검색할 수 있는 다른 슬롯 |

02 사건의 요청("참고 레포를 보고 문서 정리 다시 하기")에 적용하면 이렇게 된다.

| 슬롯 | 유형 | 조회 출처 | 의존 |
|---|---|---|---|
| 참고 레포 | 조회형 | memory의 깃허브 계정 → `gh api users/{계정}/starred` | 없음 |
| 정리 기준 | 조회형 | 참고 레포의 README와 문서 | 참고 레포 |
| 정리 대상 디렉토리 | 결정형 | 선택지 재료: 워크스페이스 디렉토리 목록 | 없음 |

이 표를 미리 갖고 있으면 "참고 레포"를 사용자에게 묻는 경로가 애초에 생기지 않는다. 유형이 조회형으로 박혀 있기 때문이다.

이 스키마가 저장소 목표(자기 분야에 전문성 있는 에이전트)와 직접 이어지는 지점이다. 코드 리뷰 요청에 필요한 슬롯(대상 diff, 리뷰 기준, 심각도 기준)과 자소서 요청에 필요한 슬롯(회사, 문항, 쓸 경험 하나, 글자수)은 다르다. 어떤 요청에 무엇이 빠져 있는지를 아는 것, 즉 그 분야의 슬롯 목록을 아는 것이 곧 그 분야의 전문성이다.

## 4. 왜 이 순서를 모델의 판단에 맡기면 안 되는가

처음엔 이 파이프라인을 "모델이 스스로 이 순서로 생각하게" 만드는 걸로 충분하다고 봤다. 하지만 `02-instruction-clarity-incident.md`의 사건을 다시 보면, 실제로 일어난 건 "조회할지 질문할지 비교하다가 질문을 잘못 골랐다"가 아니라, **비교 자체가 실행되지 않고 "값이 비어있음 → 질문 생성"이 반사적으로 바로 연결됐다**는 것이다. 즉 생략된 건 선택이 아니라 숙고 단계 그 자체였다.

이게 중요한 이유: 같은 모델에게 "이번엔 순서를 지켜서 생각해"라고 지시문에 적어두는 것만으로는 재발을 막지 못한다. 오늘 스킵된 게 바로 그 "생각하는 단계"이기 때문에, 모델이 자기 사고 과정 안에서 그 단계를 다시 스스로 챙기길 기대하는 설계는 같은 실패를 반복할 수 있다.

그래서 이 레이어는 **체크리스트가 아니라 구조적 게이트**로 만들어야 한다. 예: "사용자에게 질문을 보내는 행동(tool call)"은 "해당 슬롯에 대해 조회를 시도했다는 기록이 먼저 존재해야만" 실행 가능하도록, 모델의 사고 과정 바깥에서 강제한다. 모델이 그 단계를 생략하고 싶어도 생략할 수 없게 만드는 것 — 이게 "판단을 맡기는 레이어"와 "판단을 강제하는 레이어"의 차이다.

3절의 슬롯 스키마가 있으면 이 게이트를 기계적으로 검사할 수 있다. 질문이 나가려는 슬롯의 유형이 스키마에서 조회형이면 검색 기록을 요구하고, 결정형이면 통과시킨다. 슬롯 유형을 모델이 그때그때 판단하게 두면 게이트가 검사할 기준 자체가 없다.

## 5. 완성 프롬프트 확인과 질문 상한

루프가 끝나면 조립된 프롬프트를 실행 전에 사용자에게 한 번 보여준다. 슬롯마다 값이 어디서 왔는지(메모리, 검색, 사용자 대답, 기본값)를 같이 표시한다. 이 단계가 있는 이유는 두 가지다.

- **검색 결과가 틀린 경우를 잡는다.** 검색으로 후보가 하나로 좁혀졌다고 그게 사용자 의도라는 보장은 없다. 확인 없이 진행하면 02 사건의 반대 방향 실패(조회를 과신해서 엉뚱한 걸 실행)가 난다. 슬롯마다 질문하는 대신 완성본을 한 번에 확인받으면, 사용자 부담은 한 번으로 끝나고 틀린 슬롯만 고치면 된다.
- **질문 피로를 막는다.** 결정형 슬롯이 많은 요청에서 질문을 계속 던지면, 사용자는 몇 개 넘어가면서부터 대충 답하고, 그러면 애매한 입력이 다시 들어온다. 그래서 질문 개수에 상한을 두고, 상한을 넘은 결정형 슬롯은 기본값으로 채운다. 기본값으로 채웠다는 사실은 확인 화면에 드러나야 한다. 숨겨진 기본값은 에이전트가 결정형 슬롯을 임의로 확정하는 실패(1절)와 같다.

## 6. 오늘 사건에 이 파이프라인을 적용하면

- 슬롯 추출: "참고할 레포"라는 슬롯이 미확정 상태로 추출됨.
- 컨텍스트 확인: 대화 메모리에 사용자 깃허브 계정(`gary5876`)이 이미 있음 → 이 슬롯은 조회 가능 후보로 분류.
- 조회 시도: `gh api users/gary5876/starred` 실행.
- 결과: 28개 중 "LLM이 읽기 좋게 문서정리" 설명과 일치하는 게 `langchain-ai/openwiki` 하나로 좁혀짐 → 확정 진행. 만약 후보가 여러 개로 애매하게 남았다면, 그 후보들을 근거로 "이 중에 맞는 게 있나요?"라는 확인 질문(결정형)으로 넘어감 — 이건 정상적인 질문이다.

반면 "어떤 디렉토리를 정리할까"는 처음부터 결정형 슬롯이므로 조회 시도 없이 바로 확인 질문으로 가는 게 맞고, 실제로도 그렇게 처리됐다. 문제는 두 슬롯을 같은 급으로 섞어서 조회형까지 결정형 취급한 것뿐이었다.

루프 버전(2절)으로 다시 그리면 여기서 끝나지 않는다. 아래는 실제로 일어난 일이 아니라 사후 재구성이다. "참고 레포"가 `langchain-ai/openwiki`로 채워지면, 그 값을 단서로 "정리 기준" 슬롯이 검색 대상이 되어 openwiki의 README를 읽는다. "정리 대상 디렉토리"는 결정형이니 워크스페이스 디렉토리 목록을 선택지로 붙여서 묻는다. 세 슬롯이 다 차면 "openwiki의 문서 구조를 기준으로 {고른 디렉토리}를 재정리"라는 완성 프롬프트를 보여주고, 사용자가 확인하면 실행한다.

## 7. 열린 질문 (아직 이 문서에서 답하지 않은 것)

- 처음 버전의 열린 질문 두 개는 이번 보강으로 방향이 잡혔다. "조회가 틀린 결과를 낼 경우"는 5절의 완성 프롬프트 확인으로, "조회 가능 여부를 슬롯 단위로 판별하는 기준"은 3절의 슬롯 스키마에 유형을 미리 적어 두는 것으로 다룬다. 둘 다 아직 설계일 뿐 구현해서 검증하지는 않았다.
- 슬롯 스키마는 누가, 어떤 근거로 쓰는가. 지금 있는 예시는 02 사건 하나를 사후에 분류한 것뿐이다. 실패 사례가 쌓일 때마다 스키마에 빠진 슬롯을 추가하는 방식이면 요소4(실패 사례 기반 금지 규칙)와 같은 구조가 되는데, 아직 연결하지 않았다.
- 요청이 어느 분야인지 판별하는 첫 단계가 틀리면 엉뚱한 스키마가 로드된다. 이 판별을 어떻게 하고, 틀렸을 때 어떻게 알아챌지는 정하지 않았다.
- 질문 상한을 몇 개로 둘지, 상한을 넘었을 때 어떤 결정형 슬롯부터 기본값으로 채울지 기준이 없다.
